# Скелет для политики: технические факты

Сверка по дереву `1b85e200`, боевым базам и живым логам. 24.08.2026.
Юридических формулировок здесь нет — только то, что делает код.

Каждый факт помечен: **[ЕСТЬ]** — работает сегодня · **[ПЛАН]** — назначено
спекой веба, кода нет · **[НЕТ]** — проверено, что этого не происходит.

---

## 1. Что собирается

Хранилище — SQLite на машине, отдельная база на клиента (`.secrets/<slug>.db`,
`chatter/core/client_registry.py:97`). Данные лежат в открытом виде.

**[ЕСТЬ] Текст переписки** — `messages(contact_id, role, text, ts)`. Реплики
собеседника и ответы бота целиком, без обрезки. В боевой базе 386 записей.

**[ЕСТЬ] Идентификатор собеседника** — `contact_id` вида
`<внешний_id>:<персона>`. Внешний id выдан платформой: для Telegram это номер
аккаунта. Плюс `contacts.display_name` — имя из профиля платформы, если она его
отдала.

**[ПЛАН] Для веба** — вместо платформенного id случайный номер сессии в cookie
браузера: ключ `web:<session_id>:<slug>` (спека веба §3). Ни имени, ни
привязки к другим сайтам; склейка по IP и отпечатку устройства не делается —
это решение, а не недоделка (§3, следствие 1).

**[ЕСТЬ] То, что собеседник назвал сам** — `contact_profile(text)`: 64 версии
профиля, накопительный текст о человеке, собранный из разговора (имя, телефон,
детали заказа — всё, что прозвучало). Плюс `facts(key, value)` — пары «ключ:
значение» (в боевой базе пусто).

**[ЕСТЬ] Состояние диалога** — `contacts`: этап, пауза и её источник, метка
`human_took_over`, `last_human_out_ts`. `funnel_transitions` — история переходов
по воронке (35 записей). `contact_obligations` — что бот пообещал и закрыл ли
(15 записей). `console_cards` — какие карточки ушли владельцу (60 записей).
`control_events` — нажатия владельца (35 записей).

**[ЕСТЬ] Деньги** — `quotes`, `invoices`, `invoice_stages`, `payments`: суммы,
валюта, статус, даты, ссылка на реквизиты. Реквизитов карт в схеме **[НЕТ]** —
оплата идёт вне сервиса, подтверждение приходит как факт.

**[ЕСТЬ] Счётчики модели** — `llm_usage(ts, tag, model, токены)`, 297 записей.
Текста в них нет.

## 2. Где лежат копии — их ЧЕТЫРЕ, не одна

Это главный пункт скелета: считать копией только базу неверно.

| # | где | что внутри | ротация |
|---|---|---|---|
| 1 | рабочая база `.secrets/<slug>.db` | всё из §1 | **нет** |
| 2 | лог раннера `logs/chatter_<slug>.log` | **полный текст входящих** + id отправителя | **нет** |
| 3 | бэкап Cloudflare R2 | зашифрованная копия базы | есть, 365 дней |
| 4 | Telegram владельца | фрагменты реплик в карточках | не применимо |

**Копия 2 [ЕСТЬ], и она не учтена нигде.** Строка
`telethon_run.py:1569` пишет в лог `IN <id> [<персона>]: <полный текст>`.
Проверено на живом файле `logs/chatter_volska.log` — реплики клиентов лежат
там открытым текстом, вместе с номером аккаунта. Логи **не попадают в бэкап**
(`app/services/state_backup.py` берёт только `state/`) и **не ротируются**:
в `chatter_guardian_detached.ps1` ротации для этих файлов нет.

**Копия 4 [ЕСТЬ]:** карточка эскалации содержит до **5 последних реплик по 200
символов** каждая (`chatter/core/console.py:691`, `safe_snippet(text, limit=200)`)
и уходит владельцу через Bot API (`api.telegram.org`,
`chatter/notify/control_bot.py:235`). Следствие для веба: посетитель пишет на
сайте, а фрагмент его сообщения уезжает в Telegram.

**Полный дамп промпта** (профиль + переписка, 30–40 КБ на ход) пишется в
`logs/prompt_dump.log` **[НЕТ]** — только под переменной `CHATTER_PROMPT_DUMP`,
в живой среде она не выставлена, файла на диске нет. Постоянная строка
`prompt_log` пишется без ПДн: хеш контакта, длины блоков, счётчики.

## 3. Кто из подрядчиков видит данные

**[ЕСТЬ] Anthropic** — текст переписки и профиль уходят на API, чтобы составить
ответ. Единственный клиент модели в горячем пути клиента:
`chatter/core/llm.py:160`. Это не опция — без него сервис не отвечает.

**[ЕСТЬ] Telegram** — в двух разных ролях: как канал (переписка идёт через их
серверы) и как транспорт карточек владельцу (§2, копия 4). Вторая роль
сохраняется для ЛЮБОГО канала, включая веб.

**[ЕСТЬ] Cloudflare** — R2 как хранилище зашифрованных копий; ключ вне сервера,
хост умеет писать копию и не умеет её читать (DEV-46). Плюс туннель как транзит
трафика.

**[ПЛАН] Meta** — при включении Instagram, как платформа канала.

**[НЕТ] Остальное:** OpenAI в пути переписки клиентов не участвует (живёт в
`app/services/*`, другое крыло); распознавания голоса в пути `chatter` нет;
передач переписки куда-либо ещё в коде не найдено.

| объект | срок | статус |
|---|---|---|

| переписка в логе раннера | **бессрочно** | **[ЕСТЬ]** — ротации нет |
| зашифрованная копия в R2 | 365 дней | **[ЕСТЬ]** — `keep_days = 365` |
| переписка веб-посетителя | 365 дней | **[ПЛАН]** |
| cookie `session_id` | 14 суток | **[ПЛАН]** |
| событие во входящей очереди | 10 минут | **[ПЛАН]** |
| «визит закончен» после тишины | 60 минут | **[ПЛАН]** |

Сроки трёх последних выведены замером боевых баз, не назначены круглым числом
(спека веба §7.1): 442 сообщения, 157 переходов, 154 пары «вопрос → ответ».

Возраст самых старых данных сегодня — **38 суток** (`.secrets/demo.db`, с
17.07.2026). Годовой срок ни разу не наступал.

🔴 Срок в R2 (365) и срок для веба (365) — **разные правила, случайно равные
числом**: первое про ротацию зашифрованных копий, второе про показ переписки.
Изменение одного не тянет другое (спека веба §10.1).

## 5. Как удаляется по требованию

**[НЕТ] Пути удаления не существует.** Ни в коде, ни в панели.

Единственный `DELETE FROM messages` в дереве — `delete_command_messages`
(`chatter/storage/db.py:807`): разовая чистка команд пульта, залетевших в
историю лида, по флагу `cmd_history_purged` (`telethon_run.py:2484`). К удалению
по требованию отношения не имеет.

Чтобы удалить переписку одного человека сегодня, руками надо тронуть **четыре
места** из §2, и три из них — не база:

1. строки `messages`, `contact_profile`, `facts`, `contacts`,
   `funnel_transitions`, `contact_obligations`, `console_cards` по его
   `contact_id` — SQL вручную;
2. строки `IN <id>: ...` в `logs/chatter_<slug>.log` — текстовый файл;
3. зашифрованные копии в R2 — прочитать нельзя, вычистить точечно нельзя;
   уходят только заменой по ротации, максимум через 365 дней;
4. карточки в Telegram владельца — сообщения в чужом мессенджере, удаляются
   только вручную из чата.

Что означает «удалено» — при таком раскладе вопрос не риторический: после
пункта 1 переписка исчезает из сервиса, но продолжает существовать в пунктах
2–4.

## 6. Что проверено как НЕ происходящее

**[НЕТ]** отпечаток устройства и склейка по IP · рекламные и аналитические
cookie · геолокация · реквизиты карт · продажа или передача контактов третьим
сторонам · передача переписки кому-либо, кроме §3.

Отдельно: склейка веб-посетителя с известным лидом **[ПЛАН]** — только
предложением, подтверждает человек; автоматической склейки не будет (спека
веба §3.1).

## 7. Долг, который создаёт публикация

Сроки из §4 и удаление из §5 существуют только на бумаге спеки. Пока кода нет,
любое обещание про них — утверждение, проверяемое одним письмом.

Кандидат **DEV-69**: ротация переписки по сроку · путь удаления по требованию ·
ротация логов раннера (или отказ писать текст в лог) · сторож на то, что срок
читается из одного места и не выведен из `keep_days` бэкапа.

Порядок: закрыть **до запуска канала**, а не до публикации страницы.

(поставщик сервиса или клиент, чей бизнес) — в коде этого нет и быть не может.
