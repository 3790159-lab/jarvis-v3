## §0 Что решает спека

**Решает:** как код узнаёт отправителя из `contact_id`, чтобы завтрашняя смена
формата на `"<channel>:<external_id>:<persona>"` не сломала шесть мест МОЛЧА.

**НЕ решает:** саму смену формата. Она следующей аркой и требует миграции
данных. Здесь формат остаётся сегодняшним — меняется только то, КЕМ он
разбирается.

**Владельцу решать нечего:** поведение на сегодняшнем формате обязано остаться
байт-в-байт прежним, это и есть приёмка.

## §2 Решения

### §2.1 Один модуль `chatter/core/contact_ref.py`

Ядро (`chatter/core/*`) — потому что о транспорте эта функция ничего не знает,
и туда же смотрит правило «ноль импортов Telethon в ядре».

```python
def peer_of(contact_id: str) -> str:
    """ОТПРАВИТЕЛЬ из contact_id. Fail-closed: форму, которой не знаем,
    не угадываем."""

def telegram_peer_of(contact_id: str) -> int:
    """То же, но как telegram-peer. Не телеграмный контакт -> отказ."""

def slug_of(contact_id: str) -> str:
    """СЛУГ (хвост). Существует, чтобы `rsplit` не расползался по коду."""
```

### §2.2 Fail-closed, а не «вернём что-нибудь»

Неизвестная форма — **исключение с названным `contact_id`**, а не пустая
строка и не первый попавшийся кусок. Дефект, который здесь ловим, ровно в
том, что шесть мест возвращают правдоподобный мусор.

**Решил так, потому что** молчаливый неверный ответ здесь дороже падения:
падение видно в тот же день, а `"instagram"` вместо собеседника доедет до
клиента ([[jarvis-checks-that-answer-the-wrong-question]]).

### §2.3 Сегодняшний формат разбирается БАЙТ-В-БАЙТ как раньше

`"12345:volska"` → `peer_of` даёт `"12345"`, `telegram_peer_of` даёт `12345`,
`slug_of` даёт `"volska"`. Ни одного отличия от нынешнего поведения.

### §2.4 Восемь мест зовут функцию, а не режут строку

Каждое из восьми — вызов. Больше `contact_id.split(":"` в `chatter/` и `app/`
не остаётся вовсе; держится сторожем по AST.

### §2.5 РОВНО ДВА СЕГМЕНТА — единственная форма, которую знаем сегодня

**Замер 28.08 (`fa2554a8`): СЕМЬ мест сборки, все одной формы** — все в
`chatter/telethon_run.py`:

| строка | форма |
|---|---|
| `:1266` | `f"{peer_id}:{self.persona_for(peer_id)}"` |
| `:1269` | `f"{peer_id}:{slug}"` |
| `:1556` | `f"{entity.id}:{self.persona_for(entity.id)}"` |
| `:1689` | `f"{sender_id}:{persona_slug}"` |
| `:1702` | `contact_id = f"{sender_id}:{persona_slug}"` |
| `:1785` | `get_or_create_contact(f"{sender_id}:{persona_slug}")` |
| `:1855` | `f"{mm.sender_id}:{persona_slug}"` |

Слуги в реестре — `volska`, `demo`, `demo2`, `yarina`, двоеточий нет.

⚠️ **Первая редакция называла ТРИ места.** Занизил узкий grep — ровно та
грабля, о которой предупреждает сам замер мультиканальности («узкий шаблон
занижает МОЛЧА»), и я в неё наступил в спеке против неё же. Нашёл автор
сторожей. Вывод от этого не изменился, число — изменилось.

🔴 **`peer_id = event.chat_id` (`:1264`), а `chat_id` у групп ОТРИЦАТЕЛЕН.**
Значит `-1001234567890:demo` — законная живая форма. Проверка головы через
`isdigit()` убила бы все групповые диалоги, и убила бы молча: `peer_of` просто
начал бы отказывать там, где раньше работал. Канонический список форм в
сторожах эту форму держит.

Значит форма — **строго одно двоеточие**. Всё остальное функция отвергает,
включая трёхсегментную `"<channel>:<external>:<persona>"`.

**Опознаём по ЧИСЛУ СЕГМЕНТОВ, а не по голове.** Соблазнительная
альтернатива — «числовая голова значит telegram, нечисловая значит чужой
канал» — тихо примет `"12345:abc:volska"` ровно тогда, когда следующая арка
введёт трёхсегментный формат с числовым `external_id`. То есть она заведёт
молчаливое неверное поведение на том самом переходе, ради которого арка и
пишется.

**Решил так, потому что** цель — не угадать неизвестную форму, а громко на ней
отказать. Формат меняет следующая арка, она же снимет запрет и принесёт своих
сторожей.

### §2.6 Разбор ПРИНЯТОЙ формы обязан быть обратим

`peer_of(x) + ":" + slug_of(x) == x` для всякого `x`, который функция приняла.

Это ловит реализацию, которая приняла три сегмента и **молча потеряла
середину** — самый правдоподобный способ «почти» выполнить §2.5.

## §4 Риск

`telethon_run.py` и `run.py` — код ОБЕИХ живых клиенток. Правка механическая,
но радиус живой. Поэтому: поведение на сегодняшнем формате пинится сторожами
до правки, полная суита обязательна, дифф поимённо двухступенчато (DEV-78).

---

## §5 Сторожа — от спеки, до кода. Пишет ДРУГОЙ автор

1. `peer_of("12345:volska") == "12345"` — сегодняшняя форма не изменилась.
2. `telegram_peer_of("12345:volska") == 12345` (int, не строка).
3. `slug_of("12345:volska") == "volska"`.
4. **ИНВАРИАНТ ОБРАТИМОСТИ:** для принятой формы
   `peer_of(x) + ":" + slug_of(x) == x`. Встречная половина к нему —
   `"12345:my:slug"` ОТВЕРГНУТ, а не разобран как `12345` + `slug` с потерей
   середины.
   ⚠️ Первая редакция требовала обратного («слуг с двоеточием разбирается») —
   это описывало форму, которой не существует, и противоречило §2.5. Нашёл
   автор сторожей, исправлено замером трёх мест сборки.
5. Неизвестная форма (`"instagram:abc:volska"`) — **исключение**, а не мусор.
6. Пустая строка и строка без двоеточия — исключение.
7. `telegram_peer_of` на нечисловой голове — исключение, а не `ValueError`
   из недр `int()`: отказ обязан называть `contact_id`.
8. **По AST:** в `chatter/` и `app/` не осталось ни одного
   `contact_id.split(":"` — ни в одной из восьми точек.
9. **ВСТРЕЧНАЯ ПОЛОВИНА к 8:** `rsplit` на `telethon_run.py:1397` жив
   (или заменён на `slug_of`) — правка не причесала хвост заодно.
10. Каждое из восьми мест на сегодняшнем `contact_id` отдаёт то же, что
    отдавало до правки. Пин ПОИМЁННО, а не «мы всё заменили».
