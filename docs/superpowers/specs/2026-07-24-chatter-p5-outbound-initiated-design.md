# P5 — диалог, начатый владельцем вручную (funnel-edge)

**Дата:** 2026-07-24 · **Статус:** спека согласована, кода нет
**Проблема:** `docs/chatter/PROBLEMS.md` §P5 · **Аудит:** `docs/chatter/AUDIT.md` D5
**Блокирует:** открытие `funnel_gate` · **Живая проверка:** дрил Д-8

---

## 1. Корень (подтверждено кодом, не гипотеза)

`Runner.contact_id_for_chat` (`chatter/telethon_run.py:873`) считает диалог управляемым
только если строка в `contacts` уже существует **или** отправитель в allowlist:

```python
peer_id = event.chat_id
if peer_id in self.allowlist:
    return f"{peer_id}:{self.persona_for(peer_id)}"
for slug in self.personas:
    if store.has_contact(f"{peer_id}:{slug}"):
        return f"{peer_id}:{slug}"
return None
```

Владелец пишет первым незнакомцу → обе ветки мимо → `None` → `_outgoing_handler`
выходит на `telethon_run.py:1670` (`return  # диалог, который Аня не ведёт`).
Строка контакта не создаётся **никогда**, и факт «мы начали этот диалог» нигде
не сохраняется.

Когда лид отвечает, его сообщение попадает в `admission_decision`
(`chatter/core/admission.py`), которая про этот диалог ничего не знает:

| Состояние | Что происходит с ответом лида |
|---|---|
| `funnel_gate=False` (сегодня) | не в allowlist → `ignore`, ответ **молча выбрасывается** |
| `funnel_gate=True` + лид сохранён в контактах | `notify_owner`, ответ **блокируется** |
| `funnel_gate=True` + лид не сохранён | `answer` — случайно работает |

Третья строка и есть причина, по которой дефект до сих пор не жёг: он невидим
ровно в той конфигурации, в которой чаще всего пробуют. Обе первые — тихий
провал: никто не видит, что ответы теряются.

## 2. Ключ к решению: допуск и молчание — разные слои

Оба слоя в коде уже разделены, изобретать не нужно:

- **`admission_decision`** (`admission.py`) — «ведём ли мы этот диалог вообще»
- **`is_muted`** (`chatter/core/pause.py:9`) — «говорит ли бот прямо сейчас»

P5 чинится в первом слое. Требование владельца «бот подхватывает только по
явному тапу» реализуется вторым. Их независимость даёт главную гарантию
безопасности этой арки:

> **Ни одна ошибка эвристики §6 не может заставить бота заговорить.**
> Эвристика влияет только на слой допуска; слой паузы держит бота молчащим
> до явного действия владельца.

## 3. Схема данных

Таблица `contacts` (`chatter/storage/db.py:9`) получает две колонки через
существующий путь миграции (`db.py:128–145`, `PRAGMA table_info` + `ALTER TABLE`):

```sql
outbound_initiated INTEGER NOT NULL DEFAULT 0   -- мы написали первыми
not_a_lead         INTEGER NOT NULL DEFAULT 0   -- владелец сказал «это не лид»
```

Обе булевы, никаких магических значений. Миграция аддитивная — старые БД
поднимаются без ручных шагов.

Производная величина, которую считает вызывающая сторона (не хранится):

```python
managed_outbound = bool(row["outbound_initiated"]) and not bool(row["not_a_lead"])
```

`not_a_lead=1` **не удаляет строку** — история переписки остаётся, диалог просто
перестаёт быть управляемым. Удаление было бы необратимой потерей данных ради
косметики `/status`.

## 4. `admission_decision` — новый параметр

Сигнатура получает `outbound_initiated: bool` (это `managed_outbound` из §3).
Функция остаётся **чистой**: булево считает вызывающий, стор внутрь не заезжает.

Приоритет:

```
denylist > allowlist > outbound_initiated > is_contact > stranger
```

```python
def admission_decision(*, sender_id, is_contact, outbound_initiated,
                       allowlist, denylist, funnel_gate) -> str:
    if not funnel_gate:
        if sender_id in allowlist or outbound_initiated:
            return "answer"
        return "ignore"
    if sender_id in denylist:
        return "block_denylist"
    if sender_id in allowlist:
        return "answer"
    if outbound_initiated:
        return "answer"
    if is_contact:
        return "notify_owner"
    return "answer"
```

⚠️ **Ветка закрытого гейта правится обязательно.** Сегодня там
`answer if sender_id in allowlist else ignore`. Без правки P5 не чинится в той
конфигурации, в которой система живёт прямо сейчас (`funnel_gate=false` у
volska, проверено фактом в `chatter/clients/volska/settings.yaml:65`).

`denylist` остаётся сильнее всего: явный блок владельца перебивает и факт, что
мы когда-то написали первыми.

## 5. Автоматическая привязка (эвристика)

### 5.0 Порядок операций в `_outgoing_handler` — сначала команда, потом эвристика

⚠️ **Требует перестановки существующего кода, иначе арка ломает пульт.**

Сегодня хендлер выходит на `telethon_run.py:1670` (`contact_id is None`)
**раньше**, чем парсит команду на `:1676`. Это корректно, пока неуправляемых
диалогов не существует как категории, но с приходом `/lead` (§6) ломается
дважды:

1. `/lead`, набранный в диалоге незнакомца, не был бы перехвачен и **ушёл бы
   лиду обычным текстом** — владелец отправил бы холодному лиду «/lead».
2. Эвристика §5, сработав раньше парсера, создала бы контакт по самому факту
   отправки команды — то есть команда «веди этот диалог» и её собственный
   побочный эффект перепутались бы местами.

Целевой порядок в `_outgoing_handler`:

```
1. me_id известен?            → нет: выход (как сейчас)
2. Saved Messages?            → да:  выход (как сейчас)
3. parse_command + не наше?   → да:  исполнить команду, выход   ← поднято выше
4. contact_id_for_chat()      → есть: обычный путь takeover
5. эвристика §5               → создать контакт + пауза + карточка
6. иначе                      → выход (жизнь аккаунта, не наше дело)
```

Шаг 3 поднимается над шагом 4. Команда в неуправляемом диалоге должна
исполняться — именно там она и нужна: пока диалог не управляемый, адресовать
его из пульта нечем.

`handle_inline_command` сегодня принимает `contact_id` обязательным аргументом;
для `/lead` в неуправляемом диалоге он ещё не существует. Сигнатура получает
`contact_id: str | None`, и команды, требующие существующего диалога
(`/pause`, `/resume`), при `None` отвечают владельцу внятным «этот диалог ещё
не веду, `/lead` подключит» вместо тихого отказа (DEV-18).

### 5.1 Условия срабатывания эвристики

Условия узкие —
цель не в том, чтобы поймать всё, а в том, чтобы не утопить `/status` личной
перепиской владельца:

| Условие | Зачем |
|---|---|
| приватный DM, получатель — человек, не бот | группы/каналы/боты лидами не бывают |
| `event.chat_id != runner.me_id` | Saved Messages — это пульт (`telethon_run.py:1666`) |
| `contact_id_for_chat() is None` | диалог ещё не управляемый |
| получатель **не** в контактах Telegram (`User.contact`) | личные чаты владельца отсекаются здесь |
| не наше исходящее (`sent_registry.is_ours`) | это владелец, а не бот |

Что записывается при срабатывании:

```
outbound_initiated = 1
paused             = 1
pause_source       = 'outbound_initiated'
pause_until        = NULL
```

**Отдельный `pause_source` — не косметика.** `should_auto_resume`
(`pause.py:47`) для любого источника кроме `human_takeover` возвращает `False`.
То есть бот **никогда не разморозится сам** в диалоге, который владелец ведёт
руками. Если бы мы переиспользовали `human_takeover`, диалог разморозился бы
через `auto_resume_hours` молчания владельца — и бот заговорил бы с холодным
лидом без спроса. Для арки это был бы прямой провал требования.

## 6. Две ошибки эвристики и как владелец их правит

Эвристика §5 опирается на `User.contact`, а этот признак не совпадает с
«лид/не лид». Обе ошибки известны заранее, обе неслышны сами по себе и обе
чинятся одним действием.

### Ошибка A — настоящий лид пропущен

**Когда.** Владелец сохранил номер лида в контакты (познакомились офлайн,
обменялись визитками, лид пришёл по рекомендации) и пишет ему в Telegram.
`User.contact = True` → эвристика §5 не срабатывает → строка не создаётся.
Дальше ответ лида: при закрытом гейте `ignore`, при открытом `notify_owner`.
То есть **ровно исходный дефект P5, только для другой категории лидов.**

Это не редкий угол: для риелтора, фрилансера или дизайнера офлайн-знакомство —
основной канал. Эвристика тут промахивается систематически, а не случайно.

**Как правит владелец — два пути, оба ведут в одну точку:**

1. **Команда `/lead` прямо в диалоге лида.** Механизм уже есть: владелец,
   набравший команду в чате лида, перехватывается в `_outgoing_handler`
   (`telethon_run.py:1676`, `parse_command` + `handle_inline_command`, Fix 3
   арки 3B) — команда исполняется, в историю не пишется, сообщение удаляется,
   в пульт летит подтверждение. `lead` добавляется в `TARGETED_COMMANDS`
   (`console.py:11`) рядом с `pause`/`resume`: без аргумента — текущий диалог,
   с аргументом (`/lead <id>`) — из пульта.

2. **Кнопка на уведомлении о знакомом контакте.** При открытом гейте знакомый,
   который написал, уже порождает уведомление владельцу
   (`_notify_known_contact`, `telethon_run.py:1022`). Оно сегодня без кнопок —
   добавляется `[▶️ Вести цей діалог]`, тап делает то же, что `/lead`.

Оба пути создают строку с `outbound_initiated=1`. Пауза при ручной привязке
**не ставится**: владелец явным действием сказал «веди», ждать второго
подтверждения незачем.

> Это закрывает и давний бэклог-хвост арки 3C — «`/allow`-команда + tap-convert»
> (`AUDIT.md`, бэклог 5-го клиента). Отдельной арки на него больше не нужно.

### Ошибка B — личный чат подхвачен

**Когда.** Владелец пишет незнакомцу не по делу: курьер, объявление на OLX,
чат с мастером, незнакомый коллега. `User.contact = False` → эвристика §5
срабатывает → создаётся управляемый контакт и в пульт летит карточка.

**Цена ошибки низкая по конструкции:** контакт создан **на паузе**, бот молчит,
лид (то есть курьер) ничего не замечает. Стоимость — одна лишняя карточка в
пульте и одна строка в `/status`.

**Как правит владелец.** Кнопка `[🚫 Це не лід]` на той же карточке →
`not_a_lead=1`. Диалог перестаёт быть управляемым (`managed_outbound` = False),
из `/status` уходит, карточка по нему больше не шлётся никогда. История
переписки сохраняется. Обратный ход — `/lead` в том же диалоге.

### Сводка

| | Ошибка A (лид пропущен) | Ошибка B (личный чат подхвачен) |
|---|---|---|
| Причина | лид сохранён в контактах | незнакомец, но не лид |
| Симптом | ответы лида теряются | лишняя карточка + строка в `/status` |
| Заметность | 🔴 тихая — нужен явный сигнал (см. ниже) | 🟢 громкая, владелец видит карточку |
| Правка | `/lead` в диалоге · кнопка на уведомлении | `[🚫 Це не лід]` |
| Может ли бот заговорить ошибочно | нет | нет (пауза) |

**Ошибка A тихая — и это единственное место арки, требующее отдельной заботы.**
Поэтому при закрытом гейте входящее от неизвестного отправителя, которому мы
недавно писали (есть исходящие в этом диалоге), логируется как
`admission: ignore, но мы писали в этот диалог — возможно, пропущенный лид`.
Дешёвая строка в логе, которая превращает молчаливую потерю в диагностируемую.
Полноценный сигнал в пульт для закрытого гейта — сознательно **нет**: при
закрытом гейте аккаунт не выделен под воронку, и уведомление на каждое
входящее от знакомого превратило бы пульт в шум.

## 7. Карточка

Шлётся один раз на диалог — дедуп по факту создания строки контакта (повторное
исходящее в тот же чат карточку не порождает).

```
🆕 Ви почали діалог з Іван (@ivan)
   [▶️ Підключити Ольгу]   [✅ Веду сам]   [🚫 Це не лід]
```

| Кнопка | Действие |
|---|---|
| ▶️ Підключити | снять паузу → следующее сообщение лида идёт обычным путём |
| ✅ Веду сам | оставить паузу; вернуться можно из `/status` в любой момент |
| 🚫 Це не лід | `not_a_lead=1` (ошибка B) |

Механика тапов переиспользует существующий `route_callback` и карточки паузы
арки 3B — новых транспортных путей не появляется. Локализация ru/en/uk через
`console_text`, как остальные строки пульта.

## 8. Catch-up

`select_missed` (`telethon_run.py:248`) зовёт тот же гейт, поэтому в словарь
диалога добавляется `outbound_initiated`. Без этого после каждого рестарта
раннера outbound-лиды снова начали бы теряться — то есть дефект вернулся бы в
единственной форме, которую тесты живого пути не ловят.

## 9. Что НЕ делаем

- Не трогаем `funnel_gate` и его дефолт (`false`) — арка расширяет допуск, а не открывает его.
- Не удаляем строки контактов ни при каком исходе.
- Не шлём уведомления в пульт на каждый пропущенный ignore при закрытом гейте (§6, шум).
- Не вводим авто-резюм для `pause_source='outbound_initiated'`.

## 10. Тесты

**Чистые функции**
- Таблица истинности `admission_decision` с новым параметром: обе ветки гейта × allow/deny/contact/outbound × `not_a_lead`.
- Регресс закрытого гейта: `outbound_initiated=True, funnel_gate=False` → `answer` (без этого арка не работает сегодня).
- `denylist` перебивает `outbound_initiated`.

**Хранилище**
- Миграция на БД без новых колонок: открывается, дефолты `0`, данные целы.
- `managed_outbound` при `not_a_lead=1` → False.

**Хендлер (эвристика §5)**
- Исходящее незнакомцу → контакт создан, `paused=1`, `pause_source='outbound_initiated'`, карточка отправлена **ровно один раз** (второе исходящее в тот же чат — без второй карточки).
- Негативные: исходящее сохранённому контакту / в Saved Messages / в группу / боту / наше собственное (`sent_registry`) → контакт **не** создаётся.

**Порядок операций (§5.0) — регресс, который иначе всплывёт живьём**
- `/lead` в неуправляемом диалоге перехвачен: лиду **не отправлен**, контакт создан командой, а не эвристикой.
- `/pause` в неуправляемом диалоге → внятный ответ владельцу, не тишина и не падение.
- Обычный (не командный) текст незнакомцу по-прежнему уходит адресату и запускает эвристику.

**Ручная привязка (§6)**
- `/lead` в диалоге → контакт создан, `outbound_initiated=1`, паузы **нет**, в историю команда не попала, сообщение удалено.
- `/lead <id>` из пульта → то же для указанного диалога.
- Кнопка на уведомлении о знакомом контакте → то же.
- `[🚫 Це не лід]` → `not_a_lead=1`, допуск закрыт, повторная карточка не шлётся.
- `/lead` после `not_a_lead=1` → снова управляемый (обратимость).

**Пауза**
- `should_auto_resume` для `pause_source='outbound_initiated'` → `False` при любом возрасте паузы.

**Catch-up**
- Пропущенное сообщение от outbound-лида после рестарта → попадает в `select_missed`.

**Живая проверка:** дрил Д-8 (сценарий пишется отдельным файлом
`docs/chatter/DRILL_D8_OUTBOUND_LEAD.md` при реализации, по образцу Д-7:
baseline-счётчик → сценарий → проверка фактом по БД → негативная проверка).

## 11. Порядок реализации

1. Схема + миграция (тесты хранилища).
2. `admission_decision` + параметр (тесты чистой функции) — красные до §3.

   до любой новой логики: это правка существующего поведения, и она должна

   inline-команды) прежде, чем сверху ляжет что-то новое.
4. Эвристика в `_outgoing_handler` + карточка.
5. Ручная привязка: `/lead`, `[🚫 Це не лід]`, кнопка на уведомлении.
6. Catch-up.
7. Дрил Д-8, потом решение об открытии гейта — **отдельной командой владельца.**
