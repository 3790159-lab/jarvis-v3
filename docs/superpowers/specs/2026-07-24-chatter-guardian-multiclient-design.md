# Генерализация гардиана на N аккаунтов (первый кирпич control-plane)

**Дата:** 2026-07-24 · **Статус:** спека согласована, кода нет
**Контекст:** `docs/chatter/ONBOARDING_MANUAL.md` §4 «Текущее ограничение», Путь B
**Блокирует:** второго одновременного клиента · **Не блокирует:** открытие гейта

## 1. Что мешает сегодня (два дефекта, не один)

### 1.1 Хардкод volska

`scripts/chatter_guardian_detached.ps1`, блок `SEMIDEMO OVERRIDE` (~строка 60):

```powershell
$semidemoFlag = Join-Path $stateDir 'chatter_semidemo_volska.flag'
if (Test-Path $semidemoFlag) {
    $env:CHATTER_PERSONAS = 'volska'
    $env:TELETHON_SESSION = '.secrets\demo.session'
    $env:CHATTER_DB       = '.secrets\demo.db'
    ...
}
```

Один флаг, одно имя клиента, зашитое в скрипт. Второй клиент требует правки
скрипта — то есть деплоя вместо онбординга.

### 1.2 Взаимное убийство раннеров (тише, но опаснее)

```powershell
function Get-RunnerProcesses {
    Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
        Where-Object { $_.CommandLine -like "*$Root*chatter.telethon_run*" }
}
```

Матч по модулю, без различения клиента. `Stop-OldRunner` бьёт **всех**
найденных. Значит даже если убрать хардкод §1.1, запуск второго клиента убил бы
первого — гардиан устроен так, что двух раннеров быть не может **по
конструкции**, а не по конфигу.

Оба дефекта надо снимать вместе; починка только флага дала бы систему, которая
выглядит рабочей и молча убивает живого клиента при старте второго.

## 2. Топология: один супервизор, реестр как источник правды

Одна задача `JarvisChatterGuardian` держит N дочерних раннеров. Разрез —
желаемое состояние против наблюдаемого:

```
chatter/clients/registry.yaml     ← desired state  (кто ДОЛЖЕН жить)
        │
        ▼  супервизор конвергирует, ~30с цикл
state/chatter_clients.json        ← observed state (кто живёт НА САМОМ ДЕЛЕ)
```

Это и есть кирпич control-plane: **дашборд позже пишет верх и читает низ**, а
супервизор не переделывается, потому что он уже сейчас не знает и не должен
знать, кто правит реестр — человек, PowerShell-скрипт или HTTP-ручка. Никакой
второй ручки управления не появляется: `chatter_client.ps1` (§6) правит то же
поле, которое потом будет править дашборд.

Альтернатива «N Windows-тасков по одному на клиента» отклонена: состояние
размазывается по N задачам, и дашборду понадобился бы собственный слой сбора —
то есть ровно та переделка, которую эта арка должна предотвратить.

## 3. `registry.yaml` — желаемое состояние

```yaml
# Реестр клиентов chatter. Один клиент = один процесс раннера со своими
# сессией, БД, логом и heartbeat. Подключить клиента = добавить запись сюда.
# Правка PowerShell-скрипта гардиана НЕ требуется (см. §3.1).
clients:
  volska:
    enabled: true
    personas: [volska]
    session: .secrets/demo.session   # пин: volska живёт на сессии demo-аккаунта
    db:      .secrets/demo.db
  demo:
    enabled: false
    personas: [demo, demo2]
    session: .secrets/demo.session
    db:      .secrets/demo.db
```

Одна запись = один процесс. Внутри записи может быть несколько персон
(`personas: [demo, demo2]`) — это сегодняшнее поведение одного раннера с
несколькими персонами, оно сохраняется без изменений.

### 3.1 Сохраняемое свойство

Сегодня гардиан **намеренно** не передаёт `--personas` — состав клиентов лежит
в `active.yaml`, чтобы подключение клиента не было правкой скрипта (онбординг-
дырка №3, зафиксирована комментарием в `Start-Runner`). Реестр это свойство
сохраняет: новый клиент = запись в `registry.yaml`, скрипт не трогаем.

Разница только в том, что раннер больше не читает состав сам — состав ему
передаёт супервизор, потому что теперь процессов несколько и каждому нужен
свой. `active.yaml` остаётся для ручных запусков (`python -m
chatter.telethon_run` без гардиана) и помечается в комментарии как
«не используется гардианом».

## 4. Валидация реестра (обязательная, до любого запуска)

**Два включённых клиента не могут делить `session` или `db`.**

Это не теоретическая осторожность: в реестре §3 `volska` и `demo` **уже** имеют
одинаковые пины (`demo.session` / `demo.db`) — так volska живёт сегодня.
Одновременный `enabled: true` у обоих дал бы два процесса на одной Telethon-
сессии. Последствия — конфликт апдейтов, гонка за запись `.session` и, в худшем
случае, разлогин аккаунта (Telegram видит параллельные подключения одной
сессии). Один этот пункт — причина, по которой валидация обязана быть частью
арки, а не «улучшением потом».

### Правила

1. Проверка идёт **до** старта чего бы то ни было, на множестве `enabled: true`.
2. Пути нормализуются перед сравнением: относительный ↔ абсолютный, `/` ↔ `\`,
   регистр (Windows) — иначе `.secrets/demo.session`, `.secrets\demo.session` и
   `C:\jarvis\.secrets\demo.session` проскочат как «разные».
3. При конфликте **не стартуют оба** участника пары. Запустить одного «на
   выбор» — недетерминированное поведение, зависящее от порядка ключей в YAML;
   владелец не должен угадывать, кто из двух поднялся.
4. Каждому участнику конфликта пишется явный `last_error`:

   ```
   registry conflict: session '.secrets/demo.session' shared with enabled client 'demo'
   ```

5. Алерт владельцу — один раз на конфликт (§7), с именами обоих клиентов.
6. Остальные, неконфликтующие клиенты поднимаются нормально. Ошибка конфигурации
   одной пары не должна ронять весь парк.
7. **Невалидный клиент не запускается, но уже запущенный НЕ убивается.** Правило
   3 запрещает *старт*, а не жизнь. Иначе опечатка в реестре (включили второго
   клиента на чужую сессию) убивала бы живого первого — то есть валидация,
   написанная ради защиты продакшена, сама становилась бы способом его уронить.
   Безопасный исход конфликта: живой продолжает жить, новый не поднимается,
   владелец получает алерт с именами обоих.

**Явная ошибка, а не тихий цикл рестартов.** Отдельно оговорено, потому что
дефолтное поведение супервизора при незапускающемся клиенте — ретрай, и
конфликт конфигурации в таком цикле выглядел бы как «что-то мигает», а
диагностировался бы часами.

Тем же механизмом проверяется: `enabled: true` без существующего session-файла
(→ `last_error: session file not found`, иначе Telethon уйдёт в интерактивный
запрос кода и повиснет), неизвестный slug (нет каталога `chatter/clients/<slug>`),
пустой `personas`.

## 5. Изоляция процессов

Каждый клиент получает собственные рантайм-файлы:

| Что | Путь |
|---|---|
| Лог (stderr, основной) | `logs/chatter_<slug>.log` |
| Лог (stdout, стартовый принт) | `logs/chatter_<slug>.stdout.log` |
| Heartbeat | `state/chatter_heartbeat_<slug>.txt` |
| PID-лок раннера | `state/locks/chatter_runner_<slug>.pid` |
| Маркер алерта | `state/chatter_watch_alert_<slug>.json` |

Разделение stdout/stderr сохраняется: `Start-Process` требует **разных** файлов,
указание одного роняет запуск молча (грабля холодного старта, зафиксирована
комментарием в текущем скрипте).

### Две правки вне PowerShell

1. **`--client <slug>`** в `chatter/telethon_run.py` (argparse, `:1794`).
   Дефолт — первичный slug. Значение попадает в командную строку процесса, и
   это делает `Get-RunnerProcesses -Slug <slug>` точечным:

   ```powershell
   $_.CommandLine -like "*$Root*chatter.telethon_run*--client $Slug*"
   ```

   Ровно этим снимается дефект §1.2. Матч по `--personas` был бы хрупок: у
   записи может быть несколько персон, и подстрока одного slug совпала бы с
   чужой командной строкой.

2. **Путь heartbeat перестаёт быть константой** (`HEARTBEAT_PATH` в
   `telethon_run.py`) и выводится из `--client`. Иначе N раннеров пишут в один
   файл и супервизор считает живым любого, пока жив хоть один.

Обе правки маленькие и аддитивные; ручной запуск без `--client` сохраняет
сегодняшнее поведение.

## 6. `chatter_clients.json` — наблюдаемое состояние

Пишется супервизором каждый цикл, атомарно (tmp + rename — иначе читатель
поймает половину файла):

```json
{
  "updated_ts": 1784842504,
  "clients": {
    "volska": {
      "desired": "enabled",
      "state": "alive",
      "pid": 11484,
      "heartbeat_ts": 1784842501,
      "last_transition_ts": 1784841571,
      "consecutive_fail": 0,
      "last_error": null
    },
    "demo": { "desired": "disabled", "state": "stopped", "pid": null,
              "heartbeat_ts": null, "last_transition_ts": 1784800000,
              "consecutive_fail": 0, "last_error": null }
  }
}
```

`state` ∈ `alive` · `starting` · `down` · `stopped` · `invalid`.
`stopped` — выключен намеренно (`enabled: false`); `down` — должен жить, но не
живёт; `invalid` — не прошёл валидацию §4. Различать обязательно: «выключен» и
«упал» требуют противоположной реакции, а слипшись в одно состояние они дают
либо ложные алерты, либо пропущенные аварии.

## 7. Алерты называют клиента

`scripts/chatter_watch_check.py` получает `--client <slug>`, свой маркер-файл
(§5) и текст с именем клиента:

```
🔴 chatter/volska: раннер лёг (heartbeat 4м назад)
✅ chatter/volska: раннер поднялся
```

Свойство **stdlib-only** сохраняется — оно и есть причина, по которой алертер
переживает поломку пакета `chatter` или его зависимостей. Дедуп и cooldown
становятся per-client: авария одного клиента не должна глушить алерт о другом.

Отдельный класс — конфликт реестра (§4): алерт называет **обоих** участников,
иначе владелец пойдёт чинить не тот клиент.

## 8. Старт/стоп по отдельности

```powershell
scripts\chatter_client.ps1 -Slug volska -Action start|stop|status|list
```

`start`/`stop` правят `enabled` в реестре; супервизор сходится за один интервал
(~30с). `status`/`list` читают `chatter_clients.json`. Скрипт **не** запускает и
не убивает процессы напрямую — иначе появилась бы вторая, конкурирующая с
супервизором ручка управления, и наблюдаемое состояние разошлось бы с желаемым.

## 9. Миграция volska (в этой же арке, по решению владельца)

Реестр становится единственным механизмом; `chatter_semidemo_volska.flag` и
блок `SEMIDEMO OVERRIDE` удаляются.

**Пины выписываются в реестр дословно** — `session: .secrets/demo.session`,
`db: .secrets/demo.db`. Если их потерять, `derive_session_path` выведет
несуществующий `.secrets/volska.session` и Telethon уйдёт в интерактивный запрос
кода на живом клиенте.

### Порядок

1. **После утренних дрилов** (память + Д-7). До них раннер и профиль не трогаем.
2. Репетиция на выключенном клиенте: `demo` → `enabled: true` → проверить, что
   валидация §4 **отклонила** его из-за конфликта сессии с volska (это и есть
   живой тест правила) → вернуть `false`.
3. Переключение volska на реестр, рестарт задачи гардиана.
4. Проверка фактом, как на прошлых холодных стартах: один процесс на клиента,
   `honesty=honest`, `funnel_gate=false`, catch-up, ноль ошибок в логе через
   `Get-Content` (не `dir` — `docs/postmortems`, NTFS врёт про размер живого лога).
5. Профиль контакта `237616472:volska` v5 на месте после рестарта.

### Откат

`git revert` арочного коммита + восстановление флага. Точные пины продублированы
в этой спеке (§9) намеренно: откат не должен зависеть от того, найдёт ли кто-то
нужный коммит в истории под давлением.

⚠️ Гардиан деплоит из рабочего дерева — переключение ветки само по себе является
деплоем (~90с). Учитывать при откате.

## 10. Что НЕ делаем

- Не начинаем дашборд. Арка готовит шов, не UI.
- Не трогаем логику самого раннера, кроме `--client` и пути heartbeat (§5).
- Не вводим управление процессами в обход реестра (§8).
- Не переносим второго клиента автоматически — он поднимается вручную по
  `ONBOARDING_MANUAL`, как и решено.

## 11. Тесты

Паттерн уже отработан: `tests/test_bot_guardian_stop_old_bot.py` гоняет
настоящий `.ps1` из pytest через dot-source с `-Root <tmp> -NoLoop`, без Pester
и без касания `C:\jarvis`. У chatter-гардиана хук `-NoLoop` уже есть
(`param(... [switch]$NoLoop)`).

**Валидация реестра (§4) — главный блок**
- Два `enabled` с одинаковым `session` → оба `invalid`, у обоих `last_error` называет второго, ни один не запущен.
- То же для одинакового `db`.
- Конфликт с **выключенным** клиентом конфликтом НЕ считается (сегодняшняя пара volska/demo обязана быть валидной).
- Нормализация путей: `.secrets/demo.session` vs `.secrets\demo.session` vs абсолютный — распознаются как один и тот же файл.
- Неконфликтующий третий клиент поднимается, несмотря на конфликт первых двух.
- `enabled: true` без session-файла → `invalid` + внятный `last_error`, **без** цикла рестартов.

**Изоляция процессов (§1.2 — регресс)**
- Два живых фейковых раннера с разными `--client`; `Stop-OldRunner -Slug a` убивает только `a`, `b` жив. Это тест того самого дефекта, ради которого арка и делается.
- `Get-RunnerProcesses -Slug` не матчит чужого клиента и не матчит процессы вне `$Root`.

**Конвергенция**
- `enabled: false` у живого клиента → остановлен, `state: stopped`.
- `enabled: true` у остановленного → запущен, `state` проходит `starting` → `alive`.
- Мёртвый раннер при `enabled: true` → перезапуск после дебаунса (сохранение сегодняшнего поведения).

**Наблюдаемое состояние**
- `chatter_clients.json` — валидный JSON, все ключи присутствуют, запись атомарна (читатель во время записи не видит обрывка).
- `stopped` и `down` не путаются.

**Алерты**
- Текст алерта содержит slug; маркеры per-client; авария одного клиента не глушит алерт о другом.
- Конфликт реестра называет обоих участников.

**Раннер**
- `--client` попадает в командную строку; heartbeat пишется в per-slug файл; без `--client` поведение прежнее.

## 12. Порядок реализации

1. Парсер + валидация реестра (§3, §4) — чистая логика, тестируется первой.
2. `--client` и per-slug heartbeat в раннере (§5).
3. Супервизор: per-slug `Get-RunnerProcesses` / `Stop-OldRunner` / `Start-Runner`, цикл конвергенции.
4. `chatter_clients.json` (§6).
5. Алерты per-client (§7).
6. `chatter_client.ps1` (§8).
7. Миграция volska (§9) — **последней, после утренних дрилов**, с проверкой фактом.
