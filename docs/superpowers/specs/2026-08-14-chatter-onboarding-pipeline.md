Дата: 2026-08-14. Статус: **ЧЕРНОВИК, ждёт ОК владельца. Кода нет, ветки нет.**
Эталон и единственная честная приёмка: бриф Ярины → сверка с `chatter/clients/yarina`,
собранным руками 13–14.08.

---

## 0. Зачем и где граница

Онбординг — повторяющаяся операция (детейлинг, стоматология, дальше больше).
Первый раз пройден целиком руками, правила формата известны. ~80% работы
механические, и они сегодня живут в памяти разработчика — то есть не живут.

**Цель:** `python -m chatter.onboard <slug> --brief <файл>` даёт каталог клиента
из пяти файлов + отчёт, после которого остаётся вычитка смысла и решения владельца.

**Не цель:** заменить вычитку, деплой (`active.yaml`, логин сессии, `/funnel_gate on`),
живой платный дрил и разрешение конфликтов брифа с нашими дефолтами. Явный список — §5.

**Главный инвариант:** каждое правило формата, выученное вчера, становится КОДОМ
и СТОРОЖЕМ, а не абзацем в памяти. Правило без сторожа в §4 в спеку не принимается.

### Состав модуля

```
chatter/onboard/
  __main__.py        CLI
  form_schema.yaml   карта формы: id ↔ колонка ↔ отпечаток вопроса (версионируется)
  brief.py           xlsx → brief.json: нормализация + мусор-детектор
  render.py          brief.json → 5 файлов; правила формата = код
  report.py          → REPORT.md (человеку) + report.json (проверкам)
  checks.py          автоприёмка
```

CLI:

```
python -m chatter.onboard <slug> --brief <файл.xlsx> [--out build/onboard/<slug>]
python -m chatter.onboard <slug> --check                 # только автоприёмка
python -m chatter.onboard <slug> --diff chatter/clients/yarina   # приёмка арки, §6
```

Коды выхода везде одинаковые: `0` зелёное, `1` красное, `2` не состоялось
(битый бриф, схема не совпала — прогон не доказал ничего).

**Результат кладём в `build/onboard/<slug>/`, НЕ в `chatter/clients/`.** Боевой
каталог — деньги клиента; перенос делает человек после вычитки. `build/onboard/`
уходит в `.gitignore`: бриф содержит имя, контакты и внутренние цены клиента,
а `.gitignore` сейчас `build/` не закрывает (проверено).

## 1. ВХОД: xlsx → нормализованный JSON

Реальный бриф (`.secrets/briefs/brief.xlsx`): один лист, **57 колонок, строка 0 —
текст вопроса, строка 1 — ответы**. Одна строка = одна заявка.

### 1.1. Привязка не к тексту вопроса

Два ключа, и они проверяют друг друга:

- **Ведёт позиция колонки.** Формулировки правят чаще, чем переставляют вопросы.
- **Сторожит отпечаток вопроса.** Нормализация: casefold, NBSP→пробел, снять
  пунктуацию, привести все апострофы к одному (в брифе уже живут `U+02BC` в
  «імʼя» и `U+2019` — сравнение по сырому тексту хрупко именно здесь), выкинуть
  стоп-слова. Сравнение — доля общих токенов (Jaccard) с порогом **0.6**.

`form_schema.yaml`: `{id: q22_price_list, col: 22, fingerprint: [...], type: block, required: true, target: knowledge}`.
Стабильные id (`q22_price_list`, `q50_forbidden_phrases`) — код и отчёт говорят
про id, текст вопроса не цитируется нигде, кроме отчёта.

### 1.3. Маршрут поля объявляется в схеме, а не выводится из текста

У каждого поля в `form_schema.yaml` есть `target`: `knowledge | playbook |
settings | examples | report_only`. Это **правило по ИСТОЧНИКУ**: распознавать
«внутреннее» по содержанию мы не пытаемся и не будем.

Ключевой класс — ICP: `q37_icp` (идеальный клиент), `q38_anti_icp` (кому
отказываем), сегментация и целевая аудитория едут **только в playbook** и
никогда в knowledge. Причина в рантайме: knowledge — то, из чего бот говорит
лиду, playbook — то, как он себя ведёт. Строка «наш ідеальний клієнт — той, хто
готовий інвестувати» в knowledge однажды будет зачитана лиду; в playbook она
живёт как внутренняя разметка («вголос не цитувати»). Сторож — C9.

Расхождение позиции и отпечатка = **rc 2 и карта**, а не догадка:

```
[onboard] схема form_schema.yaml v1 не совпала с брифом:
  колонка 22: ожидали ~«Для КОЖНОЇ послуги: ціна або вилка», нашли «Ціни по послугах» (совпадение 0.41)
  колонка 57: в брифе есть, в схеме нет
  → сверь и обнови form_schema.yaml (версия схемы += 1) либо укажи --remap 22=q22_price_list
```

Молча угадать = собрать клиенту прайс из чужой колонки. Ошибка обязана быть
громкой (DEV-18).

### 1.2. Мусор-детектор

Все классы взяты из РЕАЛЬНОГО брифа Ярины, ни одного выдуманного:

| Класс | Что видели | Правило |
|---|---|---|
| Тестовое заполнение | Q5 «тест 01 Артем», Q8 «тест» | стоп-словарь `тест/test/asdf/---` |
| Числовая заглушка в текстовом поле | Q10 «1 1 1», Q52/Q54/Q55 «1.0» | доля цифр и пробелов > 0.8, длина ≤ 8 |
| Огрызок | Q36 «мне)» | длина < 12 и ни одного токена из отпечатка вопроса |
| Ответ-ссылка на другое поле | Q23, Q25 «заполнил разом» | словарь «см. выше / разом / там же» |
| Плейсхолдер-URL | Q4 `drivepro-detailing.example` | домены `example.*`, `test.*`, `localhost` |
| Наше имя в поле клиента | Q14 «Джарвис» | словарь имён продукта/персон других клиентов |

Каждое поле получает `verdict: ok | suspect | garbage` + `reason`. Ключевое:
**детектор ничего не удаляет — он понижает поле до «ответа нет»**, сырое значение
всегда лежит в `brief.json` и цитируется в отчёте. `garbage`/`suspect` в конфиг
не попадают ни при каких условиях, они попадают в раздел 3 отчёта.

Выход шага: `build/onboard/<slug>/brief.json` —
`{field_id: {col, question, raw, value, verdict, reason}}` + `schema_version`.
Это артефакт для человека и вход для генератора; генератор читает ТОЛЬКО его.

## 2. ГЕНЕРАЦИЯ пяти файлов: каждое правило — код

Ниже каждое правило дано вместе с ПРИЧИНОЙ в коде — иначе через месяц его
«упростят». Сторож каждого — в §4.

### R1. Одна строка на услугу: «цена + грн + срок», без точек внутри

`guardrails._context_numbers` режет knowledge по `[\n.!?;]`, и число попадает в
обеспеченное множество только из фрагмента, где есть валюта или ценовое слово.
Точка внутри строки рвёт фрагмент — цена теряет валюту и **guardrail режет
собственный прайс клиента**.

Генератор собирает строку `- Ціна {lo}–{hi} {currency}, тривалість {срок}` и
прогоняет через санитайзер:

- внутри строки запрещены `. ! ? ;` (сокращения разворачиваются словами);
- десятичный разделитель — **запятая**, один и тот же на весь файл: `_numbers`
  снимает только пробелы, поэтому «1,5» и «1.5» — РАЗНЫЕ токены, и ответ с
  «1.5 години» окажется необеспеченным;
- разделитель тысяч — обычный пробел; NBSP и апостроф нормализуются (из Google
  Forms NBSP приезжает регулярно и даёт другой токен);
- тире диапазона — `–` (U+2013), как в эталоне.

Замер эталона: у Ярины 31 ценовое и 18 срочных чисел признаются обеспеченными
(совпадает с цифрой в коммите `e693ec96`).

### R2. Публичные границы цены — литералом

Любое число, которое боту разрешено произнести, обязано существовать в
knowledge литералом и в ценовом фрагменте — включая производные формы
(«полірування **від 5 000** грн», «до 150 000 грн») и все числа из examples и
playbook. Генератор строит множество допустимых чисел из прайса и **не выпускает
наружу ни одного числа вне него**; попытка = ошибка генерации, а не находка на
приёмке.

### R3. persona.md — первая строка проза

`disclosure`/`honest_prefix` берут первую строку персоны и отдают её лиду на
вопрос «ты бот?». Заголовок `#` уехал бы в чат. Генератор пишет прозу
(«Мене звати {persona_name}, мені {age}. Я {role}…») и запрещает `#` в первой
строке физически.

### R4. Секция эскалации — ТОЛЬКО в playbook и с точным заголовком

`escalation._KEYWORD_HEADINGS` знает ровно три заголовка (`ключевые слова эскалации`,
`escalation keywords`, `ключові слова ескалації`). Любая другая формулировка =
детерминированный слой **молча выключен**. Плюс вторая грабля, пойманная вчера:
парсер забирает ЛЮБУЮ строку `- ` внутри секции, включая строки HTML-комментария —
генератор пишет комментарии без `- ` в начале строки.

Стоп-слова берутся из Q34, и генератор **режет корни до полных фраз**: «з власником»,
а не «власник» (лид сам себе власник авто), «з менеджером», а не «менеджер».
Контекстные намерения (просьба о скидке, торг) в детерминированный слой НЕ идут —
их судит классификатор, и это записывается в комментарий секции.

### R5. examples.yaml из Q20/Q46

Ключи РОВНО `{client, olga}` — хардкод лоадера, унаследованный от первого клиента;
переименование роняет конфиг на старте. Непустые строки, YAML-список верхнего
уровня. Каждый ответ персоны переписывается под правила playbook (вилка + один
уточняющий вопрос) и обязан содержать только числа из R2. Суммарный объём пар
считается против `brain.EXAMPLES_CHAR_BUDGET = 6000`: сверх бюджета пары молча
отбрасываются и голос персоны тихо едет (у Ярины 11 пар, 3587 символов — влезли).

### R6. forbidden_terms — полными фразами, не корнями

Корень «гарант» убил бы легальный раздел «Гарантії та якість роботи», корень
«дешев» — легальное «якщо достатньо дешевшого рішення». Цена ложного
срабатывания — потерянный ответ лиду. Поэтому из Q48/Q50 берутся полные фразы,
плюс:

- апостроф даётся в ДВУХ вариантах (`U+0027` и `U+2019`) — `forbidden_mention`
  матчит подстрокой без нормализации, один вариант молча не сработал бы;
- унаследованный платёжный блок чужой юрисдикции (рубли, российские банки) —
  всегда, стоит ноль;
- имена персон других клиентов («керівниц») — как детектор протечки чужого конфига.

**Самоотравление проверяется до записи:** если термин встречается в собственных
knowledge/playbook/examples/persona — генератор падает и показывает строку.

### R7. Обязательные ФАКТЫ: нет ответа → заглушка + строка в отчёт

`REQUIRED_FACTS` — список фактов, без которых бот врёт или молчит. Он **не
совпадает со списком вопросов формы**: адреса в форме нет вообще, а нужен он
всегда. Каждый факт объявлен как `{id, источник (может быть пустым), заглушка}`:

| Факт | Источник в брифе | Если нет |
|---|---|---|
| Адрес, ориентир, парковка | нет поля в форме | заглушка |
| Сайт, соцсети, портфолио | `q4_links` | заглушка (у Ярины — плейсхолдер-домены) |
| Канал записи | нет поля в форме | заглушка |
| Выходные дни | `q12_hours` (часы есть, выходных нет) | заглушка |
| Телефон | нет поля в форме | заглушка |
| Время ответа владельца | `q35_reply_time` | заглушка |

Заглушка — одна формула на языке клиента: «називає {owner_ref}», и она уходит
в раздел knowledge «Чого ми НЕ знаємо і не називаємо». Одновременно факт даёт
строку в раздел 3 отчёта с готовым вопросом клиенту. **Молча пропустить факт
нельзя**: либо данные, либо заглушка плюс строка. Сторож — C10.

### R8. Обязательные РАЗДЕЛЫ knowledge

Отсутствие раздела — не то же, что отсутствие поля: раздел «Як записатися»
собирается из нескольких полей плюс решения владельца, и при всех заполненных
полях его можно просто не написать. `REQUIRED_SECTIONS` (заголовки на языке
клиента): про компанию, услуги и цены, от чего зависит цена, оплата и
предоплата, гарантии, границы возможного, чего не делаем, как записаться,
чего мы НЕ знаем. Раздел обязан существовать и иметь хотя бы одну содержательную
строку — пустой заголовок считается отсутствующим. Сторож — C11.

### R9. Неконкретный срок обязан называть, КТО его назовёт

Фраза с единицей времени, но без числа («орієнтовно», «зазвичай», «плюс час на
полімеризацію», «залежить від») висит в воздухе: лид получил обещание и не знает,
у кого спросить точное. Генератор дописывает в тот же или следующий пункт
«точний час називає {owner_ref}» (в эталоне так и сделано — knowledge.md:60).
Числовой guardrail здесь бессилен по конструкции: числа нет. Сторож — C14.

### Что генератор НЕ решает сам

`owner_ref` в правильном падеже, имя персоны, модель, `funnel_gate`, `payments`,
`active.yaml` — дефолты плюс явная строка в разделе 2 отчёта. Дефолты жёсткие:
`honesty_mode: honest`, `funnel_gate: false`, `strict_knowledge: true`,
`payments` выключены при отсутствии реквизитов — **даже если бриф просит обратное**
(Q15 просил «спілкуватись як людина»; решение — раздел 2 отчёта с пометкой
«бриф просил другое»).

## 3. ОТЧЁТ — три раздела (главная ценность арки)

`REPORT.md` человеку + `report.json` проверкам (на нём стоят C-проверки §4).

**Раздел 1 — ВЗЯТО ИЗ БРИФА.** Строка на поле: `id → файл:якорь ← цитата`.
Плюс счётчики, которые вчера считали руками: услуг, цен, сроков, стоп-слов,
запрещённых фраз, пар примеров.

**Раздел 2 — ПОДСТАВЛЕНО ДЕФОЛТОМ.** Что подставили, значение, почему, и
**противоречил ли бриф**. Конфликт печатается отдельным блоком «⚠️ бриф просил
другое» — вчера таких было два (Q15 honesty, Q14 имя персоны), и оба были
решениями владельца.

**Раздел 3 — В БРИФЕ НЕТ.** Поля пустые + все `garbage`/`suspect` с дословной
цитатой и причиной. Дальше — то, ради чего раздел существует:

- список, дословно ушедший заглушкой в knowledge → «Чого ми НЕ знаємо і не називаємо»;
- **готовый текст вопросов клиенту**, который владелец копирует и отправляет.

**⚠️ Блок «ФЛАГИ — решает владелец»** идёт ПОСЛЕ трёх разделов и их не заменяет.
Сюда падают проверки, которые не могут быть красными, потому что законная
формулировка клиента и дефект выглядят одинаково (C12, C13). Каждый флаг —
`файл:строка`, цитата и вопрос в одну строку. Пустой блок печатается как «флагов
нет» — молчание и отсутствие проверки должны различаться.

Для Ярины сюда обязаны попасть: адрес студии, телефон/сайт (Q4 — плейсхолдер-домены),
выходные дни, срок службы керамики и PPF, марка материалов, наличие на складе,
контакт для уведомлений (Q36 «мне)»), кто отвечает сейчас (Q10 «1 1 1»),
2FA и доступы (Q52), дата запуска (Q54), метрики успеха (Q55).

## 4. АВТОПРИЁМКА одной командой

`python -m chatter.onboard <slug> --check`. Красное обязано назвать **файл:строку**
и виновника, а не «проверка не прошла».

| # | Проверка | Как | Красное говорит |
|---|---|---|---|
| C1 | Клиент поднимается | `load_config(build/onboard, slug)` без ошибок | текст `ConfigError` как есть |
| C2 | Все цены прайса обеспечены | для каждой строки услуги реплика прогоняется через `guardrails._findings(reply, knowledge)` → пусто | `knowledge.md:47 «Ціна 5 000–8 000 грн» → 8000 не обеспечено (rule=price): в фрагменте нет валюты, точка на поз. 23 разрезала строку` |
| C3 | examples чисты | каждый ответ персоны → `_findings` + `forbidden_mention` (+ `unbacked_promise`) | `examples.yaml пара #4 → 2000 (rule=price); ближайшая строка knowledge.md:94` |
| C4 | Слой эскалации жив | `parse_escalation_keywords(playbook)` непуст; список = списку в отчёте; ни одно слово не является подстрокой легального текста knowledge/examples | `слой пуст — заголовок секции не из _KEYWORD_HEADINGS` / `«поверн» матчит knowledge.md:181 «повернути блиск»` |
| C5 | Нет самоотравления brand-safety | `forbidden_mention` по persona/knowledge/playbook/examples = None | `«гарантія результату» встречается в knowledge.md:174` |
| C6 | persona | первая строка непустая, не `#`, содержит `persona_name` | номер строки |
| C7 | Дрил-сценарий | `drill.parse_scenario` разбирает; `vacuous_expectations` пусто; контакт `<id>:<slug>` есть в `DRILL_CONTACTS` обоих списков | шаг и причина |
| C8 | Формат-гигиена | нет точки внутри ценовых строк; нет NBSP; один десятичный разделитель на файл; бюджет `EXAMPLES_CHAR_BUDGET` не превышен | `knowledge.md:31 NBSP на поз. 12` |
| C9 | Маршрут ICP соблюдён | ни один фрагмент поля с `target: playbook` (ICP, анти-ICP, ЦА) не встречается в knowledge.md; сравнение по нормализованным фрагментам ≥ 40 символов | `q37_icp → knowledge.md:203: «наш ідеальний клієнт…» — ICP едет только в playbook` |
| C10 | Обязательные факты закрыты | каждый `REQUIRED_FACTS` либо обеспечен полем, либо имеет заглушку в «Чого ми НЕ знаємо» И строку в разделе 3 отчёта | `факт «канал записи»: ни данных, ни заглушки — бот выдумает` |

клиента лучше владельца; вчерашняя строка «старший майстер відповідає протягом

**Чего автоприёмка НЕ делает:** живого дрила. `drill_runner.py` идёт по живому

Автоматически проверяется только то, что сценарий разбирается и не самоподтверждается;

## 5. ЧЕГО НЕ АВТОМАТИЗИРУЕМ (явно)

Из шести замечаний вчерашней вычитки пять стали проверками C9–C14. Остаётся
одно, и оно НЕ автоматизируется — ниже пункт 1. **Попытка автоматизировать его
означает LLM-судью над собственным выходом LLM, и он будет соглашаться с собой.**

1. **ТОН и ПРАВДОПОДОБИЕ — только человек.** Звучит ли это как живой
   администратор, а не как справка; не продаёт ли лишнее; не обещает ли того,
   чего ниша не может; веришь ли ты этой реплике как клиент. Формальных
   признаков у этого нет: все проверяемые следствия уже вынуты в C1–C14, и то,
   что осталось, — ровно суждение. Автоматизации не подлежит, и попыток больше
   не делаем.
2. **Конфликты брифа с дефолтами.** Q15 «не говорить, что AI» против
   `honesty_mode: honest`; Q14 «Джарвис» против имени персоны. Пайплайн обязан
   ПОКАЗАТЬ конфликт, решение — владельца.
3. **Решение по флагам C12/C13 и по заглушкам.** Обещание за третье лицо —
   законная формулировка клиента или дефект; сущность «есть» и «не знаем» —
   противоречие или разные сущности; что уходит в «Чого ми НЕ знаємо», а чего
   стоит дождаться от клиента (адрес студии и срок службы керамики — разные
   классы цены ошибки).
4. **Падежи и имена.** `owner_ref: "нашим старшим майстром"` — орудный падеж,
   подставляется после предлога. Склонять программно не будем.
5. **Живой дрил и деплой.** `active.yaml`, логин сессии, `/funnel_gate on`,
   рестарт раннера. Мерж ≠ деплой.

## 6. ПРИЁМКА АРКИ — единственная честная проверка

1. `python -m chatter.onboard yarina --brief .secrets/briefs/brief.xlsx --out build/onboard/yarina`
2. `--check` на результате → **rc 0**.
3. `--diff chatter/clients/yarina` — пофайловое сравнение с ручным вариантом.
4. Каждое расхождение классифицируется письменно, третьего варианта нет:
   - **баг пайплайна** → чиним;
   - **решение человека** (падеж, имя, honesty, что спросить у клиента) → уезжает
     в отчёт, разделы 2 и 3;
   - **улучшение ручного варианта** → правим эталон отдельным коммитом, не молча.
5. Числовые инварианты сходятся с ручной сборкой: 14 услуг, 31 ценовое число,
   18 срочных, 11 пар примеров, слой эскалации непуст.
6. **Калибровка C9–C14 на РУЧНОМ эталоне** (`--check chatter/clients/yarina`,
   только чтение). Красное на файлах, собранных руками и уже отработавших живой
   дрил, означает одно из двух: проверка слишком груба — чиним проверку; либо
   вычитка вчера что-то пропустила — тогда это находка, и она идёт отдельным
   коммитом в эталон. Ожидаемый результат заранее: C12 даёт флаг на
   «Старший майстер відповідає протягом години» (законно, Q35), C10 — заглушки
   по адресу, телефону, выходным.

Боевой `chatter/clients/yarina` в приёмке **только читается**. Ничего не мержим.

## 7. Риски

- **Схема формы — новый источник дрейфа.** Форму правят, схему забывают. Лечение:
  расхождение = rc 2 с картой, а не тихий фолбэк; `schema_version` печатается в отчёте.
- **Отчёт может стать зелёной ширмой.** Если разделы 2 и 3 читать не будут,
  дефолты доедут до прода как «решения». Лечение: отчёт печатает счётчики
  разделов в конце прогона, а `--check` не зелёный, пока раздел 3 не прочитан
  глазами (метка вычитки ставится руками — см. вопрос 3).
- **DEV-28 никуда не делся.** Guardrail сверяет ЧИСЛА, а не УТВЕРЖДЕНИЯ: «кераміка
  тримається 2–3 роки» проходит чисто. Пайплайн эту границу не двигает — держит
  промпт и контрольный шаг дрила.
