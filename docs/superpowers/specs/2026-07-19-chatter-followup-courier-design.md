# Chatter follow-up (курьер + сигнал жизни) — design

- **Дата:** 2026-07-19
- **Ветка:** `chatter-config`
- **Продукт:** `chatter/` — ассистент «Аня». Владелец «Дмитрий».
- **Статус:** design v2 (расширен: два режима ответа + holding), awaiting review → writing-plans пофазно.

## Цель

Аня выполняет обещание «уточню и вернусь»: тема НЕ покрыта базой знаний → она
эскалирует владельцу, владелец даёт ответ, Аня доставляет его лиду. Это ПЕРВАЯ
функция, где Аня пишет лиду ПЕРВОЙ (проактивно) — поэтому ban-стены важнее самой
фичи. Плюс «сигнал жизни»: если владелец молчит, лид получает мягкий знак, что о
нём не забыли, а не тишину.

## Границы (scope)

**В арке:**
- **Case A (Фаза 0):** промпт-упрочнение — есть в ЗНАНИЯ → отвечать СРАЗУ,
  реактивно; «уточню и вернусь» только когда реально не покрыто. НЕ детерм. баг
  (проверено: демо-`knowledge.md` не имеет политики по жалобам → «жалоба» →
  эскалация корректна). Промпт+дрил.
- **Курьер, два режима ответа владельца (Фазы 1–4):**
  - **Режим «текст» (дословно):** владелец дал финальную формулировку → Аня
    доставляет ДОСЛОВНО (реквизиты, точные условия). Ноль LLM.
  - **Режим «инструкция»:** владелец дал Ане ПОРУЧЕНИЕ («предложи 10%, возьми
    контакт») → Аня сама формулирует сообщение лиду в своём тоне ПО поручению.
    LLM-генерация допустима: АВТОР — владелец (его поручение), не knowledge-выдумка
    (не механика 3). Обязателен гардрейл-гейт (см. I5).
- **Сигнал жизни / holding (Фаза 5):** владелец молчит N рабочих часов → Аня шлёт
  лиду мягкое «ваш вопрос ещё в работе, скоро вернусь» (НЕ ответ). Проактив → те
  же стены. Отключаемо в settings.
- **Живой контекст (Фаза 5):** лид дописал пока обещание висит → карточка владельцу
  обновляется (не игнор), часы свежести сбрасываются; лид сам закрыл вопрос →
  обещание сгорает раньше + уведомление владельцу.

**НЕ в арке (бэклог):**
- **Mechanic 3** — Аня САМА сочиняет отложенный follow-up из knowledge и пишет
  первой. Отложено: даже правдивый текст = проактив по таймеру, спам-детект банит
  ПАТТЕРН инициативы, не ложь; а если ответ в knowledge — правильный фикс Case A.

## Инварианты (не нарушать)

- **I1 — до Фазы 3 ноль проактивных отправок лиду.** Фазы 1–2 регистрируют,
  рисуют/обновляют карточку, ловят ответ+режим владельца — и МОЛЧАТ лиду. Первый
  проактив — Фаза 3. Тестируется в каждой фазе.
- **I2 — режим «текст» = курьер, ноль LLM.** Дословная доставка = `owner_answer` +
  лёгкая детерм. рамка (напр. «Вернулась по вашему вопросу — <owner_answer>»;
  строка-шаблон, локализуемая). LLM к этому тексту НЕ прикасается.
- **I3 — регистрация только при ДОСТАВЛЕННОЙ карточке** (нет карточки → владельцу
  нечем ответить → не заводим). Зеркалит H2.
- **I4 — стены обязательны и дрил-проверяемы.** Непроверенная дриллом стена =
  отсутствующая стена.
- **I5 — режим «инструкция» под гардрейл-гейтом.** Сгенерированный текст проходит
  brand-safety ВСЕГДА + unbacked-claim/promise-нет против базы = `knowledge +
  поручение владельца` (поручение = авторизация: «10%» в поручении → обеспечено;
  «20%» вне поручения и вне knowledge → не обеспечено → НЕ отправляем, алерт
  владельцу). H1 приемлем, потому что рамка авторизации — поручение владельца.
- **I6 — КАЖДЫЙ проактивный канал под одними стенами.** Курьер (текст/инструкция)
  и holding — все проходят свежесть/ночь/дневной-кап; каждый «один раз» (доставка
  однократна; holding однократен отдельным флагом).

## Архитектура

### Данные: таблица `follow_ups` (SQLite, переживает рестарт)

| поле | смысл |
|---|---|
| `contact_id` | лид (`<peer>:<slug>`); один активный follow-up на контакт |
| `topic` | тема (реплика лида; обновляется, если лид дописал) |
| `promised_ts` | когда Аня сказала «вернусь» |
| `lead_last_ts` | ts последнего входящего лида (стена свежести; сбрасывается при новом сообщении лида) |
| `card_ref` | ref карточки владельцу, куда он реплайт (`bot:<chat>:<msgid>`) |
| `state` | `pending_owner → ready → sent \| expired \| cancelled` (режим меняется кнопкой ✍️ пока `ready` в окне задержки, без отдельного состояния) |
| `mode` | `verbatim \| instruction` (выбор владельца) |
| `owner_answer` | текст владельца: дословный ответ ИЛИ поручение |
| `owner_answer_ts` | когда владелец ответил (стена задержки) |
| `holding_sent` | сигнал жизни отправлен (однократность holding) |
| `created_ts`, `updated_ts` | служебные |

### Детект обещания возврата — `promises_return(reply) -> bool` (чистая)

- Ловит RU/UK/EN: «вернусь / уточню и вернусь / отвечу позже / дам знать / напишу
  вам»; uk «повернуся/відповім пізніше/дам знати»; en «get back to you/let you
  know/I'll follow up».
- **Негейт:** мяч у лида — «когда определитесь / как решите / вернёмся когда вы /
  дайте знать когда» → НЕ обещание.

### Детект закрытия лидом — `lead_closed_topic(text) -> bool` (чистая, Фаза 5)

- Лид сам снял вопрос: «спасибо, не надо / уже не актуально / отмена / разобрался
  / нашёл в другом месте» (+uk/en). → раннее сгорание follow-up + уведомление
  владельцу «лид закрыл вопрос».

### Триггер эскалации `return_promise`

Новый НЕ-suppress триггер в `deterministic_escalation` (как `owner_handoff`):
обещание возврата → карточка владельцу гарантированно. Ответ НЕ подавляем.

### Поток

1. **Регистрация (Фаза 1, МОЛЧИТ).** В `_escalation_pass`: `promises_return(reply)`
   И карточка доставлена (I3) → `register_follow_up(...)` (`pending_owner`),
   `card_ref` = ref карточки. Одна на контакт (upsert). Карточка несёт строку:
   «Аня обещала вернуться к <лид> по «<тема>». Ответь на эту карточку — доставлю
   дословно; для поручения мне начни с „!“ или нажми ✍️».
2. **Живой контекст (Фаза 5, МОЛЧИТ лиду).** Лид дописал пока `pending_owner` →
   обновляем `topic`/`lead_last_ts`, редактируем карточку владельцу (свежий
   контекст). `lead_closed_topic` → `expired` + уведомление владельцу.
3. **Ответ + режим владельца (Фаза 2, МОЛЧИТ).** Поллер контрол-бота: reply на
   карточку → `owner_answer`. Режим:
   - префикс «!» → `mode=instruction`, текст = остаток;
   - иначе `mode=verbatim` (дефолт), state=`ready`; ак: «Отправлю ДОСЛОВНО через
     ~Xмин. Если это поручение мне — нажми ✍️» (кнопка переключает `mode`→
     instruction в окне задержки — та же стена служит окном коррекции).
   Кнопка «Оставить Ане»/действие владельца → `cancelled`.
4. **Доставка (Фазы 3–4, ПРОАКТИВ).** `follow_up_loop` берёт `ready`,
   `follow_up_send_decision(...)`:
   - `send` + `mode=verbatim` (Фаза 3) → курьерская рамка + `owner_answer` (ноль
     LLM, I2) → лиду через humanizer → `sent`;
   - `send` + `mode=instruction` (Фаза 4) → Аня генерит по поручению → гардрейл-
     гейт (I5) → ок: лиду; фейл гейта: НЕ отправляем, `state` держим, алерт
     владельцу «сгенерированное вышло за рамки поручения»;
   - `wait` (ночь/задержка/кап не дозрел) → оставить `ready`;
   - `expire` (протухло) → `expired` + карточка «окно закрылось, лид остыл».
5. **Сигнал жизни (Фаза 5, ПРОАКТИВ).** `pending_owner` дольше
   `holding_after_work_hours` И `holding_enabled` → одно holding-сообщение лиду
   (шаблон, ноль LLM), `holding_sent=true`. Под стенами I6 (ночь/кап/один раз).
   Follow-up остаётся `pending_owner` (ждём владельца дальше).

### Стены — `follow_up_send_decision(now, follow_up, work_hours, settings, sent_today) -> "send"|"wait"|"expire"`

- **Свежесть:** `now - lead_last_ts > max_age_hours` (деф. 24ч) → `expire`.
- **Не ночью:** `now` вне `work_hours` → `wait`.
- **Задержка:** `now - owner_answer_ts < random[delay_min, delay_max]` → `wait`.
- **Один follow-up:** `sent` не пере-отправляется; лид молчит после follow-up →
  тишина.
- **Дневной кап:** `sent_today >= daily_cap` → `wait`. Кап общий на ВСЕ проактивы
  (курьер + holding), I6.
- Только не холодный контакт (Аня отвечает лишь писавшим) + свежесть.
- Holding — своя чистая проверка (те же ночь/кап + `holding_after_work_hours` +
  `holding_sent` однократность + свежесть).

### Настройки (settings.yaml, дефолты рабочие)

```
follow_up:
  max_age_hours: 24
  daily_cap: 20
  delay_min_seconds: 90
  delay_max_seconds: 600
  holding_enabled: true
  holding_after_work_hours: 4     # молчание владельца (в рабочих часах) → сигнал жизни
```
Рабочие часы — существующий `work_hours`.

## Фазы (каждая: TDD → стоп → дрил-чекпойнт)

### Фаза 0 — Case A (промпт+дрил)
`brain._STYLE`: «есть в ЗНАНИЯ → отвечай сразу; „вернусь“ только когда нет». Тест:
`_STYLE` содержит директиву + дрил in-knowledge вопросов.

### Фаза 1 — модель + детект + регистрация (МОЛЧИТ, I1)
`promises_return`(+негейт), таблица `follow_ups` (ПОЛНАЯ схема, вкл. `mode`,
`holding_sent`) + Store-методы, триггер `return_promise`, регистрация (только при
delivered, I3), строка follow-up в карточке. **I1-тест: лиду ничего не ушло.**
Чекпойнт: «вернусь» → карточка «обещала вернуться… ответь» + `pending_owner`;
лиду тишина.

### Фаза 2 — ответ + режим владельца (МОЛЧИТ, I1)
Поллер: reply→`owner_answer`; режим (дефолт verbatim; «!»→instruction; ✍️
переключает); `ready`; ак с предупреждением о режиме; «Оставить Ане»→`cancelled`.
**I1-тест: лиду всё ещё ничего.** Чекпойнт: реплай → `ready` с текстом+режимом;
тишина лиду.

### Фаза 3 — доставка ДОСЛОВНО + стены (ПРОАКТИВ ВПЕРВЫЕ; ГЛАВНЫЙ ЧЕКПОЙНТ)
`follow_up_send_decision` (каждая стена — тест), `follow_up_loop`, проактивная
курьерская доставка verbatim (I2), burn+карточка, one-per-promise, дневной кап.
**Дрил (обязательно):** (а) полный verbatim — «вернусь»→карточка→мой реплай→через
задержку Аня пишет лиду мой текст; (б) протухшее (>max_age) → сгорает, «окно
закрылось», НЕ реанимируется; (в) ответ владельца ночью → ждёт утра.

### Фаза 4 — режим «инструкция» (ПРОАКТИВ, LLM под гейтом)
Генерация по поручению + гардрейл-гейт I5 (brand-safety + unbacked против
`knowledge+поручение`), send-или-suppress+алерт. **Дрил:** «предложи 10%» → Аня
формулирует и шлёт (10% проходит); проба выхода за рамки («20%»/запрещённый
термин) → НЕ уходит, алерт владельцу.

### Фаза 5 — сигнал жизни + живой контекст (ПРОАКТИВ)
Holding: `pending_owner` > `holding_after_work_hours` → одно мягкое сообщение под
стенами I6; `holding_enabled=false` → тишина. Живой контекст: новый msg лида →
обновление карточки+свежести; `lead_closed_topic` → раннее сгорание+уведомление.
**Дрил:** молчание владельца → holding раз (не ночью, не дубль); holding off →
тишина; лид дописал → карточка обновилась; лид закрыл вопрос → сгорело.

## Edge cases

- Режим не выбран, окно задержки прошло → дефолт verbatim отправляется (ак
  предупредил); поручение без «!»/✍️ уйдёт дословно (видимая ошибка, не тихая).
- Instruction-гейт зафейлил → follow-up НЕ уходит, `ready` держим, алерт; владелец
  переформулирует поручение (новый reply).
- Лид написал снова после `ready` → свежесть ок, доставка идёт; реактивный ответ
  Ани мог опередить — дубля нет (`sent` однократно).
- Peer entity не резолвится → лог + `wait`, не краш.
- Рестарт между фазами потока → состояние в SQLite переживает, loop добьёт.
- Holding отправлен, потом владелец ответил → доставка идёт нормально (holding не
  мешает; свои однократности раздельны).

## Тест-стратегия (сквозная)

- Чистые ф-и (`promises_return`, `lead_closed_topic`, `follow_up_send_decision`,
  holding-решение) — юнит без сети.
- Store — юнит на CRUD/состояния/режим/holding_sent.
- Wiring (`_escalation_pass`, поллер) — как `test_escalation_wiring`/
  `test_control_bot_*`.
- **I1 — явный тест в Фазах 1 и 2** (лиду ноль).
- **I5** — юнит: сгенерированное вне рамок поручения ловится гейтом.
- Стены (I4/I6) — юнит на каждую + дрил.
