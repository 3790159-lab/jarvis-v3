# Спека: дрил v2 — тест-стенд (лид шлёт реплики сам)

**Дата:** 2026-07-26 · **Статус:** ЧЕРНОВИК, ждёт ОК Даниила (код НЕ писать до согласования) · **Предшественник:** `2026-07-25-chatter-drill-harness-v1.md` (в проде), бэклог п.6 «v2»

## 1. Зачем, если v1 работает

v1 свёл дрил к «прочитал строку — отправил — тапнул». Это работает, но упирается в человека: за ночь 26.07 из шести прогонов **до конца дошёл один**. Остальные умерли не от кода — владелец отошёл (таймаут), опоздал на шаг (прогон разъехался), отправил две реплики подряд (два хода схлопнулись в один). Каждый такой прогон стоит вечера и не даёт вердикта.

Пока прогон требует человека у телефона, дрила нет в регрессе. А без регресса каждая правка chatter-арки проверяется вручную — то есть редко.

**Цель v2:** `python scripts/drill_runner.py <сценарий> --auto-lead` проходит сценарий целиком без человека и выдаёт тот же вердикт (0/1/2), что и ручной прогон.

**Не-цели v2:** менять поведение бота; трогать `funnel_gate`; гонять дрил на аккаунте живого клиента; заменять живые дрилы на фикстуры (стенд проверяет ЖИВУЮ модель, просто без человека в цикле).

## 2. Что показал опыт v1 — и что из этого следует для v2

| Наблюдение ночи 26.07 | Следствие для стенда |
|---|---|
| Две реплики за 46 с схлопнулись в один ход, ответ на первую отменился | Отправка следующей реплики — **только после закрытия хода** (`process END` + ≥1 OUT). В v1 это было «часть человека», в v2 это инвариант кода |
| Прогон разъехался на шаг, проверки применились к чужим ходам | Сопоставление по тексту остаётся, но в v2 несовпадение = **красное**, а не предупреждение: стенд шлёт ровно сценарную строку, расхождение означает баг стенда |
| Слот у контакта тащит состояние прошлых прогонов, проверки становятся пустыми | Нужен **сброс состояния** тестового контакта перед прогоном (§6). На клиентском контакте запрещён кодом |
| Классификатор упал на 400 и прогон сгорел вхолостую | **Живой смоук одним вызовом** перед прогоном — обязательный шаг стенда, а не добрая воля |
| Первый ход всегда холодный | Смета стенда: `1 × $0.1191 + (N−1) × $0.0352`; для Д-10 ≈ $0.26 |

## 3. Архитектура: лид — отдельный процесс, а не вторая сессия в харнессе

Инвариант v1 — «харнесс не поллит Telegram» — родился из того, что второй `getUpdates` на токене контрол-бота роняет живой пульт. У v2 добавляется симметричный:

### 🔴 Инвариант v2: боевая сессия и сессия лида НИКОГДА не живут в одном процессе

Раннер держит сессию Ольги — аккаунт клиента. Лид держит свою. Свести их в один процесс значит однажды отправить реплику лида из аккаунта Ольги (или наоборот), а на живом клиенте это необратимо: сообщение уже увидели. Плюс общий event-loop путает Telethon-состояние двух клиентов.

```
drill_runner (судья, читает БД и лог)
   │  stdin: "SAY <текст>"          ← одна строка на реплику
   ▼
drill_lead.py (отдельный процесс, СВОЯ сессия, СВОЙ peer-allowlist)
   │  telegram
   ▼
аккаунт Ольги → раннер обрабатывает ход обычным путём
   │
drill_runner ◀── ждёт закрытия хода в логе, снимает факты, считает вердикт
```

Процесс лида поднимается харнессом на время прогона и гасится в `finally` — долгоживущего демона нет, гасить руками нечего.

## 4. `drill_lead.py` — минимальный отправитель

```
python scripts/drill_lead.py --session .secrets/drill_lead.session --peer <id>
```

Читает stdin построчно, каждая строка `SAY <текст>` → отправляет, печатает `SENT <unix_ts>`; `QUIT` → выходит. Никаких getUpdates, никакой логики сценария: он умеет ровно «сказать в один конкретный чат».

**Предохранители (все с тестами):**

1. **Peer-allowlist.** `--peer` обязателен, и он сверяется со списком разрешённых id в коде. Любой другой получатель — отказ и выход с ненулевым кодом. Опечатка в id не должна становиться сообщением незнакомому человеку.
2. **Только текст.** Ни файлов, ни медиа, ни пересылок.
3. **Потолок сообщений на прогон** (`--max-messages`, дефолт 15). Зацикленный оркестратор не превращается в флуд.
4. **Человеческие паузы** 5–25 с перед отправкой (случайно). Мгновенные ответы на дистанции — сигнал автоматики для антифрода Telegram, а рискуют оба аккаунта, включая клиентский.
5. **Своя сессия, зашифрованная** по образцу P1/P2 (`.enc`), 2FA на аккаунте обязателен.

## 5. Оркестрация в харнессе (`--auto-lead`)

Цикл шага меняется мало — добавляется отправка и ожидание закрытия хода:

1. Пауза (человеческая) → `SAY <текст шага>` в лид-процесс.
2. Ждём **входящее в БД** (как в v1) — подтверждение, что сообщение доехало.
3. Ждём **закрытие хода**: `process END` И ≥1 `OUT` в логе. Только после этого следующий шаг. Если хода нет N минут — шаг `SKIPPED`, работает тот же fail-fast.
4. Снимаем факты, считаем проверки — код v1 без изменений.

Ручной режим остаётся: без `--auto-lead` всё работает как сегодня. Стенд — надстройка, а не замена (на живом клиенте лида-автомата не будет никогда).

## 6. Сброс состояния: только на тестовом контакте

Регресс требует предсказуемого старта, иначе «пустые проверки» съедают половину сценария (в прогоне 25.07 три из четырёх obligations-проверок были зелены ещё до старта).

`scripts/drill_reset.py --contact <тестовый>` удаляет у контакта сообщения, профиль, обязательства и стадию воронки. Предохранитель — тот же `DRILL_CONTACTS`, что уже стоит на `--delete` в `drop_phantom_obligations.py`: на клиентском контакте отказ, потому что это стирание истории живой переписки.

Со сбросом сценарий Д-10 становится сильнее: можно проверять **создание** долгов с нуля (сегодня `recalc` пришлось удалять руками, чтобы это стало возможным), а `profile_contains` перестаёт зеленеть за счёт прошлых прогонов.

## 7. Что стенд НЕ отменяет

- **`funnel_gate` не трогаем.** Тестовый лид попадает в `allowlist` клиента явной строкой в `settings.yaml`. Открытие гейта ради дрила — это приём незнакомых лидов на живом аккаунте, цена ошибки несопоставима.
- **Рабочие часы.** У volska есть `work_hours`; ночью бот может не отвечать. Регресс по расписанию — только внутри рабочего окна, иначе прогон честно упрётся в таймаут (и будет прав).
- **Живой смоук классификатора** одним вызовом перед прогоном: инцидент 26.07 показал, что офлайн-тесты с подменённым LLM-швом не ловят контракт API. $0.02 против сгоревшего прогона.
- **Дрил остаётся живым.** Стенд убирает человека из цикла, а не модель из проверки.

## 8. Риски и как их держим

| Риск | Держим |
|---|---|
| Блокировка тестового аккаунта Telegram | человеческие паузы, потолок сообщений, один получатель, низкая частота (не чаще 1 прогона в час) |
| Блокировка аккаунта КЛИЕНТА (страшнее) | лид пишет только нам; частота та же; прогон в рабочем окне; при первом же намёке на лимит — стоп прогонов |
| Реплика уходит не туда | peer-allowlist в коде + тест на отказ |
| Стенд правит состояние живого клиента | сброс только на `DRILL_CONTACTS`; на клиентском контакте отказ |
| Прогон незаметно дорожает | смета до старта, `--max-cost`, факт по окнам шагов (v1 уже умеет) |

## 9. Приёмка v2

1. Д-10 проходит **одной командой без человека**, вердикт 0.
2. Прогон повторяется **дважды подряд с одинаковым вердиктом** — воспроизводимость, которой у ручного дрила нет в принципе.
3. Лид отказывается писать кому-либо, кроме заданного peer (тест).
4. Сброс отказывается работать на клиентском контакте (тест).
5. Ни одного обращения к `funnel_gate` в коде стенда (тест-сторож по исходнику, как на `getUpdates` в v1).
6. Полный прогон укладывается в смету ±20% и в 10 минут.
