# Спека: catch-up обязан отличать «не успел» от «решил молчать»

**Статус:** ЖДЁТ ОК владельца. Код по ней НЕ писан.
**Повод:** живой случай 17.08 на клиенте Артёма.
**Родня:** [[jarvis-catchup-reanswers-escalated-dialog]], DEV-18 (молчаливый
отказ), правило «молчаливый дефолт = класс бага» (P17).

## 1. Что произошло

17.08 13:15, плановый рестарт Ярины после мержа продовых правок. На старте
`catch-up` увидел один диалог с непрочитанным сообщением и обработал его:

```
16.08 23:46   клиент: «перед тим як оплачувати PPF на 120–150 тисяч, хочу
                      побачити ваш договір…»
              → диалог ЭСКАЛИРОВАН, карточка владельцу, бот замолчал
17.08 13:15   рестарт → catch-up: 1 dialog(s) with missed messages
              → тот же текст записан в историю ВТОРОЙ раз (id 46 → id 65)
              → два вызова LLM, два ответа отправлены, новая карточка
```

Клиент получил ответ бота **через 13 ч 49 мин** — поверх человека, который
уже вёл диалог. Это не «лишняя реплика»: это вмешательство в разговор,
который бот сам же и передал.

## 2. Корень

`telethon_run.collect_missed` фильтрует по трём признакам: приватный диалог с
человеком, отправитель допущен (`admission_decision`), сообщение не старше
`CATCHUP_MAX_AGE_SECONDS` (24 ч). **Состояние КОНТАКТА не спрашивается вообще.**

А молчание бота имеет две причины, и снаружи они выглядят одинаково:

| причина | как выглядит | что должен делать catch-up |
|---|---|---|
| не успел (лежал, деплой, ребут) | нет ответа на входящее | ответить — ради этого он и есть |
| решил молчать | нет ответа на входящее | **не трогать** |

Catch-up знает только первую. Значит КАЖДЫЙ подъём раннера — деплой, гардиан,
ребут, `chatter_client -Action start` — переоткрывает диалоги, которые человек
забрал себе.

## 3. Полный список состояний «бот молчит НАМЕРЕННО»

Вопрос владельца: «сколько ещё состояний означают намеренное молчание?»
Замер по коду и по схеме БД (`contacts`, `runtime_flags`, `settings.yaml`):

| # | состояние | где живёт | смысл | catch-up |
|---|---|---|---|---|
| 1 | `state = 'escalated'` | `contacts.state` | передан человеку, ждёт его | **пропустить** |
| 2 | `human_took_over = 1` | `contacts` | человек уже пишет в диалог | **пропустить** |
| 3 | `paused = 1` (+ `pause_until`, `pause_source`) | `contacts` | пауза по команде пульта или по правилу | **пропустить** |
| 4 | глобальный `kill_switch` | `runtime_flags` | бот выключен на ВСЕХ | **пропустить** (и это уже так: раннер не отвечает вовсе — проверить) |
| 5 | `funnel_gate: false` + контакт не в allowlist | `settings.yaml` | трафик не открыт | уже учтено `admission_decision` |
| 6 | `denylist` | `settings.yaml` | явный запрет | уже учтено |

**Открытый вопрос владельцу (Q1):** `paused` с истёкшим `pause_until` — это
«ещё пауза» или «уже нет»? Предлагаю: истёкшая пауза = обычный диалог,
catch-up отвечает. Пауза без срока = молчание по решению.

**Открытый вопрос (Q2):** снотворное (`snooze`) в схеме БД отдельным полем НЕ
найдено — если такой режим есть на уровне пульта, назови его, добавлю.

## 4. Что делаем

**Р1. `collect_missed` получает состояние контакта и пропускает молчащие по
решению.** Функция сейчас чистая и transport-agnostic — состояние приезжает
ВМЕСТЕ с диалогом (`silent_by_decision: bool`), а не читается из БД внутри:
чистоту ядра ломать нельзя, её же сторожат существующие тесты.

**Р2. Пропуск ГРОМКИЙ.** Строка лога на каждый пропущенный диалог:
`catch-up skip 545893540:yarina — escalated (молчание по решению, возраст 13.8 ч)`.
Молчаливый пропуск — тот же класс, что молчаливый ответ: через месяц никто не
скажет, почему клиент остался без реплики.

**Р3. Владелец узнаёт.** Пропущенный диалог с ЖИВЫМ ожиданием — повод не для
ответа бота, а для напоминания человеку: одна карточка в пульт
«при подъёме пропущено N диалогов, которые ведёшь ты» — БЕЗ дублирования уже
поднятых карточек эскалации.

**Р4. Порог возраста остаётся** как есть (24 ч) и продолжает жить в одном
месте.

## 5. Чего НЕ делаем

* Не трогаем `admission_decision` — это другой вопрос (кого вообще слушаем).
* Не «умное» решение по содержимому («похоже, человек уже ответил») — это
  LLM-судья над собственным выходом, отвергнуто в §5.1 спеки онбординга.
* Не откладываем ответ в очередь «на потом». Диалог ведёт человек; очередь
  превратится в ту же реплику, только позже.

## 6. Сторожа (пишет НЕ автор кода)

| # | утверждение | мутация, которая обязана краснеть |
|---|---|---|
| C1 | эскалированный диалог с непрочитанным входящим НЕ попадает в ответ | снять проверку состояния |
| C2 | обычный диалог с непрочитанным входящим — попадает | сделать пропуск безусловным |
| C3 | `human_took_over` пропускается | сузить список до `escalated` |
| C4 | `paused` без срока пропускается | то же |
| C5 | пауза с ИСТЁКШИМ сроком — отвечаем | считать любую паузу вечной |
| C6 | каждый пропуск оставляет строку лога с причиной | убрать логирование |
| C7 | порог возраста берётся из одной константы | заменить литералом 86400 |
| C8 | ядро остаётся чистой функцией (состояние приходит аргументом) | чтение БД внутри `collect_missed` |

## 7. Приёмка

1. Гейт и мутационный гейт зелёные.
2. Живой прогон на СТЕНДЕ: диалог дрил-контакта эскалируется, раннер
   перезапускается, в логе `catch-up skip …`, реплика НЕ отправлена.
3. Замер радиуса (`chatter_catchup_radius.py`) до и после подъёма даёт одно и
   то же число — то есть подъём ничего не переответил.
4. Регрессия: обычный пропущенный диалог по-прежнему получает ответ (иначе мы
   починили одно и сломали то, ради чего catch-up существует).

## 8. Пока не сделано — костыль работает

`chatter_client.ps1 -Action start` меряет радиус и отказывается поднимать
клиента, если catch-up кого-то переответит (коммит `98342b6a`). Костыль
закрывает ПЛАНОВЫЕ подъёмы и не закрывает подъём гардианом после смерти
раннера — именно поэтому нужна эта спека.
