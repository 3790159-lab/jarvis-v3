## 0. Что чиним

Сегодня подключение живёт в `docs/chatter/ONBOARDING_MANUAL.md` — 9 разделов,
~15 команд, три из которых нельзя менять местами. Ярину подключали по нему
16–17.08: логин → токен → перешифровка → реестр → подъём → дрилы. Прошло
хорошо, и это ничего не доказывает: чеклист исполнял человек, который его же
и писал, в один заход, не отвлекаясь.

Три способа, которыми этот путь ломается, уже наблюдались:

1. **Порядок.** Сегодня, 20.08, трижды подряд: рестарт не в том месте убил бы
   здоровую панель, а `enabled: true` до валидного конфига дал бы гардиану
   бесконечный цикл подъёма. Порядок держится памятью исполнителя.
2. **Обрыв.** Сессии рвутся по несколько раз в день. Половина подключения —
   это состояние, которого нет ни в одном файле: «токен уже записал?
   перешифровал? бандл снимал?». Возобновление сегодня = пересказ по памяти.
3. **Двенадцать команд подряд.** Каждая печатает своё, и ни одна не знает, что
   было до неё. Пропущенный шаг обнаруживается на следующем — или у клиента.

**Цель:** ОДНА команда, которая доводит подключение до конца, останавливается
на первом несоответствии, называет действие и продолжает с того же места после
любого обрыва.

**Не цель:** заменить человека там, где решает вкус, доступ или закон — §5.

## 0-бис. 🔴 Поправка к постановке: `active.yaml` — ЛОЖНЫЙ КАНАЛ

В задаче названо «`active.yaml` + рестарт + приёмка». Автоматизировать
`active.yaml` **нельзя**, и не потому, что трудно, а потому, что подключения он
не касается. Факты, снятые сегодня:

* шапка самого файла: «⚠️ ГАРДИАНОМ ЭТОТ ФАЙЛ БОЛЬШЕ НЕ ИСПОЛЬЗУЕТСЯ»;
* `scripts/chatter_guardian_detached.ps1:338` — гардиан зовёт раннер как
  `chatter.telethon_run --personas <slug> --session … --db … --client <slug>`,
  то есть состав приходит **планом из реестра**, а `active.yaml` не читается
  вовсе;
* в том же скрипте (стр. 145–155) есть комментарий, объясняющий, почему из
  стартовой строки гардиана убрали упоминание состава: строка «печатала бы
  неизменное `active.yaml` / по первому слагу, то есть врала бы ровно там, где
  должна помогать».

`active.yaml` остаётся живым ровно для одного случая: ручной запуск
`python -m chatter.telethon_run` без аргументов, для разовой отладки. Подключение
клиента этим путём не идёт и идти не должно — ручной процесс умирает вместе с
сессией (урок 22.07, записан в §4 мануала).

**Значит:** источник истины подключения — `chatter/clients/registry.yaml`.
Автоматизируем запись туда. `active.yaml` не трогаем **ни на байт**, и это
записано отдельным сторожом (Д13): правка `active.yaml` во время подключения —
дефект, а не недоделка.

Класс уже знаком: [[jarvis-panel-db-source-is-the-live-runner]] — спека
чинила канал, которого живой процесс не читает.

## 1. Модель состояния: шаг = ПРОБА ФАКТА НА ДИСКЕ

Главное требование заказчика: подключение может прерваться посередине, и
состояние обязано восстанавливаться из фактов, а не из памяти процесса.

Поэтому у команды **нет своего файла состояния как источника истины**. Каждый
шаг — чистая функция:

```
probe(ctx) -> StepResult          # точная сигнатура — §12.2, здесь только модель
Verdict ∈ { ЗАКРЫТ, НЕ ЗАКРЫТ, ПРОТИВОРЕЧИЕ }
```

* **ЗАКРЫТ** — факт есть и согласован с соседями;
* **НЕ ЗАКРЫТ** — факта нет; шаг предстоит (кому — §3);
* **ПРОТИВОРЕЧИЕ** — факты спорят друг с другом (реестр включён, а конфига
  нет; в реестре одна сессия, на диске другая). Это дефект, не ожидание.

Журнал (`state/connect/<slug>.md`, дописывается после каждого шага) заводится
для ЧЕЛОВЕКА и **не читается пробами никогда**. Если журнал удалить, ни один
вердикт не изменится; если журнал подделать — тоже. Это прямое следствие
[[jarvis-two-numbers-for-one-thing]]: второе представление состояния молча
погасило бы первое. Сторож Д7 держит оба направления.

Отсюда же **идемпотентность**: повторный запуск команды не повторяет ни одного
действия, чей факт уже на диске. Особенно платного — §2.3.

## 2. Ворота: три вида, и у каждого названа цена

Ворота — не «проверка на всякий случай». Каждое стоит между действием и
конкретным ущербом, который уже наблюдался.

### 2.1. Предусловие (что должно быть ДО шага)

| ворота | что предотвращает |
|---|---|
| конфиг грузится НАСТОЯЩИМ `load_config` | `enabled: true` при битом конфиге = гардиан поднимает и роняет раннер по кругу |
| сессия открывается (`session_available`, правило `.enc` из `secret_loader`) | подъём в вечный рестарт: сессии нет, процесс умирает на старте |
| `.env.enc` в состоянии `in_sync` | `bootstrap_env` при наличии `.enc` читает ТОЛЬКО его: токен, записанный в plaintext `.env`, до процесса не доедет — ловушка Ярины 16.08 |
| имя env-переменной токена **пер-клиентское** и уникальное среди включённых | общий токен = два раннера в `getUpdates`, Telegram отдаёт long-poll одному, второй ловит 409, команды пульта ходят через раз **без ошибок в логе** |
| `session`/`db` не совпадают с другим ВКЛЮЧЁННЫМ клиентом | гонка за запись `.session` вплоть до разлогина аккаунта (валидация реестра это уже умеет — зовём её, а не повторяем) |
| `funnel_gate: false` на всём протяжении | подключение не имеет права открыть трафик; открывает владелец отдельной командой |

### 2.2. Доказательство (что должно быть ПОСЛЕ шага)

Шаг закрывается фактом, а не отсутствием ошибки:

* реестр — не «файл записан», а `registry_cli` не находит ошибок. Тонкость,
  которую легко потерять: валидация смотрит только ВКЛЮЧЁННЫХ, а S10 пишет
  `enabled: false`, поэтому проверяется ВКЛЮЧЁННАЯ КОПИЯ записи — иначе
  требование было бы недостижимым по построению;
* подъём — не «скрипт отработал», а `state/chatter_clients.json` даёт `alive`
  И heartbeat свежий. **`starting` за `alive` не считается** (Д10);
* токен доехал — строка `control-bot poller starting (isolated token)` в
  `logs/chatter_<slug>.log`. Именно она доказала перешифровку у Ярины;
* дрил — файл `state/drills/<ts>.md` и код возврата харнесса, а не «прогнали».

### 2.3. Деньги и радиус

* **Дрил платный** (~$0.20–0.30 за прогон, замер 17.08: $0.2287 при смете
  $0.2951). Смета печатается ДО старта. Второй прогон при существующем
  результате — только явным флагом. Повтор «на всякий случай» — это деньги
  клиента и посторонний трафик в его БД.
* **Подъём меряет catch-up радиус** — но НЕ своей копией: зовём
  `scripts/chatter_client.ps1 -Slug <slug> -Action start`, в который замер уже
  вшит (17.08, требование владельца). Отказ замера = остановка. `-Force` команда
  подключения **не подставляет никогда**: у нового клиента радиус нулевой по
  построению, а если он вдруг не нулевой — это и есть то, что надо прочитать
  глазами.

## 3. Карта шагов

Колонка «кто» — **А** автомат, **Ч** человек по конструкции (§5).
Колонка «факт» — то, что читает проба. Порядок менять нельзя; каждая строка
опирается на факт предыдущей.

| # | шаг | кто | факт на диске |
|---|---|---|---|
| S0 | среда: `TELEGRAM_API_ID/HASH`, `ANTHROPIC_API_KEY`, реестр парсится | **Ч** | значения в env-материале, `registry_cli` без `fatal` |
| S1 | конфиг собран T1–T6 | **Ч** | `build/onboard/<slug>/` + `report.json`, красных проверок нет |
| S2 | вычитка тона и правдоподобия | **Ч** | метка `REVIEWED` в каталоге сборки, после неё `--check` даёт rc 0 |
| S3 | решения по флагам и конфликтам брифа | **Ч** | каждый флаг, поднятый в `report.json` (подмножество `C12`/`C13`/`C16`), **назван** в тексте метки |
| S4 | конфиг перенесён в `chatter/clients/<slug>/` | А | каталог существует и грузится `load_config` |
| S5 | **согласие клиента на доступ к аккаунту** | **Ч** | `chatter/clients/<slug>/CONSENT.md`: дата + от кого получено |
| S6 | логин Telegram (код из SMS, 2FA) | **Ч** | `.secrets/<slug>.session(.enc)`, `session_available` = true |
| S7 | токен у BotFather → `.env` → перешифровка | **Ч** | пер-клиентская env-переменная непуста, `-Check` = `in_sync` |
| S8 | пересъём бандла секретов `.jrvbak` | **Ч** | маркер `state/connect/<slug>.bundle.txt` со строкой «сессии в бандле», в ней есть слаг |
| S9 | allowlist: владелец + дрил-контакт | А | `telegram.allowlist` в `settings.yaml` живого конфига |
| S10 | запись в `registry.yaml`, `enabled: false` | А | запись есть, `runnable` посчитан, `error=null` |
| S11 | подъём: `chatter_client.ps1 -Action start` | А | `enabled: true` в реестре + замер радиуса прошёл |
| S12 | приёмка живости | А | `alive` + свежий heartbeat + строка `isolated token` |
| S13 | первый дрил-прогон, автономный (`--auto-lead`) | А + **ворота денег** | `state/drills/<slug>/<ts>.md`, в ТЕЛЕ отчёта назван клиент, + код возврата |
| S14 | вычитка текста дрила глазами | **Ч** | харнесс не судит правдоподобие: `EXPECT_KEYS` закрыт |
| S15 | открытие трафика `/funnel_gate on confirm` | **Ч** | **вне команды навсегда** — §5.5 |

**Почему S0 и S1 помечены «человек», хотя проверяются автоматом.** Колонка
«кто» отвечает на вопрос «кто ЗАКРЫВАЕТ шаг», а не «кто проверяет». Секрет в
`.env` кладёт владелец; конфиг собирает отдельная команда `chatter.onboard`.
Автоматического действия у этих шагов нет, и выдумывать его нельзя: `connect`,
умеющий сам пересобрать конфиг, однажды пересоберёт вычитанный.

Отсюда инвариант, который держит код честным: **AUTO ⇔ у шага есть `act`**.
Шаг без действия — человеческий по определению, и его остановка обязана
называть точную команду (§12.4). Автоматических шагов ровно шесть: S4, S9,
S10, S11, S12, S13.

**S1 и S2 разведены не случайно.** `--check` даёт rc 0 только ВМЕСТЕ с меткой
(решение владельца q3 от 17.08), поэтому «rc 0» не может быть признаком S1 —
он уже содержит в себе S2. Проба S1 читает `report.json`: красных нет, флаги
могут быть. Иначе шаг «конфиг собран» был бы недостижим до вычитки и печатал бы
человеку «сделай то, что ты и так собирался», вместо «читай отчёт».

**S3 стоит объяснить отдельно.** «Человек принял решения по флагам» — суждение,
и проверить его нельзя. Но можно проверить МЕХАНИЧЕСКОЕ следствие: что в тексте
метки названы все флаги, которые поднял отчёт. Это не оценка решения, это
доказательство, что решение вообще принималось про каждый флаг, а не про те,
что попались на глаза. Метка уже сегодня несёт свободный текст («подпись под
выжимкой от 17.08, полный REPORT.md не читался») — форма не меняется, добавляется
только требование назвать id.

**S5 (согласие) стоит ПЕРЕД логином, и это не формальность.** Бот читает ВСЮ
личку аккаунта — мы просим доступ к личной переписке человека. Факт: одна
строка с датой и от кого получено. Проба проверяет ровно проверяемое: файл
есть, непуст, дата разбирается и не в будущем.

Сверку «согласие датировано РАНЬШЕ логина» я рассматривал и **отвергаю**:
единственная опора для даты логина — mtime session-файла, а он двигается при
каждой записи Telethon. Сторож на нём был бы то зелёным, то красным без связи
с предметом. Порядок держится порядком шагов, а не сверкой времён.

**S8 (маркер бандла), вариант (б) владельца.** Команда экспорта печатает
строку `сессии в бандле: ...` — её человек кладёт в маркер. Проба требует
ровно двух вещей: маркер существует и непуст, и в строке **назван слаг этого
клиента**. Это и есть тот факт, которого не давал вариант (а).

Чего проба НЕ делает: не сравнивает время маркера с временем session-файла.
Соблазн («бандл снят ДО логина и не несёт новой сессии») понятен, но опора
негодная — та же, что отвергнута в S5: mtime сессии двигается при каждой
записи Telethon, и после подъёма раннера (S11) такой сторож краснел бы на
здоровом подключении. Сторож, который меняет вердикт сам по себе, — это фон,
а не проверка.

Остаточный риск назван вслух: маркер доказывает, что бандл снимали и что в
нём была эта сессия, но не доказывает ни свежести бандла, ни того, что
носитель уехал с машины. Это потолок проверяемого; round-trip из §9 мануала
остаётся человеческим.

**S4: расхождение с `build/` ПОСЛЕ переноса — норма, а не ворота.** Человек
правит тон в живом конфиге, и это ровно то, ради чего §5.1 существует. Проба
S4 спрашивает «каталог есть и грузится», а разницу с `build/` печатает
СТРОКОЙ ОТЧЁТА. Ворота здесь превратили бы вычитку в дефект.

**Тройка вердиктов S4 — ОБЩЕЕ ПРАВИЛО, а не свойство одного шага.**

| факт | вердикт |
|---|---|
| артефакта нет вовсе | НЕ ЗАКРЫТ; `todo` называет шаг, который его создаёт |
| артефакт есть и читается | шаг идёт дальше по своим воротам |
| артефакт есть и НЕ читается / спорит сам с собой | ПРОТИВОРЕЧИЕ |

`ПРОТИВОРЕЧИЕ` означает «факты спорят ИЛИ факт нечитаем», и ни одно из двух не
описывает факт, которого ещё просто нет. Правило распространяется на всех, кто
читает НЕ СВОЙ факт: S7, S9 и S15 читают живой конфиг (его переносит S4), S11 —
запись реестра (её заводит S10) и сам реестр (его заводит S10 вместе с первой
записью).

Цена ошибки здесь не на исполнении — цикл до S7 с непереносённым конфигом не
доходит, — а в `--plan`. Карта это ПЕРВЫЙ взгляд человека на инструмент, и
четыре красных в первом же запуске учат не смотреть на красное: то же
слипание, ради снятия которого решался q2, только в обратную сторону —
«жду тебя», напечатанное как «сломано».

## 4. Один вход

```
python -m chatter.connect <slug>              # довести подключение до ближайших ворот
python -m chatter.connect <slug> --plan       # НИЧЕГО не делать: карта шагов и вердикты
python -m chatter.connect <slug> --drill-yes  # разрешить ОДИН платный дрил-прогон (S13)
python -m chatter.connect <slug> --drill-again  # повторный дрил при уже имеющемся результате
python -m chatter.connect <slug> --root <путь>  # корень ДАННЫХ (репетиция §9.1)
```

`--root` — не флаг «сделай шаг N»: это корень ДАННЫХ (конфиг, реестр, сессии,
БД, логи), он нужен репетиции §9.1 в отдельном дереве. КОД при этом всегда
берётся от дерева модуля: `--root`, из которого запускались бы скрипты,
превратил бы ключ «где лежат данные» в «какой код исполнить». У
`chatter_client.ps1` дефолт `C:\jarvis`, поэтому `-Root` передаётся ему
ВСЕГДА — без этого репетиция в песочнице правила бы живой реестр.

Флагов для «сделай только шаг N» нет намеренно: это и есть возврат к двенадцати
командам. Порядок выбирает код, человек выбирает — продолжать или нет.

`--drill-yes` — решение владельца q4: **перед дрилом останавливаемся всегда**,
даже на $0.2–0.3. Повод конкретный: позавчера баланс кончился посреди прогона,
и владелец узнал об этом от бота. Поэтому остановка печатает смету ДО списания,
а не после. Флаг разрешает ровно один прогон и не запоминается: следующий
запуск снова остановится.

Каждая остановка печатает ТРИ строки и ничего сверх:

```
ОСТАНОВ на S7: токен контрол-бота.
ПОЧЕМУ: CHATTER_CONTROL_BOT_TOKEN_ACME пуст. Общий токен с другим клиентом
        даёт 409 в getUpdates, и пульт отвечает через раз без ошибок в логе.
ЧТО СДЕЛАТЬ: возьми токен у @BotFather, добавь через .\scripts\add_secret.ps1,
        затем .\scripts\reencrypt_env.ps1; после этого повтори ту же команду.
```

Строка «повтори ту же команду» обязательна везде: вход один, и человек не
должен помнить, чем продолжать.

### Коды выхода

| код | значение |
|---|---|
| 0 | ГОТОВО: все автоматические шаги закрыты, осталась только команда владельца об открытии трафика |
| 3 | ЖДЁТ ЧЕЛОВЕКА: штатная остановка на шаге из §5 |
| 1 | ПРОТИВОРЕЧИЕ: факты спорят между собой — разбираться |
| 2 | НЕ СОСТОЯЛСЯ: не прочитали вход/факты, прогон ничего не доказал |

Отделять 3 от 1 нужно ради автоматики и ради человека: «жду тебя» и «сломано»
требуют разной реакции, а слипшись они приучают не смотреть на красное.
**Решение владельца q2: четыре кода, конвенция `onboard` подождёт.**

У `--plan` кодов ровно два: **0**, если карта построена (какими бы ни были
вердикты — он отвечает на вопрос «где я», а не «всё ли хорошо»), и **2**, если
факты прочитать не удалось. Кодов 1 и 3 у него не бывает: он ничего не делает,
значит ни ждать, ни ломать не может.

## 5. ЧЕГО НЕ АВТОМАТИЗИРУЕМ — ПО КОНСТРУКЦИИ

Список закрытый. Каждый пункт — не «руки не дошли», а «автоматизация здесь
означает подделку».

1. **Тон и правдоподобие** (S2, S14). Звучит ли это как живой администратор;
   не обещает ли лишнего; веришь ли реплике как клиент. Все проверяемые
   следствия уже вынуты в C1–C14 автоприёмки; остаток — суждение. Автомат здесь
   = LLM-судья над выходом LLM, и он согласится с собой. Попыток больше не
   делаем (решение записано в §5.1 спеки T1–T6).
2. **Решения по флагам и конфликтам брифа** (S3). «Не говорить, что AI» против
   `honesty_mode: honest`; «Джарвис» против имени персоны; обещание за третье
   лицо — законная формулировка или дефект. Пайплайн обязан ПОКАЗАТЬ конфликт;
   выбор — владельца, и цена ошибки лежит на нём, а не на коде.
3. **Логин Telegram** (S6). Код из SMS, 2FA, чужой номер. Автоматизировать
   нечего и не нужно: session-файл = полный доступ к аккаунту.
4. **Токен у BotFather** (S7). Секреты вводит владелец интерактивно; команда
   только проверяет, что токен доехал до процесса.
5. **Открытие трафика** (S15). `/funnel_gate on confirm` — команда владельца.
   Ни при каком раскладе, ни при каком флаге команда подключения его не
   выполняет: за ним стоит catch-up по непрочитанному за сутки.
6. **Пересъём бандла секретов** (S8). Пароль только через getpass, носитель —
   вне машины. Автомат не может ни ввести пароль, ни унести файл.
7. **Согласие клиента на доступ к аккаунту** (S5). Разговор с человеком и его
   слово. Автомат может только требовать факт и отказываться идти дальше без
   него — что и делает.
8. **Разрешение на трату** (S13). Не потому, что суммы велики, а потому, что
   человек обязан видеть списание до него, а не узнавать от бота.

Пункты 1–4 названы заказчиком; 5–8 добавлены по той же причине — чтобы через
месяц никто не пытался их «доделать».

## 6. Обрыв посреди подключения

Обрыв обязан быть невидим для результата. Требования, из которых это следует:

* **Каждая запись атомарна.** `registry.yaml` пишется во временный файл рядом
  и переименовывается поверх; половины файла не существует ни в один момент.
  Реестр читает гардиан каждые ~30 с — полуфайл означал бы `fatal` у всех
  клиентов сразу, включая живых.
* **Ни один шаг не зависит от предыдущего в памяти.** Между шагами процесс
  может умереть; следующий запуск читает те же факты.
* **Порядок выбран так, что любое прерывание безопасно.** Опасное состояние
  ровно одно — «в реестре `enabled: true`, а конфига/сессии нет»: гардиан
  начнёт цикл подъёма. Поэтому включение (S11) стоит ПОСЛЕ конфига (S4) и
  сессии (S6), и оно же — последнее автоматическое действие перед приёмкой.
  Это тот самый порядок деплоя, из-за которого сегодня трижды понадобились
  ворота.
* **Платное не повторяется** (S13). Прерванный дрил оставляет файл прогресса,
  и он читается: харнесс пишет `state/drills/<ts>.md` ПОСЛЕ КАЖДОГО ШАГА
  именно на этот случай.

## 7. Сторожа

Пишутся **от этой спеки**, автором, который планового кода не видел
([[jarvis-guards-not-by-the-plan-author]]). Ниже — что ловить, а не как.

| # | что ловит |
|---|---|
| Д1 | обрыв на КАЖДОМ шаге: процесс убит после шага N, повторный запуск доводит до конца и не повторяет ни одного действия |
| Д2 | порядок: при отсутствии валидного конфига или сессии `enabled: true` не выставляется НИ ПРИ КАКОМ пути |
| Д3 | деньги: при существующем результате дрила второй прогон не запускается без явного флага |
| Д4 | радиус: отказ замера catch-up останавливает подъём; `-Force` не подставляется автоматически ни в одной ветке |
| Д5 | токен: общее (не пер-клиентское) имя env-переменной или совпадение с включённым клиентом → останов |
| Д6 | allowlist: произвольный id не вписывается; дрил-контакт берётся из `payments/drill_gate.DRILL_CONTACTS`; owner id обязателен |
| Д7 | состояние ТОЛЬКО из фактов: удаление журнала не меняет ни одного вердикта; подделка журнала — тоже |
| Д8 | живой клиент не трогаем: slug уже `alive` с открытым гейтом → команда отказывается целиком, а не «доподключает» |
| Д9 | запись реестра атомарна: прерывание в момент записи не оставляет файла, который `parse_registry` не читает |
| Д10 | приёмка живости не принимает `starting` за `alive` и не принимает протухший heartbeat |
| Д11 | у КАЖДОЙ остановки «что сделать» непустое И АДРЕСНОЕ (закрытый список признаков А1–А5 — §12.4) — структурно, по всем ветвям, а не на трёх примерах |
| Д12 | идемпотентность: два запуска подряд на завершённом подключении не меняют на диске ничего |
| Д13 | `active.yaml` не изменяется ни на одном шаге (§0-бис) |
| Д14 | `funnel_gate` не переводится в `true` ни на одном шаге и ни при каком флаге |
| Д15 | согласие: без `CONSENT.md` подключение не доходит до логина; пустой файл и файл без даты — тоже останов |
| Д16 | маркер бандла: маркер без слага этого клиента → останов; вердикт НЕ зависит от mtime сессии (двигать сессию — вердикт не менять) |
| Д17 | деньги: без `--drill-yes` дрил не запускается НИ РАЗУ; флаг не запоминается между запусками |
| Д18 | «факта нет» ≠ «факты спорят»: в мире, где ничего не делали, НИ ОДНОГО `CONFLICT` по всем шагам; в мире, где факты спорят, `CONFLICT` там же, где был. Обе стороны обязательны — без второй починка вырождается в «объявить всё не закрытым» |

Д1 и Д7 — главные: они держат то самое требование, ради которого арка и
затевается. Д14 — единственный, чья цена измеряется в живых лидах.

## 8. Мутационный гейт

`scripts/mutate_connect_pipeline.py`. Мишени — механика ворот, а не тексты:
снятая проверка порядка (S11 до S4), `alive` из `starting`, повторный платный
дрил, чтение состояния из журнала, подстановка `-Force`, пропуск проверки
уникальности env-имени токена. Каждая мутация обязана краснеть РОВНО у того
сторожа, который на неё заведён, и гейт обязан отдавать rc 1.

Перед каждым прогоном — статическая сверка мишеней с кодом
([[jarvis-mutation-gate-target-drifts-from-code]]): сегодня она нашла две
уехавшие мишени за секунды.

**Сведение мишеней 21.08 (3 слепых из 7).** Слепая мутация — находка о ГЕЙТЕ,
и каждая оказалась своим классом:

* **сторож назван не по предмету.** Снятое предусловие у `act_s11` ловилось —
  но не тем сторожем, что был назван: названный проверяет ПОРЯДОК и до
  `act_s11` с битым конфигом не доходит, потому что порядок как раз соблюдён.
  Правится имя, а не код.
* **мишень на втором рубеже.** «Повторный платный дрил» стоял на `forced` в
  `__main__`, а деньги держит `act_s13`: снятие `forced` не потратило ни цента.
  Ноль красных в переписи означал не дыру в сторожах, а мишень не по предмету.
* **сторож зелёный по ДРУГОЙ причине.** Мир сторожа на совпадение имени токена
  давал нашему клиенту имя соседа, и проба останавливалась раньше — на «имя не
  пер-клиентское». Проверка совпадения не исполнялась ни разу; сторож был
  зелёным и на исправном коде, и на мутанте.

**Пятый способ, которым гейт врал** (к четырём из его шапки): статическая
сверка читала файл `read_text`, а писатель мутанта — `read_bytes().decode()`.
Питон при чтении переводит `CRLF` в `LF`, поэтому на CRLF-файле сверка
находила ВСЕ мишени, а `replace` не находил ни одной многострочной: гейт
печатал «все мишени на месте» и уходил в «мутация не применилась». Сверка
приведена к чтению писателя. Рядом стоит грабля, которая CRLF и принесла:
`Path.write_text` на Windows — ПЕРЕВОДЧИК переводов строки, и скрипт-патч,
читающий `read_text` и пишущий `write_text`, молча меняет весь файл.

## 12. КОНТРАКТ МОДУЛЯ (обязателен для обеих сторон)

Сторожа и плановый код пишут РАЗНЫЕ авторы, друг друга не видящие
([[jarvis-guards-not-by-the-plan-author]]). Значит имена и формы данных обязаны
быть заданы ЗДЕСЬ, иначе сторожа проверят фантом, а код окажется правильным
про другое. Всё, чего в этом разделе нет, автор решает сам — и сторож не имеет
права на это опираться.

### 12.1. Состав

```
chatter/connect/
  __init__.py
  model.py       Verdict, Owner, StepResult, Step, Ctx — данные, БЕЗ ввода-вывода
  probes.py      probe_s0 … probe_s15 — ТОЛЬКО чтение фактов, ничего не меняют
  actions.py     act_s4, act_s9, act_s10, act_s11, act_s12, act_s13 — ровно шесть автошагов
  steps.py       STEPS — литеральный кортеж в порядке исполнения
  __main__.py    CLI, порядок, коды выхода, тексты остановок
```

Модуль **отдельный от `chatter.onboard`** (решение q5). Импорта `chatter.onboard`
из `chatter.connect` нет: сборка файлов и подъём живого клиента — разные права.

### 12.2. Данные

```python
class Verdict(str, enum.Enum):
    CLOSED   = "закрыт"
    OPEN     = "не закрыт"
    CONFLICT = "противоречие"

class Owner(str, enum.Enum):
    AUTO  = "автомат"
    HUMAN = "человек"

@dataclass(frozen=True)
class StepResult:
    step_id: str          # "S6"
    verdict: Verdict
    why: str              # одна строка: какой факт есть/отсутствует И чем это грозит
    todo: str             # что сделать; НЕПУСТО у любого не-CLOSED (Д11)
    facts: dict           # машиночитаемые улики: пути, признаки. СЕКРЕТОВ НЕТ НИКОГДА
    waits_for_human: bool = False   # штатное «жду тебя» у АВТОШАГА (деньги, секрет)

@dataclass(frozen=True)
class Step:
    id: str               # "S0".."S15"
    title: str
    owner: Owner
    probe: Callable[[Ctx], StepResult]
    act: Callable[[Ctx], StepResult] | None   # None у HUMAN-шагов; AUTO <=> act is not None

@dataclass(frozen=True)
class Ctx:
    root: Path
    slug: str
    now: float
    env: Mapping[str, str]
    runner: CommandRunner    # ЕДИНСТВЕННЫЙ путь наружу: подпроцессы только через него
    drill_yes: bool
    drill_again: bool
```

`facts` — единственное, что читают сторожа для тонких утверждений; `why`/`todo`
проверяются на непустоту и адресность, но НЕ на дословный текст: сторож на
буквы сообщения превратил бы правку формулировки в красное.

`CommandRunner` — протокол с одним методом
`run(argv: list[str], *, cwd: Path, timeout: float) -> CommandResult(rc, stdout, stderr)`;
`CommandResult` живёт в `model.py`, `isinstance` против конкретного класса не
используется нигде — подставной раннер сторожа обязан работать по форме, а не
по родству. Внешние вызовы (`registry_cli`, `chatter_client.ps1`,
`drill_runner.py`, `reencrypt_env.ps1`) идут ТОЛЬКО через него. Прямой
`subprocess` в `probes.py` и `actions.py` запрещён — это и делает сторожей
возможными без живых процессов.

Поле называется `runner`, а вызов пишется `ctx.runner.run(argv, cwd=..., timeout=...)`.
Прежнее имя `run` допускало ДВА законных прочтения — `ctx.run(...)` и
`ctx.run.run(...)`, — и пара авторов разошлась на нём молча. Одна вещь — одно
имя; по той же причине шов CLI назван так же:

```python
def main(argv: list[str] | None = None, *,
         runner: CommandRunner | None = None,
         root: Path | None = None) -> int
```

`runner=None` — боевой раннер, `root=None` — корень репозитория. Без этого шва
сторож на §12.4 и на коды выхода поднимал бы живые подпроцессы, живой телеграм
и живой реестр, то есть не существовал бы.

**Беда раннера — это ИСКЛЮЧЕНИЕ, а не `CommandResult` с выдуманным `rc`.**
Таймаут, ненайденный исполняемый, любая невозможность выполнить: ловит
вызывающая проба или действие и превращает в `CONFLICT` с внятным `why`.
«Замер не состоялся» и «замер сказал нет» обязаны различаться.

`Ctx.now` — unix-секунды (float), и время берётся ПО ХОДУ, а не замораживается
на старте: подключение живёт минутами, а замороженное время сделало бы
протухший heartbeat вечно свежим — то есть погасило бы Д10.

#### 12.2.1. Ключи `facts` — минимальная схема

Сторожа читают `facts`, значит имена задаются ЗДЕСЬ, а не выдумываются каждым
автором. Ключей может быть больше; перечисленные обязаны быть.

| шаг | обязательные ключи |
|---|---|
| S0 | `env_missing: list[str]`, `registry_fatal: str \| None` |
| S1 | `report_path: str`, `red: list[str]`, `flags: list[str]` |
| S2 | `mark_path: str`, `mark_present: bool` |
| S3 | `flags_named: list[str]`, `flags_missing: list[str]` |
| S4 | `client_dir: str`, `loads: bool`, `slug_in_config: str \| None` |
| S5 | `consent_path: str`, `consent_date: str \| None` |
| S6 | `session_path: str`, `session_available: bool` |
| S7 | `env_name: str`, `token_len: int`, `env_enc_state: str` |
| S8 | `marker_path: str`, `slug_named: bool` |
| S9 | `allowlist: list[int]`, `owner_present: bool`, `drill_present: bool` |
| S10 | `entry_present: bool`, `runnable: bool`, `error: str \| None` |
| S11 | `enabled: bool`, `radius_ok: bool` |
| S12 | `state: str`, `heartbeat_age: float \| None`, `isolated_token_line: bool` |
| S13 | `run_path: str \| None`, `rc: int \| None`, `estimate_usd: float` |

`token_len` вместо значения — иллюстрация §12.5, а не исключение из него.

**`False` значит «проверили, нет». «Не проверяли» — это `None`.** Ключ,
который проба не смотрела на своей ветке, обязан быть `None`, а не значением
по умолчанию: `isolated_token_line: False` при СУЩЕСТВУЮЩЕЙ строке в логе
отправляет человека перешифровывать исправный токен. Обратное тоже верно и
проверяется отдельно: там, где ответ ПОЛНЫЙ («владельца в конфиге нет вовсе»),
`None` читался бы как «может, и есть».

**`env_enc_state` — перечень ЗАКРЫТ:** `no_env` · `no_enc` · `unreadable` ·
`in_sync` · `stale` (значения `scripts/reencrypt_env.py`). Закрывает шаг только
`in_sync`. Значение ВНЕ перечня — включая «строку статуса вообще не нашли» —
это ПРОТИВОРЕЧИЕ: мы не поняли ответ инструмента, а не «шаг предстоит».

### 12.3. Порядок исполнения (единственный)

```
для каждого шага в STEPS:
    если шаг в TAIL_HUMAN_IDS:                      -> ПРОПУСТИТЬ (см. ниже)
    r = probe(ctx)
    если r.verdict == CONFLICT:                     -> печать, выход 1
    если r.verdict == CLOSED:                       -> следующий шаг
    если owner == HUMAN:                            -> печать, выход 3
    если owner == AUTO:
        act(ctx)
        r2 = probe(ctx)                             # ДОКАЗАТЕЛЬСТВО, а не «act не упал»
        если r2.verdict == CLOSED:                  -> следующий шаг
        если r2.waits_for_human или act вернул waits_for_human -> печать, выход 3
        иначе                                       -> печать, выход 1
все шаги S0…S13 закрыты -> печать того, что осталось за человеком -> выход 0
```

Повторная проба после действия обязательна: «команда отработала» и «факт
появился» — разные утверждения, и сегодня это стоило бы панели.

**У автошага есть ветка «жду разрешения человека», и это не четвёртый
вердикт.** Денежные ворота S13 — именно ожидание (§5.8), и по буквальному
алгоритму они печатали бы «сломано» на штатном пути: ровно то слипание, ради
снятия которого решался q2. Признак один — булево `waits_for_human`; «ждёт
человека» это не другое состояние ФАКТА, а другой АДРЕСАТ следующего действия.
**Старшинство:** признак значим ТОЛЬКО при вердикте, отличном от `CLOSED`.
Факт на диске старше ожидания — если шаг закрыт, ждать нечего.

**Хвостовые человеческие шаги S14 и S15 в цикл не входят.** Они закрываются
словом владельца, а не фактом на диске, и буквальный цикл упирался бы в код 3
ВСЕГДА — то есть код 0 был бы недостижим, а §4 расходился бы с §12.3. В карте
`STEPS` они ЕСТЬ (её читает человек в `--plan`, и путь, обрывающийся на дриле,
соврал бы про то, чем подключение кончается), а исключение живёт отдельной
литеральной константой `TAIL_HUMAN_IDS = ("S14", "S15")` в `steps.py`. Вывести
её из `owner == HUMAN` нельзя: человеческих шагов десять, хвостовых ровно два.

**Единственная ветка, где действие зовётся ПОВЕРХ вердикта пробы** — явно
запрошенный повтор платного прогона (`--drill-again` ВМЕСТЕ с `--drill-yes`).
Он перекрывает и «закрыт» (прогон был зелёный), и «противоречие» (прогон был
красный или прерван). Пробы флагов не читают вовсе: флаг — это разрешение
действовать, а не факт на диске.

**Нарушение контракта — код 2, а не трассировка.** `ConnectContractError` и
любое исключение сборки шагов CLI обязан поймать и напечатать как «прогон НЕ
состоялся: контракт нарушен, <что именно>». У этой ветки нет шага, который
назвать, поэтому три строки §12.4 к ней не применяются; требование к ней одно —
сказано, ЧТО нарушено, и трассировки нет.

**Журнал `state/connect/<slug>.md` пишет `__main__.py`, и только он**, одной
записью на ИСПОЛНЕННЫЙ шаг (append). Прогон, который ничего не исполнил,
журнала не заводит и не трогает — иначе повторный запрос состояния менял бы
диск. `probes.py` не пишет ничего; `actions.py` — только то, что назван писать
шаг.

### 12.4. Тексты остановки

Ровно три строки, в этом порядке и с этими префиксами:

```
ОСТАНОВ на <id>: <title>.
ПОЧЕМУ: <why>
ЧТО СДЕЛАТЬ: <todo>; после этого повтори ту же команду.
```

`todo` обязан быть не просто непустым, а **АДРЕСНЫМ**: называть хотя бы один
токен из закрытого списка. Список закрыт именно затем, чтобы сторож Д11
проверял адресность механически, а не «на глаз»:

| # | признак | образец |
|---|---|---|
| А1 | **путь** к файлу или каталогу (разделитель `/`/`\` или расширение) | `chatter/clients/volska/settings.yaml`, `.secrets/`, `state/drills/` |
| А2 | **имя скрипта или команды ВМЕСТЕ хотя бы с одним ключом/аргументом** | `chatter_client.ps1 -Action start -Slug volska`, `Start-ScheduledTask -TaskName JarvisChatterGuardian`, `registry_cli disable --slug volska` |
| А3 | **флаг самой команды подключения** | `--drill-yes`, `--drill-again`, `--root` |
| А4 | **слаг клиента** — конкретный, из `ctx.slug` или реестра | `volska`, `yarina` |
| А5 | **слеш-команда пульта** | `/funnel_gate on confirm`, `/clients` |

Пунктов ровно пять; расширять список — правка спеки и сторожа, а не решение
автора текста на месте. В стороже список **литеральный**, не выведенный из
кода ([[jarvis-literal-lists-not-introspection]]): выведенный согласился бы с
реализацией по определению и промолчал бы там, где она забыла.

Адрес берётся из `facts` ТОГО ЖЕ вердикта: если проба знает слаг, путь или имя
таска — они обязаны доехать до строки `ЧТО СДЕЛАТЬ`, а не остаться в улике.
Улика машиночитаема, а читает её ночью человек. Отсюда же смычка с правилом
`None`/`False` (§12.2.1): ключ, которого проба не смотрела, адреса не даёт.

Два образца НЕадресного текста, оба из планового кода, и оба исправлены:

* **S12, было:** `убедись, что таск JarvisChatterGuardian живёт, и подожди один
  его цикл (~30 с)` — имя таска названо, признаков ноль: имя это
  существительное, а не команда. **Стало:** `подними таск: Start-ScheduledTask
  -TaskName JarvisChatterGuardian, через 30 с повтори ту же команду; если таск
  падает — его лог в logs/chatter_guardian.log` (А2 + А1).
* **S7, было:** `почини конфиги названных клиентов либо выключи их, затем
  повтори` — «названных» отсылает к строке выше, которую ночью прочитают по
  диагонали. **Стало:** `почини chatter/clients/volska/settings.yaml (полный
  список — facts.broken_slugs) либо выключи запись: registry_cli disable
  --slug volska` (А1 + А4 + А2).

Непустоты НЕДОСТАТОЧНО. «Убедись, что таск живёт, и подожди цикл» —
грамматически «что сделать», а фактически совет: человеку в три ночи он
не говорит, что набрать, и отправляет в мануал — ровно туда, куда арка
обещала не отправлять (§9 п.2). Адрес берётся из `facts` того же вердикта:
если проба знает слаг и путь, они обязаны доехать до строки, а не остаться
в улике.

Проверяется АДРЕСНОСТЬ, а не дословный текст (§12.2): сторож на буквы
сообщения превратил бы правку формулировки в красное, и его первым же делом
обошли бы копипастой. Сверка идёт в ОБЕ стороны: `todo` без единого признака
обязан краснеть, `todo` с признаком — зеленеть при любой переписанной вокруг
него фразе.

### 12.5. Красные линии кода

* `probes.py` НИЧЕГО не пишет на диск — ни файла, ни строки журнала;
* `actions.py` пишет только то, что назван писать шаг; запись `registry.yaml` —
  через временный файл и `os.replace`, никаких частичных состояний;
* ни один модуль не пишет в `chatter/clients/active.yaml` (Д13) и не ставит
  `funnel_gate: true` (Д14);
* `-Force` у `chatter_client.ps1` не подставляется никогда (Д4);
* секреты не попадают ни в `facts`, ни в журнал, ни в вывод: доказываем
  ПРИЗНАКОМ («переменная непуста, длина 46»), а не значением;
* **любая наша запись в существующий файл конфигурации** идёт через временный
  файл рядом и `os.replace`. Правило шире реестра: `act_s9` правит
  `settings.yaml` ЖИВОГО клиента, а полуфайл конфига читают раннер и гардиан.
  Каталог клиента въезжает так же — одним переименованием (§6).

Две сверки держатся AST, а не взглядом:

* в `probes.py` и `actions.py` нет прямого `subprocess` — иначе шов §12.2
  обходится, и сторожа перестают что-либо доказывать, оставаясь зелёными;
* `chatter.connect` не запускает `chatter.onboard`. Запрет q5 — про ПРАВА и
  радиус ошибки, а не про две замороженные константы: `from
  chatter.onboard.checks import REVIEWED_FILENAME` и подобное разрешено,
  запрещено всё, что ЗАПУСКАЕТ пайплайн (сборку, рендер, пересборку конфига).

### 12.6. Журнал правок 20–21.08: что менялось и почему

Восемь разделов-журналов, стоявших здесь, сведены в §1–§12: там решения и
живут. Появились они потому, что семь пар авторов читали документ параллельно и
находили дыры быстрее, чем переписывалось тело, — для работы это правильный
порядок, для чтения нет. Остаётся короткое «что менялось» и УКАЗАТЕЛЬ: в
докстрингах модуля и сторожей ссылки вида «§12.7 п.1» ещё живы, и оставить их
висеть в пустоту значило бы завести третий экземпляр правды ровно того класса,
что ловит [[jarvis-approved-text-three-places]].

#### Что нашла дисциплина «сторожа пишет НЕ автор кода»

Все находки — дефекты СПЕКИ, найденные ДО первой строки исполнения либо
измеренные на ней; ни одна не найдена чтением кода глазами.

1. **Цикл не мог вернуть 0 НИКОГДА.** Хвостовые человеческие S14/S15 фактом не
   закрываются, и буквальный §12.3 всегда упирался в код 3. → §12.3,
   `TAIL_HUMAN_IDS`.
2. **Полукопия каталога заклинивала подключение навсегда.** Обрыв посреди
   пофайлового копирования оставлял каталог, который не грузится, и следующий
   запуск объявлял ПРОТИВОРЕЧИЕМ то, что команда сама же и оставила. →
   атомарный въезд одним переименованием, §6 и §12.5.
3. **Согласие лежало в каталоге, который создаёт автомат** — тупик у того, кто
   всё сделал ПРАВИЛЬНО и положил согласие первым. → `state/connect/<slug>.consent.md`.
4. **`state/drills/<ts>.md` без слага** — чужой прогон закрыл бы шаг дрила:
   ложный зелёный на единственном шаге, доказывающем, что бот отвечает. →
   каталог отделяет, ТЕЛО отчёта доказывает (§3 S13).
5. **У автошага не было ветки «ждёт человека»** — денежные ворота выдавали бы
   «сломано» на штатном пути. → `waits_for_human`, §12.3.
6. **Схема врала про флаги:** `checks._c7` ставит `is_flag` руками, поэтому
   «подмножество C12/C13/C16» прощало бы флаг DEV-36. → S3 требует назвать ВСЕ
   поднятые в отчёте флаги (§3).
7. **Пара авторов разошлась на `ctx.run`:** один читал как объект с методом,
   другой как функцию — обе трактовки законны. → `ctx.runner`, §12.2.
8. **Д8 не был реализован: команда «доподключала» ЖИВОГО клиента** — замер
   сторожа дошёл до платного дрила в БД клиента с ОТКРЫТОЙ воронкой. Первая
   попытка привязки не считается: отказ поставили в `main()` НАД циклом, и
   сторож на порядок не увидел его вовсе. **Защита, которую нельзя выразить
   вердиктом шага или инвариантом данных, недостижима для всякого, кто идёт по
   контракту.** → отказ живёт в `probe_s0`, проверка слага — в `Ctx.__post_init__`.
9. **Улика утверждала то, чего не проверяли:** `probe_s12` коротил на не-`alive`
   и отдавал `isolated_token_line: False` при СУЩЕСТВУЮЩЕЙ строке в логе. →
   правило `None`/`False`, §12.2.1.
10. **Незнакомое `env_enc_state` — ПРОТИВОРЕЧИЕ, а не «не закрыт»:** значение
    вне закрытого перечня означает, что мы не поняли ответ инструмента. → §12.2.1.
11. **Непустота «что сделать» — не то требование.** «Убедись, что таск живёт, и
    подожди цикл» грамматически «что сделать», а фактически совет, отправляющий
    человека в мануал — то есть в цену всей арки (§9 п.2). Разбор владельца
    21.08: «человек в три ночи должен получить КОМАНДУ, а не совет». →
    адресность в КОНТРАКТЕ, закрытый список А1–А5, §12.4.
12. **«Факта нет» печаталось как «факты спорят»** (21.08). `--plan` на
    неподключённом клиенте давал ЧЕТЫРЕ ПРОТИВОРЕЧИЯ (S7, S9, S11, S15) — там,
    где ждут человека. Сторож-перебор нашёл ПЯТОЕ, невидимое глазами: у S11
    «реестра нет файлом» слипалось с «реестр не разбирается», хотя S0 и S10 эти
    случаи уже разводили. → тройка вердиктов как общее правило (§3) и Д18 (§7).

#### Находки ВНЕ границ арки

* **`scripts/drill_runner.py::format_report` не называл, ЧЕЙ прогон** — на
  машине с несколькими клиентами отчёт был уликой ни о чём. Правка сделана в
  этой же ветке (в шапку отчёта добавлены `client` и `contact`).
* **Бэкап состояния НЕ забирал согласие.** `CRITICAL_PATTERNS` в
  `app/services/state_backup.py` — явный БЕЛЫЙ список, и `connect/` в нём не
  было: единственная улика доступа к чужой личной переписке жила в одном
  экземпляре на одном диске. Добавлены `connect/*.consent.md` и
  `connect/*.bundle.txt`.
* **Белый список бэкапа не пришпилен ничем.** Теста на СОСТАВ нет; арка
  пришпилила только свои два шаблона, остальные двенадцать держатся
  человеческим взглядом. Отдельная задача.
* **Импорт `chatter.onboard` — узкое исключение** (замороженные константы
  вроде `REVIEWED_FILENAME`), запрет q5 остаётся про запуск пайплайна. →
  §12.5.
* **Коллизия имени токена с ВЫКЛЮЧЕННЫМ клиентом законна** (§2.1 говорит
  «уникальное среди включённых»): сторож на этот случай не пишется — тест,
  краснеющий на более строгом коде, плохой тест.
* **S1 не может проверить «красных нет» по `report.json`:** вердиктов C1–C17
  там нет вовсе. `red` на S1 — это красное, которое отчёт доказывает САМ
  (`slug_mismatch`, `file_missing`); красное автоприёмки живёт в S2.
* **`Config.slug` для S4 не годится** — он равен переданному аргументу и
  совпадёт всегда. Принадлежность доказывается содержимым
  (`control.control_bot_token_env`, иначе шапка `settings.yaml`); не нашлось —
  шаг закрывается, но `why` прямо говорит, что принадлежность доказана только
  путём.
* **Дрил — СУФЛЁР**, а `CommandRunner` вывод захватывает: шаг, задуманный
  автоматическим, тихо стал бы «сиди и жди, подсказки увидишь потом». Поэтому
  S13 идёт автономно (`--auto-lead`), а без предпосылок автолида СТАНОВИТСЯ
  человеческим шагом с точной командой для СВОЕЙ консоли.
* **Смету считает САМ ХАРНЕСС** (режим плана, без `--yes`): наша копия ставок
  разошлась бы с его `COST_TURN_*` молча.
* **Посторонние id в allowlist СОХРАНЯЮТСЯ и называются вслух:** стереть чужую
  строку значит выключить бота живому человеку.
* **Формат `CONSENT.md`:** первая строка начинается с ISO-даты `YYYY-MM-DD`,
  дальше свободный текст «от кого получено».
* **Owner id — из `control.owner_chat_id` живого конфига**, не из env и не из

* **`radius_ok = enabled`:** `chatter_client.ps1` выставляет `enabled: true`

* **Сверки времён отвергнуты дважды** (S5 и S8): `.session` переписывается
  Telethon при каждой записи, и сторож на mtime краснел бы на здоровом
  подключении. Сторож, который меняет вердикт сам по себе, — фон, а не проверка.
