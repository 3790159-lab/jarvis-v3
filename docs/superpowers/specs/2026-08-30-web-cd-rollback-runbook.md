## §2. 🔴 Почему обратный порядок НЕ РАБОТАЕТ

Перепись живёт в конструкторе `Store` (`chatter/storage/db.py:512-551`) и
срабатывает **по ФАКТУ формы** данных, а не по флагу: если в базе есть
двухсегментные `contact_id`, любое открытие её новым кодом переписывает базу и
снимает `.bak`. Выключателя «пока не мигрировать» в этой схеме нет.

`.bak` снимается **до** переписи, значит лежит в **старой** форме. Отсюда:

> **Новый код, открыв восстановленный `.bak`, мигрирует и его тоже.**
> Замерено на пробнике 29.08: `.bak` открылся новым кодом за 0.059 с и вышел
> из открытия с `старая форма 609 → 0`.

| порядок действий | что получится |
|---|---|
| положить `.bak`, код оставить новым | база мигрируется **заново** при первом же открытии — откат не состоялся |
| откатить код, базу оставить мигрированной | новый формат в старом коде — **не читается** (`peer_of('237616472:volska')` → `ContactRefError`) |
| **сначала код назад, потом `.bak`** | ✅ единственный работающий порядок |

И вторая половина той же причины — **гардиан**. Он поднимает раннер **из
рабочего дерева** (DEV-31), а триггер подъёма — смерть процесса, не команда
человека. Пока `JarvisChatterGuardian` в состоянии Running и в дереве лежит
новый код, любой подъём раннера открывает базу новым кодом и **съедает
положенный `.bak`**. Поэтому стоп гардиана — **первый** шаг, а не последний.

## §3. Порядок отката

Выполнять сверху вниз. Ни один шаг не пропускать, порядок не менять.

### Шаг 1 — СТОП ГАРДИАНА (первым, до всего остального)

```powershell
Stop-ScheduledTask    -TaskName JarvisChatterGuardian -ErrorAction SilentlyContinue
Disable-ScheduledTask -TaskName JarvisChatterGuardian | Out-Null
Get-ScheduledTask -TaskName JarvisChatterGuardian | Select-Object TaskName, State
```

Ожидается `State = Disabled`. **Проверить фактом, а не предположить:** пока
задача Running, шаги 2–3 бессмысленны.

Затем снять сами раннеры — **по ТОЧНЫМ PID**, не по подстроке (широкий kill по
`*telethon_run*` уже сносил боевые процессы):

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like '*chatter.telethon_run*' } |
  Select-Object ProcessId, CommandLine        # СНАЧАЛА посмотреть
# затем таргетированно, по каждому найденному PID:
Stop-Process -Id <PID> -Force
```

Убедиться, что ни одного процесса `chatter.telethon_run` не осталось: живой
раннер держит хэндл базы, и подмена файла на шаге 3 либо не пройдёт
(`WinError 32`), либо пройдёт наполовину.

### Шаг 2 — КОД НАЗАД на `9b5ff3f7`

```powershell
cd C:\jarvis
git status --porcelain          # дерево обязано быть чистым
git checkout phase-4.0-unified-jarvis
git reset --hard 9b5ff3f7
git log --oneline -1            # обязано показать 9b5ff3f7
```

**Только после того, как `git log` показал `9b5ff3f7`,** переходить к шагу 3.
Это и есть тот шаг, который делает откат данных возможным: пока в дереве новый
код, положенный `.bak` — расходник.

### Шаг 3 — `.bak` НА МЕСТО, обе базы, каждая своим

Для **каждой** из двух баз, по отдельности:

```powershell
# 1. найти её .bak (у каждой базы СВОЙ)
Get-ChildItem C:\jarvis\.secrets\demo.db.pre-web-c-*.bak
Get-ChildItem C:\jarvis\.secrets\yarina.db.pre-web-c-*.bak

# 2. увести мигрированную базу в сторону, НЕ удаляя (она — улика)
Move-Item C:\jarvis\.secrets\demo.db `
          C:\jarvis\.secrets\demo.db.migrated-<дата> -Force

# 3. убрать хвосты sqlite, иначе поверх старого файла ляжет новый журнал
Remove-Item C:\jarvis\.secrets\demo.db-wal, C:\jarvis\.secrets\demo.db-shm `
            -ErrorAction SilentlyContinue

# 4. положить .bak на место базы
Copy-Item C:\jarvis\.secrets\demo.db.pre-web-c-<epoch>.bak `
          C:\jarvis\.secrets\demo.db
```

Затем то же для `yarina.db` с **её** `.bak`.

**Проверка ДО подъёма** — читать только `sqlite3` в режиме `mode=ro`, **не через
`Store`**: открытие через `Store` кодом любой версии есть действие, а не
наблюдение.

```
для каждой базы:
  число строк по таблицам           — совпадает с «до» из отчёта прогона
  contact_id NOT LIKE '%:%:%'       — БОЛЬШЕ НУЛЯ (старая форма вернулась)
  PRAGMA table_info(contacts)       — human_took_over ПРИСУТСТВУЕТ
  PRAGMA table_info(invoices)       — origin_msg_id снова INTEGER
```

Ожидаемые числа старой формы из отчёта прогона: **volska 609**, **yarina 115**.
Если старая форма = 0 — восстановился не тот файл, либо код на шаге 2 не
откатился и `.bak` уже съеден. **Не поднимать раннеры, разбираться.**

### Шаг 4 — ПОДЪЁМ и доказательство, что обе живые

```powershell
cd C:\jarvis
.\scripts\chatter_client.ps1 -Slug volska -Action start
.\scripts\chatter_client.ps1 -Slug yarina -Action start
.\scripts\chatter_client.ps1 -Slug volska -Action status
.\scripts\chatter_client.ps1 -Slug yarina -Action status
```

Подъём обязан быть **доказан**, а не объявлен: зачистка живого и подъём замены —
одна транзакция, и непподъём не имеет права выглядеть как тишина.

| что проверить | чем |
|---|---|
| процесс есть | `Get-CimInstance … chatter.telethon_run`, **два** slug'а |
| heartbeat свежий | `state\chatter_heartbeat_volska.txt`, `…_yarina.txt` — возраст в секундах, не «файл есть» |
| раннер отвечает | живой ход в каждую клиентку, ответ бота дошёл |

Только после этого:

```powershell
Enable-ScheduledTask -TaskName JarvisChatterGuardian | Out-Null
Start-ScheduledTask  -TaskName JarvisChatterGuardian
Get-ScheduledTask | Where-Object { $_.TaskName -like 'Jarvis*' -and $_.State -eq 'Running' } |
  Select-Object TaskName, State
```

Гардиан включается **последним** и только после доказанного подъёма: включённый
раньше, он поднимет раннер сам, из того дерева, какое есть, и сделает это
беззвучно.

## §4. Чего этот runbook НЕ покрывает

* **Переписку, пришедшую ПОСЛЕ миграции.** `.bak` — это снимок на момент до
  переписи. Всё, что клиенткам написали между миграцией и откатом, в `.bak`
  отсутствует и откатом теряется. Значит цена отката растёт с каждым часом
  работы после мержа — это довод откатываться быстро или не откатываться вовсе,
  и его надо назвать вслух в момент решения.
* **Панели клиенток** (`JarvisPanelClientGuardian*`) — они читают ту же базу.
  При откате их тоже надо снять и поднять, иначе панель будет держать хэндл на
  файле, который подменяют.
* **Ситуацию «мигрировали, поработали, откатились, снова мержим»** — второй
  прогон миграции снимет **новый** `.bak` с новым epoch. Старый не удалять и не
  путать.

## §5. Условие применения

Runbook исполняется **целиком и без импровизации** при любом красном на приёмке
пары C→D. Частичное исполнение («ну я только базу верну») — это первый из трёх
неработающих порядков §2.
