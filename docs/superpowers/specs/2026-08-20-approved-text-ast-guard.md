## 1. Почему AST, а не grep

Grep не отличает **код** от **комментария**. В том же
`tamapi_dashboard.py` фраза уже цитируется рядом в комментариях к правке, и
`grep -c` дал бы «текст на месте» ровно тогда, когда из кода его вынесли.
Проверено: по сырому тексту файла вхождений 1, по AST — тоже 1, строка 536; но
достаточно одному комментарию процитировать фразу, и эти два числа разойдутся —
а сторож обязан считать только то, что **исполняется**.

Второе: `APPROVED_1` собран неявной склейкой двух литералов через перенос
строки. `ast.literal_eval` отдаёт склеенное значение; регулярка — нет.

Третье: импортировать тест-модуль ради константы нельзя — это сбор pytest'а
внутри сторожа. Нужен именно разбор файла.

## 2. Механика сторожа

Новый файл `tests/test_approved_text_matches_spec.py`. Три извлечения, затем
сверка **посимвольно** (после нормализации только пробельных последовательностей
— в HTML фраза разбита переносом; больше ничего не нормализуем, ни регистр, ни
кавычки, ни `<b>`).

1. **Из кода**: `ast.parse` файла, обход `ast.walk`, сбор всех `ast.Constant`
   со строковым значением — включая константные куски `JoinedStr` (f-строк),
   они и есть наш случай. Комментарии в AST отсутствуют по определению — это и
   даёт нужную слепоту к ним.
2. **Из сторожа**: `ast.parse` файла теста, найти модульное присваивание с
   нужным именем, значение взять `ast.literal_eval`.
3. **Из спеки**: прочитать markdown, найти фенсед-блок под заголовком-якорем,
   взять его строки.

Сверка: значение из спеки обязано **совпасть** с константой сторожа и
**встретиться ровно один раз** среди строковых констант кода. Ровно один, а не
«хотя бы один»: два вхождения означают, что текст начали дублировать, и
следующая правка поправит одно из них.

## 3. Реестр — литеральным списком

В стороже — явная таблица кортежей, а не обход каталога спек:

```
(спека, якорь-заголовок, № фразы в блоке, файл кода, файл сторожа, имя константы)
```

Сегодня в ней две записи (`APPROVED_1`, `APPROVED_2`). Добавить третью — одна
строка.

Обход каталога отвергнут по той же причине, что и всегда: выведенный список
согласен с реализацией по определению и молчит там, где о фразе забыли. Список
пишет человек.

## 4. Fail-closed: сторож обязан краснеть от ОТСУТСТВИЯ

Главная ловушка этого класса — сторож, зелёный по построению. Если спеку
переименуют, якорь поменяют, а константу удалят, наивная реализация «сравнить
то, что нашли» найдёт пустоту и сравнит пустоту с пустотой.

Поэтому **каждое** из трёх извлечений сначала утверждает факт находки, с
отдельным внятным сообщением:

* спека-файла нет / якорь не найден / блок под якорем пуст → красный;
* константы с таким именем в стороже нет → красный;
* фраза не встретилась среди строковых констант кода → красный;
* встретилась дважды → красный.

И парный сторож на самого себя: подсунуть временную копию реестра с заведомо
несуществующим якорем и убедиться, что проверка **падает**. Иначе мы завели
сторожа, который не умеет краснеть.

## 5. Кодировка — не мелочь

Все три файла читать **явно** `encoding='utf-8'` (для `.md` и `.py`;
`utf-8-sig` не годится — BOM в `.py` запрещён). Сравнение вести значениями, а
не через печать: консоль здесь cp1251, и она уже однажды сделала пойманную
мутацию слепой — «И» не пережила байт `0x98`. Сообщение об ошибке обязано
показывать `repr()` обеих сторон, чтобы расхождение в невидимом символе (nbsp,
другой апостроф) было видно глазом.

## 6. Границы

* Сторож НЕ правит текст и НЕ предлагает правку. Он только фиксирует
  расхождение. Менять одобренный текст по-прежнему может только слово
  владельца.
* Пока — только модалка `stop_all`. Расширять реестр на другие согласованные
  тексты можно потом, отдельным решением.
* Мутационный гейт: мишень — новый файл сторожа; мутация обязана краснеть
  ровно rc 1.
