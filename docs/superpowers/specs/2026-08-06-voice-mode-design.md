## 2. Дефект Д-1: голосовая ветка не зовёт confirm-флоу (правится в Ф0)

**Голосовая ветка не переиспользует confirm-флоу.**

`_route_plain_text` (текст) при `pending_paid` вызывает `_router_paid_confirm` и
показывает кнопку. `_route_voice` (голос) этой ветки **не имеет**: он идёт сразу
в `_render_router_response`, а тот при `pending_paid` с пустым текстом
(`router.py:281-289` не заполняет `text`) молча возвращается —
`_render_router_response` ветка `if getattr(response, "pending_paid", None): return`.

Итог: **сказал голосом «сгенерируй картинку» → бот молчит.** Деньги не тратятся
(fail-closed по факту), но пользователь не получает ничего — ни кнопки, ни
отказа. По нашей дисциплине молчаливый дефолт — класс бага
(см. `jarvis-chatter-drill-p17`).

Второе следствие того же: `reply_with_voice` тоже платный, поэтому просьба
голосом «ответь голосом» уходит в ту же тишину.

Это первый пункт Ф0 и он же — эталонный пример принципа «голос не создаёт
второго контура»: чинить надо не копией конфирма в голосовую ветку, а сведением
обеих веток в один общий постобработчик ответа роутера.

## 3. Архитектура: голос отдельно от мозга

Три слоя, между ними — только данные. Добавление команды не трогает голосовой
цикл; смена STT-вендора не трогает команды.

```
 ┌──────────────────────────── ТРАНСПОРТ (голос) ──────────────────────────┐
 │  вход:  TG voice note │ микрофон ПК (Ф4) │ гарнитура = вход тех же двух  │
 │           │                    │                                        │
 │           ▼                    ▼                                        │
 │     [ активация ]      PTT-кнопка / hotkey / wake-word (локально, CPU)   │
 │           │                                                             │
 │           ▼                                                             │
 │     [ STT-адаптер ]  transcribe.py — батч (заметка) | стрим (разговор)   │
 │           │                                                             │
 │      транскрипт (текст) + метаданные: user_id, канал, длительность       │
 └───────────┼─────────────────────────────────────────────────────────────┘
             │            ← ЕДИНСТВЕННЫЙ интерфейс вниз: строка + кто сказал
 ┌───────────▼──────────── МОЗГ (наш, существующий) ───────────────────────┐
 │  llm_router/router.py — Claude + ToolRegistry. Тот же, что для клавиатуры│
 │  Голос не даёт мозгу ни новых инструментов, ни новых прав.               │
 └───────────┼─────────────────────────────────────────────────────────────┘
             │  намерение = имя инструмента + параметры (структурно)
 ┌───────────▼──────────── ГЕЙТЫ (данные, не промпт) ──────────────────────┐
 │  1) whitelist (кто)   2) политика уровней (что можно ЭТИМ каналом)       │
 │  3) денежный гейт paid/est_usd   4) дневной потолок                      │
 │  Неизвестное действие → уровень 4 → голосом запрещено (fail-closed)      │
 └───────────┼─────────────────────────────────────────────────────────────┘
             │
 ┌───────────▼──────────── ИСПОЛНЕНИЕ (тот же командный слой) ─────────────┐
 │  ToolRegistry-хендлеры / cmd_*-обработчики пульта. Ни одной команды,     │
 │  доступной ТОЛЬКО голосом.                                              │
 └───────────┼─────────────────────────────────────────────────────────────┘
             │  результат (текст + медиа)
 ┌───────────▼──────────── ОТВЕТ ──────────────────────────────────────────┐
 │  всегда текст  +  опционально TTS-адаптер (synthesize.py) → voice note   │
 │  Подтверждения — НИКОГДА не голосом: только кнопка/текст (см. §6)        │
 └─────────────────────────────────────────────────────────────────────────┘
```

Контракт слоёв: транспорт знает про аудио и ничего про инструменты; мозг знает
про инструменты и ничего про аудио; политика — это файл, а не рассуждение
модели.

## 4. Классы действий и уровни

Политика — машиночитаемый файл `config/action_policy.yaml`, **общий** с ярусом 2
автономности (там уже заложены уровни 0–4 с дефолтом fail-closed 4, но самого
файла ещё нет — прогон 06.08 показал «политики нет»). Голос становится первым
реальным потребителем этой таблицы, карточки «Джарвіс пропонує» — вторым.

Уровень — свойство **действия**. Что с ним делать — свойство **канала**:

| Уровень | Голос | Карточки яруса 2 |
|---|---|---|
| 0 — чтение | сразу | сразу |
| 1 — обратимый запуск | сразу + эхо-отчёт «сделал X» | кнопкой |
| 2 — необратимое / прод | одно подтверждение (кнопка) | явный апрув владельца |
| 3 — деньги / клиенты | двойное подтверждение | не предлагать |
| 4 — всё неизвестное | никогда | никогда |

Правила таблицы:

1. **Fail-closed.** Действие без явной строки в политике = 4 = голосом
   запрещено. Ответ честный: «Это голосом не делаю, сделай с пульта».
2. **Уровень — метаданные, не текст.** Как денежный гейт берётся из
   `Tool.paid`, а не из фразы, так и уровень берётся из файла политики по имени
   действия. Никакая формулировка вслух не меняет уровень.
3. **Дороже — значит выше.** Если у действия есть `est_usd > 0`, его уровень не
   может быть ниже 3, даже если строка в политике говорит иначе. Проверяется
   тестом-сторожем.
4. **Одна таблица на все каналы.** Добавили инструмент — обязаны добавить
   строку, иначе он просто недоступен голосом (и это правильно).

## 5. Контракты безопасности

- **К1. Голос не расширяет права.** Голосовой канал использует тот же
  `_whitelist_gate`, тот же `ToolRegistry`, тот же `guard_spend`. Ни одной
  команды «только голосом». Нарушение = новая дыра в обход auth.
- **К2. Один постобработчик ответа.** Текстовая и голосовая ветки обязаны
  проходить через общую функцию рендера ответа роутера (включая `pending_paid`).
  Тест-сторож: голосовой ход с платным инструментом обязан породить ту же
  карточку подтверждения, что и текстовый.
- **К3. Транскрипт — недоверенный ввод.** Всё, что услышал микрофон, — текст от
  пользователя, но не обязательно **от владельца**: рядом может говорить другой
  человек, телевизор, ролик в ленте. Отсюда: чем слабее подтверждение личности
  канала, тем ниже максимальный уровень (см. §7).
- **К4. Подтверждение — сменой модальности.** Опасное действие подтверждается
  не голосом (см. §6).
- **К5. Потолок канала — две ступени (решено 06.08).** Модель «пакет-бар», как
  у клиентов:
  - **30 мин разговора в день — мягкий алерт:** «наговорил на $X, осталось 30
    мин». Ничего не блокируется, но цифра названа вслух — в деньгах, не в
    минутах;
  - **60 мин — жёсткий стоп:** разговорный режим на сегодня закрыт, канал
    деградирует до уровня 0 (читать можно, делать нельзя). Снятие — только
    руками с пульта, не голосом (иначе потолок снимается тем же каналом,
    который его пробил).

  Отдельные счётчики ведутся по всем трём статьям (минуты STT, символы TTS,
  ходы мозга), потому что дороже всего третья (§8), а слышно только первую.
  Счётчик — по дню, cold-start-ходы не выкидываем: правило замера то же, что в
  дриле обязательств.
- **К6. Каждый голосовой ход виден в аудите.** Уже есть `_record_voice_event`;
  добавляется поле «уровень действия» и «чем подтверждено».

## 6. Подтверждения: одно и двойное

**Одно (уровень 2):** существующий флоу — `pending_confirm` + кнопка
`confirm:run` / `confirm:cancel` (`_router_paid_confirm`,
`jarvis_smart_telegram_control.py:11011`). Ничего нового строить не нужно, нужно
только довести до голосовой ветки (§2).

**Двойное (уровень 3):** одно нажатие ≠ два. Двойное = **два независимых
фактора**, а не две одинаковые кнопки подряд:

1. **Смена модальности.** Подтверждение приходит и принимается только текстом/
   кнопкой в Telegram. Голосом подтвердить нельзя — принципиально. Причина: если
   ложное срабатывание породило команду (чужая речь, ТВ, эхо своей же озвучки),
   то тем же каналом придёт и «да».
2. **Явная сумма и объект.** Кнопка показывает `est_usd` и конкретный объект
   («Анимация батча, 12 кадров, ~$0.50»), а подтверждающий тап требует, чтобы
   сумма была прочитана — не «Запустить?», а «Списать ~$0.50?».

Плюс два предохранителя, уже знакомых по деньгам: идемпотентность (повторный тап
не запускает второй раз) и срок жизни подтверждения (протухло — надо повторить
запрос целиком, а не тапнуть по старой карточке).

**Эхо своей озвучки** — отдельный риск в Ф3: бот произносит «запустить генерацию
за $0.50?», микрофон это слышит, STT это распознаёт. Обязателен барьер: пока
играет TTS, вход канала заглушён (half-duplex) или включено эхоподавление.
До Ф3 это неактуально, потому что вход — только явные голосовые заметки.

## 7. Кто говорит: сила подтверждения личности по каналам

| Канал | Кто говорит | Максимальный уровень |
|---|---|---|
| Telegram voice note | `user_id` в апдейте + whitelist — сильная привязка | до 3 (с двойным подтверждением) |
| Микрофон ПК, PTT (hotkey) | физическое присутствие у машины владельца | до 2 |
| Микрофон ПК, wake-word (always-on) | никакой — микрофон слышит всех | 0–1, выше не поднимать |
| Гарнитура | наследует канал, к которому подключена | как у канала |

Это прямое следствие К3 и отвечает на «гарнитура = всегда со мной»: гарнитура
отдельной работы действительно не требует, но её режим always-on снижает потолок
до «читать и запускать обратимое».

## 8. Вендоры и цены

### Выбор

| Роль | Выбор | Цена | Почему |
|---|---|---|---|
| STT, заметки/диктовка (батч) | OpenAI `gpt-4o-mini-transcribe` | ~$0.003/мин | вдвое дешевле нынешнего `whisper-1` ($0.006/мин), ключ уже есть — **ноль новых секретов**; замена = одна строка в `transcribe.py` |
| STT, разговор (стрим) | Deepgram Nova-3 streaming | $0.0077/мин (Growth ~$0.0065) | нужны interim-результаты и endpointing для перебивания; у OpenAI батч-транскрипция этого не даёт |
| TTS, дефолт | OpenAI `gpt-4o-mini-tts` | ~$0.015/мин аудио | ключ уже есть, качество достаточное для служебных ответов |
| TTS, «живой» голос | ElevenLabs Flash v2.5 | $0.05 / 1k символов | если русский голос OpenAI не устроит; низкая задержка (важно только в Ф3) |
| Мозг | наш `llm_router` (Claude) | по факту ходов | требование владельца; чужой speech-to-speech отклонён (ниже) |
| Wake-word | локально (openWakeWord / Porcupine), CPU | $0 | RX570 не нужен: детектор ключевого слова — это не Whisper, он крутится на CPU |

**Отклонено: OpenAI Realtime (speech-to-speech).** `gpt-realtime-2.1` берёт
$32/$64 за 1M аудио-токенов вход/выход; при типичной оценке ~600 аудио-токенов
на минуту речи это ≈$0.019 + $0.038 = **~$0.06/мин** — дороже связки
Deepgram+TTS+наш мозг. Но главная причина не цена: в этой схеме мозгом
становится **их** модель, а наш роутер с `ToolRegistry`, `paid`-гейтом и
политикой уровней выпадает из контура. Это прямо противоречит требованию
«наш роутер как мозг». (Оценка токенов/мин — допущение, отдельным замером
не проверялась.)

**Найденная неточность в коде:** `synthesize.py:25` считает ElevenLabs по
$0.30/1k символов — это в 3–6 раз выше реальной цены ($0.05 Flash / $0.10
Multilingual). Леджер завышает стоимость озвучки. Правится в Ф0 вместе с §2
(та же дисциплина, что и с ставкой записи кэша: цена в коде — это тоже факт,
который может протухнуть).

### Стоимость на реальном использовании

что и с клавиатуры. Голос платит только за транспорт, кроме режима разговора,
где он меняет **число** ходов.

| TTS OpenAI mini | 150 мин × $0.015 | **2.25** |
| TTS ElevenLabs Flash | 120k симв × $0.05/1k | 6.00 |
| **Итого профиль А** | | **≈$2.7 (OpenAI) … $6.5 (ElevenLabs)** |

| STT стрим Deepgram | 600 мин × $0.0077 | 4.62 |
| TTS (бот говорит ~40% времени) | 240 мин × $0.015 | 3.60 |
| **Мозг** — ~3 обмена/мин = 1800 ходов | 1800 × $0.008–0.02 (по замерам chatter с кэшем и без) | **14–36** |
| **Итого профиль Б** | | **≈$22–44** |

Главный вывод по деньгам: **разговор дорог не голосом, а числом ходов мозга** —
на него приходится 65–80% сметы. Отсюда К5 и приёмка Ф3 по деньгам, а не по
«работает».

Потолок К5 в деньгах: мягкий алерт на 30 мин/день ≈ $33–66/мес, жёсткий стоп на
60 мин/день ≈ $66–132/мес — это и есть цена «заболтался». Верхняя граница
сопоставима с полосой $500 в тарифной модели chatter, поэтому потолок здесь не
формальность: без него голос способен съесть маржу одного клиента.

## 9. Ключи и секреты (§12)

- Новые вендорские ключи (`DEEPGRAM_API_KEY`, `ELEVENLABS_API_KEY`) заводятся
  **сразу в `.enc`** через существующий DPAPI-контур
  (`chatter/security/crypto.py`: `encrypt_to_file` / `decrypt_from_file`,
  энтропия отдельным файлом, `restrict_to_system_admins`). В `.env` их не
  класть — иначе мы увеличиваем plaintext-поверхность ровно в тот момент, когда
  хвост O1 этап 2 её сокращает.
- Крипто-модуль сегодня живёт внутри `chatter/`, а голос — в `app/`. Значит в
  Ф0 нужен маленький шаг: вынести чтение секретов в общий модуль (или тонкий
  адаптер), чтобы `app/` не импортировал `chatter/` — нулевая связность
  `chatter ↔ app` это наш действующий контракт.
- `OPENAI_API_KEY` остаётся как есть (он уже используется всей системой);
  голосовой режим его статус не меняет и не блокируется им.
- Ключи не логируются, в транскрипты и аудит не попадают; при недоступном ключе
  — честная ошибка, не тихий no-op (DEV-18).

## 10. Privacy

**Дефолт: активатор, не «всегда слушает».** Совпадает с твоим склонением, и на
телефоне он уже есть бесплатно: голосовая заметка в Telegram — это и есть
push-to-talk, микрофон не слушает фон вообще. На ПК дефолт — hotkey (PTT).
Wake-word появляется только в Ф4, и обязательно **локальный**: в облако уходит
аудио только после срабатывания активатора, до этого ни байта не покидает
машину.

**Где живёт аудио — сегодня проблема.** `_download_telegram_file` кладёт
входящие в `state/incoming_files/`. Механизм уборки существует
(`app/services/garbage_cleanup.py`: всё старше 14 дней), но по умолчанию он
**dry-run** (`GARBAGE_CLEANUP_DRY_RUN` default `true`, `scheduler.py:165`), и по
факту не удаляет: на 06.08 в каталоге 1391 файл, старший — от 09.07, то есть
28 дней, вдвое старше порога. Голосовых там пока 0 (режимом не пользовались).
Если включить голос как есть, каждое сказанное слово ляжет на диск и останется.

Отдельно: 14 дней — это порог для картинок и мусора, для записи речи он
неуместен. Голосу нужна своя, более короткая политика, не общая уборка.

Правила хранения (вводятся в Ф0, до любого расширения):

| Что | Где | Сколько живёт |
|---|---|---|
| Исходное аудио | `state/incoming_files/` | удаляется сразу после успешной транскрипции — своей веткой, не общей уборкой; при ошибке — не дольше 24 ч |
| Транскрипт | аудит-лог + история диалога | как история диалога (уже действующее окно), но не больше 30 дней |
| Аудио ответов (TTS) | не хранится | отправили в Telegram — забыли |
| Стрим разговора (Ф3) | не пишется на диск в принципе | — |

Плюс: транскрипты не попадают в git (каталог уже gitignored — проверить перед
Ф0), в отчётах и панелях показывать не текст, а факт «голосовой ход, N секунд».

### План фаз

Порядок твоей гипотезы поправлен в двух местах (обоснование ниже).

**Ф0 — границы и правда о том, что уже есть.** Риск: низкий, новых возможностей
ноль. Содержание: (а) **Д-1** — фикс молчаливого no-op через **общий**
постобработчик ответа роутера; (б) политика `config/action_policy.yaml` +
применение уровня к голосовому каналу (пока таблица = только уровень 0, всё
остальное запрещено); (в) **Д-3** — ретенция аудио своей веткой (§10);
(г) переезд ключей на `.enc`-контур и общий адаптер секретов; (д) **Д-2** —
фикс цены ElevenLabs в леджере. **Приёмка:** живой смоук — одна
голосовая заметка «покажи расходы» → ответ; одна голосовая «сгенерируй картинку»
→ честный отказ с указанием, где это делается, а не тишина.

**Ф1 — безопасные команды (уровни 0–1) + диктовка.** Риск: низкий, всё
обратимо. Уровни 0–1 таблицы §4 открываются голосом; уровень 1 обязан отдавать
эхо-отчёт «сделал X». Диктовка длинной мысли в текст/черновик — сюда же, она по
природе уровень 1. **Приёмка:** неделя обычного использования, ноль действий
уровня ≥2, счётчик отказов по fail-closed не растёт молча (каждый отказ виден).

**Ф2 — опасное через подтверждение (уровни 2–3).** Риск: средний. Одно
подтверждение для уровня 2, двойное по §6 для уровня 3. Голосовое подтверждение
запрещено кодом, не соглашением. **Приёмка:** дрил — голосом запросить платную
генерацию, увидеть карточку с суммой, тапнуть, увидеть списание ровно один раз;
затем повторить тап и убедиться, что второго списания нет.

**Ф3 — real-time разговор с перебиванием.** Риск: высокий (новый вендор, новый
секрет, стриминг, барджин, эхо своей озвучки, деньги за ходы мозга). Только
после Ф2. Обязательно: потолок по К5 (мягкий алерт 30 мин, жёсткий стоп 60),
half-duplex или эхоподавление, кнопка «стоп» вне голосового канала. **Приёмка:** замер денег за 3 дня против
сметы §8 (профиль Б), как в дриле Д-10.

**Ф4 — ПК-микрофон, гарнитура, always-on.** Риск: высокий по приватности.
**Гейт входа: Д-3 закрыт фактом** (аудио реально удаляется, проверено не кодом,
а пересчётом файлов в каталоге). Локальный wake-word, потолок уровня по §7
(always-on = максимум 1), явный индикатор «слушаю». **Приёмка:** дрил на ложное срабатывание — включить рядом
видео с речью и убедиться, что ни одно действие уровня ≥2 не стартовало.

### Что поменяно против твоей гипотезы и почему

1. **Ф0 — это не «доказать конвейер», а «поставить границы».** Конвейер уже
   доказан (он в проде-коде), а вот «ноль риска» сегодня неверно: голосовая
   ветка уже ходит в роутер, где есть платные инструменты. Сейчас её спасает
   случайность (тихий no-op), а не замысел. Границы должны быть первыми.
2. **Опасные действия (был Ф3) — перед real-time (был Ф2).** Конфирм-контур
   дешёвый, текстовый и почти готов; real-time — самая дорогая и сложная часть
   с новым вендором и новым классом рисков (эхо, барджин, поток денег). Строить
   разговорный режим раньше, чем существует контур подтверждений, значит держать
   самый быстрый канал команд без тормозов дольше, чем необходимо.
3. **Озвучка ответа ≠ real-time.** Простая озвучка (`JARVIS_VOICE_REPLY_ENABLED`,
   `reply_with_voice`) уже есть и включается флагом хоть в Ф1 — она не требует
   стриминга. В Ф3 остаётся именно *разговор с перебиванием*.

## 12. Где я расхожусь с брифом

1. **Отправка сообщения живому клиенту от имени персоны — РЕШЕНО 06.08 в пользу
   более строгого варианта.** В брифе было одно подтверждение; принято:
   **уровень 3 (двойное) в общем случае, на chatter-проде — 4, голосом
   запрещено вообще.** Формулировка владельца: «живому клиенту от имени персоны
   голосом нельзя — необратимо, публично, чужая репутация; ответ клиенту только
   руками, глядя на текст».

   Отсюда контракт, который проверяется тестом: голосовой канал не имеет доступа
   к отправляющим действиям chatter ни при каком подтверждении. Это не настройка
   и не уровень в файле политики, который можно поднять, — это отдельная
   проверка «канал == голос → отказ» перед исполнением.
2. **«Создание — свободно голосом».** Согласен только для черновиков и записей.
   Генерация изображения/видео — тоже «создание», но это деньги, поэтому она
   в уровне 3. В таблице §4 это разведено явно.

## 13. Чего в этой спеке намеренно нет

- локального STT/TTS (RX570 без ROCm — решено, стек облачный);
