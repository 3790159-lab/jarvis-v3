## 1. Проблема

Сегодня «что бот должен лиду» живёт только двумя лоссовыми носителями:

1. **Проза профиля** (`contact_profile.text`, ≤250 ток) — классификатор пересобирает её каждый ход и **прямо инструктирован выбрасывать закрытые вопросы первыми**. Открытое обязательство (обещан бриф/примеры/пересчёт) — ровно тот «висящий вопрос», который сжатие теряет.
2. **Окно истории** (`select_window`, 1700 ток / 40 сообщений) — верно ровно до тех пор, пока ход, где обязательство возникло/закрылось, не уехал за хвост.

**Сценарий, который спека ОБЯЗАНА закрыть:** обязательство старше окна. Через неделю диалога ход с брифом уезжает за 24-сообщенное окно, в прозе его уже сжали — и компенсировать нечем. Сегодня спасло, что закрытие было в окне (msg 203). Это удача, не гарантия.

## 2. Цель / не-цели

**Цель:** структурный, НЕ прозаический слот в памяти лида, который переживает и сжатие, и уезд за окно; носит статус каждого обязательства и критерий закрытия по ВЫПОЛНЕНИЮ ФУНКЦИИ; brain обязан отработать открытое обязательство раньше эскалации; фундамент фоллоу-апа (бот, пишущий первым, должен знать, что висит).

**Не-цели (в этой арке):** сам фоллоу-ап (бот пишет первым) — отдельная ветка; UI пульта под обязательства; авто-напоминания. Слот — только носитель состояния.

## 3. Модель данных

Отдельная структурная таблица (НЕ поле в прозе, НЕ часть `contact_profile.text`):

```sql
CREATE TABLE IF NOT EXISTS contact_obligations (
    contact_id     TEXT NOT NULL,
    okey           TEXT NOT NULL,   -- ключ обязательства: kind (+ slug для 'other')
    kind           TEXT NOT NULL,   -- brief | examples | recalc | owner_write | other
    owed_by        TEXT NOT NULL,   -- bot | client
    status         TEXT NOT NULL,   -- open | delivered | cancelled
    detail         TEXT NOT NULL,   -- короткая человекочитаемая строка
    created_msg_id INTEGER,         -- id сообщения, где возникло
    closed_msg_id  INTEGER,         -- id сообщения, где закрылось (delivered/cancelled)
    created_ts     REAL NOT NULL,
    closed_ts      REAL,
    PRIMARY KEY (contact_id, okey)
);
```

- **Один активный ключ на (contact_id, okey)**. `okey = kind` для перечисленных видов (два открытых «brief» одновременно бессмысленны), `okey = "other:" + slug` для kind=other. Апсерт по ключу: модель сообщает желаемый статус, код делает переход и штампует msg_id/ts.
- **`created_msg_id`/`closed_msg_id` штампует КОД, не модель.** Модель ненадёжно знает id сообщений; при возникновении обязательства store ставит `created_msg_id = MAX(messages.id)` для контакта на этот ход, при закрытии — `closed_msg_id`. Так линковка детерминирована и аудируема.
- **Слот НЕ версионируется как профиль** — это живой набор строк с переходами статусов. История переходов сохраняется самими полями created/closed (msg_id + ts).

### Виды обязательств (kind) и КРИТЕРИЙ ЗАКРЫТИЯ по функции

Ключевой принцип (прецедент дрила): закрыто по ВЫПОЛНЕНИЮ ФУНКЦИИ, не по упоминанию слова.

| kind | Возникает | `delivered` когда (функция выполнена) | `cancelled` когда |
|---|---|---|---|
| `brief` | персона обещала/лид просил бриф | заданы квалифицирующие вопросы по существу (сфера/обсяг/стиль/символ-vs-текст/референси) — НЕ когда сказано слово «бриф» | лид отказался/тема закрыта |
| `examples` | обещаны примеры работ | дана ссылка на портфоліо/Upwork | — |
| `recalc` | обещан пересчёт под задачу | названа сумма ИЛИ запрос зафиксирован + карточка керівниці выставлена | лид передумал |
| `owner_write` | обещано «керівниця напише» | **карточка эскалации доставлена владельцу** (часть бота выполнена; сам факт письма — вне системы, человек) | эскалация снята |
| `other` | прочее явное обещание | по описанию в detail (модель формулирует критерий) | — |

**Критерий закрытия — в спеке намеренно per-kind и функциональный**, а не строковый матч. Решение о `delivered` принимает КЛАССИФИКАТОР (он видит окно + новый ход и оценивает, выполнена ли функция). owner_write помечаем `delivered` по факту доставленной карточки (детерминированный сигнал `console_cards`/H2-гейт из `run.py`), не по слову.

**Известное ограничение MVP (owner_write):** «карточка доставлена» ≠ «владелец написал». Сценарий «карточка ушла владельцу, человек молчит, лид ждёт» MVP пометит долг `delivered` по факту карточки — с точки зрения бота обязательство закрыто, хотя лид первого письма ещё не получил. Тем более после `/resume` (владелец разгрёб паузу) бот считает owner_write закрытым. Это осознанный компромисс MVP; истинное закрытие — по факту РУЧНОГО исходящего владельца → бэклог v2 (§13).

**CONTRACT T1 (добавлено 2026-07-24 по итогам дрила Д-10): `owed_by` для `brief`/`examples`/`recalc` — ИНВАРИАНТ КОДА, не поле выбора модели.** Эти виды всегда `owed_by=bot`: клиент лишь ПОСТАВЛЯЕТ материал (референси/фото), но обязательство ПРОВЕСТИ бриф / дать примеры / пересчитать лежит на боте. Гарантия — в коде (`obligations_slot.filter_model_updates` нормализует что бы модель ни прислала → `bot`; множество видов = `CODE_BOT_OWNED_KINDS`), а НЕ в промпте: `owed_by` убран из JSON-схемы классификатора (§4). Мотив — реализовавшийся риск §12: на живом Д-10 классификатор прислал `owed_by=client` для брифа → `render_slot_block` (только `owed_by=bot`) вернул пусто → `obl=n=1`, но в brain обязательство не инъектилось. Метрика §8 разделена (`n=` все / `renderable=` только bot-owed open), чтобы «посчитано» ≠ «доедет до модели». Ретро-данные чинит `scripts/normalize_obligations_owed_by.py`.

**CONTRACT T2 (добавлено 2026-07-24 по итогам дрила Д-10 T2): обязательство закрывается по ВЫПОЛНЕНИЮ ФУНКЦИИ, и ожидание материала от клиента — НЕ открытый долг бота.** Квалифицирующие вопросы ЗАДАНЫ → `brief` = `delivered`, даже если лид ещё ничего не прислал: функция бота (провести бриф) выполнена, дальше ход клиента. Держать `open` «в ожидании материалов» запрещено — иначе долг не закрывается никогда и бот на каждом ходу дожимает уже отданное (ровно та реплика-повтор, которую слот призван убрать). Критерий несёт промпт классификатора (явная формулировка + анти-пример), потому что это семантическое судейство; **детерминированный бэкстоп — в коде**: `merge_obligations` не создаёт новый `other`, пока открыт канонический долг того же смысла (`brief`/`examples`/`recalc`/`owner_write`), иначе живая модель фрагментирует один долг на клоны и выбирает cap ≤5. Мотив — реализовавшийся дефект Д-10 T2: `brief` висел `open` при заданных вопросах + рядом плодилось дублирующее `other` про то же уточнение. Ретро-данные чинит `scripts/cleanup_duplicate_other_obligations.py`. Живая валидация: повтор T2 (msg 241) закрыл `brief` `delivered`/`closed_msg_id=241`; на T4 бот не переспросил. Прецедент в памяти: `jarvis-obligation-closed-by-function`.

**CONTRACT T4 (добавлено 2026-07-24 по итогам дрила Д-10 T4): весь жизненный цикл `owner_write` ПОСЛЕ создания ведёт ТОЛЬКО КОД.** Модель может лишь СОЗДАТЬ первую строку (`open`, когда её ещё нет — «керівниця напише»); дальше любой её апдейт по `owner_write` отбрасывается `filter_model_updates`: `delivered`/`cancelled` — всегда (закрытие детерминировано карточкой), а `open` — если строка `owner_write` уже существует (в любом статусе). Мотив — реализовавшийся баг T4: пока платёжный контекст висит в окне истории, классификатор на КАЖДОМ последующем ходу заново эмитит `owner_write open`; без этого гарда `merge_obligations` трактует его как «переобещали» и сбрасывает `closed_msg_id`/`closed_ts` (строки 130-134) → code-доставленный `owner_write` (T3, `closed_msg_id`=id карточки) тихо переоткрывается, и на следующем ходу `renderable=1` → ложная повторная передача керівниці. `merge` при этом остаётся чистой механикой без политики владения — политику несёт `filter_model_updates` (модель) и `_close_owner_write_by_card` (код). Симметрично: повторная ЛЕГИТИМНАЯ эскалация (лид через неделю снова про оплату) не запирается — `_close_owner_write_by_card` авторитетно перештамповывает `closed_*` на НОВУЮ карточку (в обход idempotency `merge`, которая бережёт первое закрытие для классификатор-ведомых `brief`/`examples`/`recalc`). Регрессии держат `test_obligations_slot`/`test_obligations_wiring` (T3→T4 не трогает строку; новая карточка обновляет `closed_msg_id`).

## 4. Поток обновления (через тот же classifier JSON)

Расширяем существующий `ClassifierResult` (`classifier.py`), НЕ добавляем второй LLM-вызов (требование Даниила):

```jsonc
{
  "escalate": false,
  "reason": "",
  "stage_signal": "engaged",
  "profile": "…сжатая проза ≤250 ток…",
  "obligations": [                      // НОВОЕ; пусто → нет изменений
    {"kind": "brief", "owed_by": "bot", "status": "delivered", "detail": "квал. вопросы задані"},
    {"kind": "recalc", "owed_by": "bot", "status": "open", "detail": "порахувати під ребрендинг"}
  ]
}
```

- Классификатор получает в промпт ТЕКУЩИЕ открытые обязательства (рендер из таблицы) + правило закрытия по функции, и возвращает актуальный статус по каждому активному виду.
- **Слот НЕ сжимается.** Сжимается только `profile` (проза, ≤ budget). Обязательства — маленький ограниченный по числу массив, отдельная ось; правило вытеснения профиля на него НЕ распространяется. Явно прописать в промпте классификатора: «obligations — отдельный структурный список, его НЕ ужимай и НЕ выбрасывай при сжатии профиля».
- **Применение под тем же guard, что профиль** (`run.py:238-266`, `if cr is not None and not cr.degraded`): деградировавший/битый классификатор **НЕ трогает** обязательства (не создаёт и не закрывает). Мусорный ход не имеет права стереть долг. На degraded — обязательства остаются как были + `profile_miss`/алерт как сейчас.
- **Порядок:** brain-реплика генерится ДО классификатора (как сейчас), т.е. видит обязательства ПРЕДЫДУЩЕГО хода (персистентные). Обязательство, созданное/закрытое ЭТИМ ходом, отражается следующим — консистентно с поведением профиля.

## 5. Инъекция в system-промпт brain

Отдельный детерминированный блок, рендерится из ОТКРЫТЫХ (status=open, owed_by=bot) строк таблицы:

```
=== ВІДКРИТІ ЗОБОВ'ЯЗАННЯ (відпрацювати ПЕРЕД хендоффом) ===
- бриф: обіцяний, ще не відданий — задати квал. питання
- пересчёт: обіцяний під ребрендинг

=== ЗАКРИТО НЕДАВНО (НЕ повторювати) ===
- бриф ✓ — квал. питання вже задані
```

- Блок в **uncached suffix** рядом с профилем (`brain.py:131-136`) — как профиль, платится full каждый ход (см. стоимость §7).
- **Рендер из таблицы, не из окна** → обязательство доезжает до brain, даже если ход-источник уехал за окно 24 сообщений. **Это и есть решение проблемы §1.**
- **Секция «ЗАКРИТО НЕДАВНО» (решение 7, в MVP):** `delivered` за последние 7 дней рендерятся отдельным под-блоком с пометкой ✓. Это **симметричное закрытие §1**: когда закрытие уедет за окно, а проза его сожмёт, brain без этой секции переспросит уже отданный бриф (повтор вопросов был багом дрила 2026-07-23). Тот же cap ≤5, те же компактные ключи; тянется из таблицы (`status=delivered AND closed_ts >= now-7д`).
- Проза playbook (в) уже говорит «відпрацювати відкрите зобов'язання перед хендоффом» — правим её ссылкой на этот блок (минорная правка `playbook.md`: «див. блок ВІДКРИТІ ЗОБОВ'ЯЗАННЯ / ЗАКРИТО НЕДАВНО»), чтобы brain опирался на структуру, а не на прозу профиля.
- Cap: инжектим ≤5 открытых bot-обязательств + ≤5 недавно-delivered, detail ≤ ~80 симв. Переполнение (маловероятно) — лог + показываем 5 старейших открытых / 5 свежайших закрытых.

## 6. Совместимость с lossy-сжатием (явно)

- Проза профиля продолжает сжиматься ≤250 ток и терять «закрытые вопросы» — это ОК, потому что открытые обязательства теперь несёт слот.
- Слот — единственный носитель, не подверженный ни сжатию профиля, ни окну. Инвариант: **обязательство исчезает из промпта brain ТОЛЬКО через явный переход delivered/cancelled**, никогда — «молча выпало при сжатии».

## 7. Стоимость: оценка дельты токенов/$

Базлайн (со слов Даниила): **$0.31/диалог** (с кэшем; ≈20 ходов при текущем расходе — прикидка из `llm_usage`). Слот платится full (uncached, как профиль). Что добавляется на ход:

| Компонент | ~ток/ход (типично 1–2 откр.) | худший (5 откр.) |
|---|---|---|
| brain input (+ блок) | +40–70 | +130 |
| classifier input (видит обязательства) | +40–90 | +130 |
| classifier output (JSON obligations) | +60–120 | +250 |

Грубо при $3/$15 за M (стандарт; до 31.08 промо +50%):
- типично: input ~+130 ток·$3/M + output ~+90 ток·$15/M ≈ **$0.0018/ход** → при 20 ходах ≈ **+$0.035/диалог (~+11%)**;
- реалистично обязательств чаще 0–1 → **~+5–8%**;
- патология (5 открытых КАЖДЫЙ ход) ≈ +$0.08/диалог (~+25%), крайне маловероятно.

**Секция «ЗАКРИТО НЕДАВНО» (решение 7)** добавляет ещё ≤5 компактных строк в **brain input** и **не трогает output классификатора** (delivered тянется из таблицы детерминированно, модель их не переэмитит) → маржинальна к оценке выше (+~30–60 ток input/ход, output не растёт).

**Главный лишний расход — output классификатора (JSON, $15/M).** Рычаги: cap ≤5, компактные ключи, не эмитить `obligations` когда изменений нет (пусто). **Точную дельту МЕРЯЕМ** через §8 (llm_usage до/после) на приёмке — замер включает обе секции (открытые + недавно-закрытые); мерж гейтим порогом **≤ +10% СУММАРНО** к $0.31 (renegotiable).

## 8. Логирование system-промпта (приёмочный инструмент арки)

Не отдельная задача — приёмка слота обязана ПОКАЗАТЬ собранный промпт с содержимым слота.

- **Всегда (prod-safe):** одна структурная строка на каждую генерацию — теги блоков + их длины (симв/≈ток) + sha256 всего system + `obligations: {count, kinds, statuses}`. Без текста ПДн. Пишется в `llm_usage`-смежный лог или новую таблицу `prompt_shape`.
- **Полный дамп — ТОЛЬКО по флагу** `CHATTER_PROMPT_DUMP=1` (env, default off): пишет весь собранный system (включая блок обязательств) в отдельный файл-дамп per contact/turn.
- **Обоснование выбора «структура всегда / полный дамп по флагу»:** (1) **ПДн** — полный промпт содержит профиль лида и факты переписки; в always-on логе это утечка (условие Даниила: полный дамп только по явному включению). (2) **Объём** — system ~7–9k ток ≈ 30–40 КБ/ход × десятки ходов = раздувание лога. Флаг даёт видимость на приёмке (включаем, снимаем дамп с блоком обязательств), в проде выключен → только хеш+длины+счётчик.
- Приёмка арки: включить флаг, прогнать сценарий, показать дамп, где виден `=== ВІДКРИТІ ЗОБОВ'ЯЗАННЯ ===` с содержимым.

## 9. Приёмочные критерии

1. Обещание брифа/примеров/пересчёта → строка open/bot в таблице + рендер в блок brain.
2. **Закрытие по функции:** «бриф» произнесён, но квал.вопросы НЕ заданы → остаётся `open`; квал.вопросы заданы → `delivered` (даже без слова «бриф»). Два теста-антипода.
3. **Переживает окно:** обязательство создано на ходе T, всё ещё инжектится в brain на T+25 (за окном 24), хотя проза профиля его потеряла.
4. **Переживает сжатие:** классификатор ужал прозу, слот сохранён полностью.
5. **Degraded не стирает** обязательства.
6. brain отрабатывает открытое обязательство раньше эскалации (интеграция с прозой (в)).
7. Дельта токенов/$ измерена через §8 (обе секции), в пределах порога (≤ +10% цель).

## 13. Бэклог v2 (после MVP)

- **owner_write: закрытие по факту письма владельца, не карточки.** MVP закрывает owner_write по доставленной карточке (§3) — известная дыра «карточка ушла, человек молчит, лид ждёт», плюс `/resume` тоже трактуется как закрытие. v2: детерминированный сигнал — РУЧНОЕ исходящее владельца из `pause.py` (`on_human_takeover` / `last_human_out_ts`): owner_write → `delivered` только когда владелец реально написал лиду. Это снимает расхождение «бот считает долг закрытым ≠ лид получил письмо».

- **Клиентские долги (client-owed) — отдельный слой, питающий follow-up.** На дриле Д-10 T2 (2026-07-24) классификатор упорно моделировал «клиент должен прислать референси/материал» как обязательство. В MVP-слоте это подавлено (owed_by пинится bot для brief/examples/recalc; ожидание материала НЕ пишем — §3 CONTRACT). Но инстинкт модели указал на **реальную будущую фичу**: client-owed долги («прислать бриф/референси/лого/фото») — это отдельные записи, которые НЕ рендерятся в bot-секцию brain (бот их не «отрабатывает»), но питают **chatter-followup** — проактивное «нагадати про матеріали», если клиент замолчал, не прислав обещанное. Не в этом слоте: слот brain = «что должен БОТ перед хендоффом»; client-owed = «чего ждём от лида» для реактивации. Связать с веткой `chatter-followup` (память `jarvis-chatter-followup-arc`).
