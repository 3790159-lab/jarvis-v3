## 1. Проблема (фактом, вчерашние прогоны)

`accept_generic` в `app/handlers/vizir_task_handler.py` принимает как ✅ всё, что
`completed` + непустой `final_response`. Она НЕ проверяет, СДЕЛАНА ли задача:

- **task-3** «проанализируй проект Jarvis V3 + 5 советов» → Hermes вернул **«Не могу найти
  проект автоматически. Пожалуйста, укажите путь к папке проекта…»** → принято ✅ (задача
  не сделана — агент попросил ввод и встал).
- **task-4** «сделай простую веб-игру крестики-нолики» → Hermes вернул текст **«Готово!
  Игра создана по адресу `C:\Users\Admin\Desktop\tictactoe\index.html`. Просто открой
  этот файл в браузере.»** → принято ✅. Проверено фактом: file-тулсет у Hermes ВЫКЛЮЧЕН
  (`disabled_toolsets=[…,"file",…]`) → файла на диске НЕТ (десктоп пуст, `*tictactoe*` не
  найден) → Hermes **галлюцинировал** запись; кода игры в ответе НЕТ — только описание.

Оба ответа — текст. **task-2** «что ты умеешь?» → тоже текст, но легитимный (self-contained
ответ на вопрос — список способностей инлайн). Ядро задачи: отличить легитимный текст-ответ
от текста-вранья, **не** зная заранее intent произвольной `/task`.

## 2. Цель

Приёмка, ловящая структурные галлюцинации/пустышки → **честная эскалация вместо лживого ✅**,
при этом: НЕ ломает легитимные текст-ответы (task-2 проходит); для задач «сделай артефакт»
требует РЕАЛЬНЫЙ артефакт (task-4 требует код); $0, детерминированно, воспроизводимо
(в духе арки — `hermes_acceptance` тоже детерминированная со спай-зубами мутацией);
переиспользует существующую loop-машину (reject → впрыск фидбека → retry → стоп).

## 3. Ключевой дискриминатор (честно)

По содержанию текст-от-текста без знания intent'а не отличить. Надёжный структурный сигнал,
не требующий ни платного судьи, ни классификации задачи:

- **Легитимный ответ** = результат доставлен ИНЛАЙН; сам ответ и есть результат.
- **Галлюцинация** = ответ = УКАЗАТЕЛЬ / ОБЕЩАНИЕ / ОТСРОЧКА результата, который «где-то
  ещё» («готово, открой файл `C:\…`», «сохранил в…», «не могу, укажите путь»), ЛИБО проза
  О коде вместо самого кода.

**Честное ограничение (принято Daniil):** детерминированно ловится **структурный** класс
(указатель/отсрочка/пустышка/«код словами»). **Семантическую** неправоту (5 правдоподобных,
но выдуманных советов без чтения проекта) v1 не поймает — для неё честная эскалация +
человек в петле (Daniil проверяет). Если станет реальной проблемой → добавим судью
ОТДЕЛЬНО, флагом off-по-умолчанию (§8). Не претендуем ловить любую неправоту — чиним ровно
тот класс, что укусил.

## 4. СЛОЙ 1 — детектор указателя/отсрочки (универсальный, RU+EN, case-insensitive)

Работает на `final_response` (иначе `artifact_path`-контенте). Две независимые под-проверки;
собираем ВСЕ причины (не короткое замыкание) для точного фидбека retry.

### 4.1 Под-проверка 1a — «отсрочка-на-локацию» (co-occurrence, НЕ одиночный маркер)

Срабатывает, только когда **completion-токен СО-ВСТРЕЧАЕТСЯ с external-location-токеном** —
именно паттерн «Готово! …создана по адресу C:\…». Одиночный токен НЕ триггер (см. §6 ложные
срабатывания).

- **completion-токены:** `готово`, `создан`, `создана`, `создал`, `сохран` (сохранил/
  сохранён), `записал`, `сделал`, `done`, `created`, `saved`, `generated`, `ready`, `built`.
- **external-location-токены:**
  - путь-паттерны (regex): диск-буква `[A-Za-z]:[\\/]…`, POSIX-абсолют `/home/`, `/root/`,
    `/mnt/`, `/tmp/`, `~/`;
  - фразы-локации: `по адресу`, `по пути`, `файл находится`, `файл на`, `на рабочем столе`,
    `открой этот файл`, `открой файл`, `открой в браузере`, `saved to`, `saved at`,
    `file is located`, `located at`, `created at`, `open the file`, `open this file`.

→ reason (actionable): **«вернул ссылку/путь на файл вместо самого результата — верни
полный артефакт (код) прямо в ответе, не ссылку и не описание»**. Ловит task-4.

### 4.2 Под-проверка 1b — «уточнение/невозможность» (одиночный токен = триггер)

Агент не сделал задачу, а попросил ввод / признал невозможность.

- **токены:** `не могу найти`, `не удалось найти`, `не могу определить`, `укажите путь`,
  `укажите папку`, `укажите где`, `предоставьте доступ`, `предоставьте путь`, `куда сохранить`,
  `где находится`, `уточните`, `пожалуйста, укажите`, `please provide`, `please specify`,
  `could not find`, `couldn't find`, `unable to locate`, `where is`, `where should i`,
  `provide the path`.

→ reason: **«задача не выполнена: агент попросил ввод / не смог продолжить вместо результата»**.
Ловит task-3.

**Почему две разные семантики триггера:** 1a — «ложное готово» — опасно только в паре
completion+location (иначе легит-ответ, упомянувший путь в примере кода, ловился бы зря).
1b — «прямой отказ/вопрос» — самодостаточный сигнал незавершённости, одиночного токена
достаточно, ложных мало (легит-ответ редко содержит «не могу найти проект, укажите путь»).

## 5. СЛОЙ 2 — артефакт-задача → ответ должен СОДЕРЖАТЬ реальный код

### 5.1 Как понять, что задача просит артефакт-код (из `goal`)

build-intent = (**build-глагол** И **artifact-существительное**), case-insensitive,
по основам слов (RU-словоформы):

- **build-глаголы:** `сдела`, `созда`, `напиши`, `сгенерир`, `свёрстай`/`сверстай`,
  `собери`, `запили`, `build`, `make`, `create`, `write`, `generate`, `code`, `implement`.
- **artifact-существительные:** `игр` (игра/игру), `сайт`, `страниц`, `html`, `css`,
  `скрипт`, `код`, `приложени`, `компонент`, `виджет`, `форм`, `калькулятор`, `таблиц`,
  `бот`, `лендинг`, `game`, `app`, `page`, `site`, `script`, `component`, `widget`, `form`,
  `landing`, `file`.

Если обе категории присутствуют в `goal` → **build-task** (Слой 2 применяется).
Иначе (`что умеешь`, `объясни`, `расскажи`, `посоветуй`, `проанализируй … советы`) → НЕ
build-task → Слой 2 ПРОПУСКАЕТСЯ → ответ проходит на тексте (при чистом Слое 1).

Примечание: task-3 «проанализируй … сделай 5 советов» содержит «сделай», но НЕ содержит
artifact-существительного (совет — не артефакт-код) → НЕ build-task → Слой 2 не бьёт;
task-3 ловится Слоем 1b («не могу найти … укажите путь»). Дизайн когерентен.

### 5.2 Проверка наличия реального кода (для build-task)

Ответ должен содержать хотя бы один **код-маркер** (регэкспы/подстроки, case-insensitive):

- `<html`, `<!doctype html`, `<script`, `<style`, `<body`, `<div`, `</` (закрывающий тег);
- `function `, `def `, `class `, `=>`, `const `, `let `, `var `, `import `, `return `;
- код-fence с телом: ` ``` ` … непустое … ` ``` `.

Если build-task и НИ ОДНОГО код-маркера → reason: **«вернул описание/текст вместо реального
кода — верни сам артефакт (полный код) инлайн в ответе»**.

task-4 «сделай веб-игру» = build-task (сделай+игр), ответ = проза без `<html>/<script>` →
ловится и Слоем 1a (pointer), и Слоем 2 (нет кода) — двойное покрытие.

## 6. Ложные срабатывания — честный разбор

- **«файл» само по себе НЕ триггер.** task-2 «что умеешь» содержит «Читать, создавать и
  редактировать файлы» — нет completion+location пары, нет 1b-токенов → проходит.
- **Легит-ответ с путём в ПРИМЕРЕ кода** (напр. вопрос «как открыть файл в питоне» →
  ответ с `open('C:\\x.txt')`). Риск для 1a. Смягчение: 1a требует completion-токен
  (`готово`/`создан`/…) РЯДОМ (в том же ответе) с путём — примеры кода обычно без «готово,
  создано по адресу». Остаточный риск принят: такой ответ И ТАК содержит код → если это
  build-task, Слой 2 его пропустит, а 1a даст reason → retry с фидбегом «верни артефакт
  инлайн»; для не-build вопроса «как открыть файл» completion+path пары почти не бывает.
  Помечаем как известный edge; спай-зуб C сторожит легит-регресс.
- **Легит-ответ, объясняющий про сохранение файлов** (текстовый how-to) — может содержать
  «сохрани в C:\…». Если это НЕ build-task и completion-токена нет — проходит. Если фраза
  реально выглядит как «готово, сохранил в C:\…» — 1a сработает; но такой ответ на
  вопрос-объяснение маловероятен. Приоритет: лучше ложно зареджектить редкий пограничный
  текст (→ retry, +1 попытка, честно) чем принять галлюцинацию. Асимметрия осознанная.
- **1b на легит-тексте:** легит-ответ крайне редко содержит «не могу найти проект, укажите
  путь» — это сигнатура именно незавершённости. Ложных ≈ 0.

Принцип асимметрии: **ложный reject (лишний retry) дешевле ложного accept (враньё юзеру)**.
Слои настроены консервативно в сторону честности, но с co-occurrence-защитой от очевидного
перелова легита.

## 7. Что при детекте пустышки/галлюцинации: retry vs эскалация

**Выбор: reject → retry с направленным фидбеком (переиспускаем loop-машину), НЕ мгновенная
эскалация.** Честнее: даём Hermes шанс исправиться (он реально может вернуть код инлайн на
2-й попытке — как в живом loop с API_URL). Механика (0 изменений в loop):

`accept_task` → `AcceptanceResult(accepted=False, reasons=[…])` → loop `_compose_prompt`
дописывает `[FEEDBACK] Предыдущая попытка провалила проверки: <reasons>. Исправь их,
остальное сохрани.` в СЛЕДУЮЩИЙ промт (immutable база сохраняется). reasons сформулированы
ACTIONABLE («верни сам артефакт инлайн, не ссылку/описание»), чтобы retry сходился.

Ограничители (существующие, не трогаем): `max_attempts` (кап попыток), `stopped_stalled`
(идентичные reasons два витка → стоп), budget-кап (reserve-before-attempt). Если Hermes не
исправился → честная эскалация (`needs_escalation=True`, `⚠️ Задача не завершена…`). Итог:
retry даёт шанс, но не бесконечно — детерминированные зубы бьют.

## 8. Деньги (честная граница)

- **✅-метка:** ПОЛНОСТЬЮ чинится — галлюцинация reject → не `accepted` → нет ✅, вместо
  него честная эскалация. Главный ask Daniil закрыт.
- **Финализация успеха:** когда `record_cost` подключат (отдельный хвост, НЕ в этой арке),
  charge-after-success уже устроен так, что финализируется только `accepted`-ветка
  (`rep.accepted` в handler). Reject → эскалация → артефакт НЕ пишется, ✅ НЕ шлётся.
- **$ за уже-сделанную попытку:** честно — Hermes УЖЕ сжёг токены, произведя галлюцинацию
  (coordinator списывает за успешный step ДО приёмки). Reject не рефандит. Ограничитель —
  loop budget-кап на весь цикл. Заявляем честно: предотвращаем ЛОЖНЫЙ ✅ и ложный артефакт;
  стоимость галлюцинированной попытки не возвращаем, её бьёт budget-кап.
