# Спека: Б4-хвост (D2/P4) — epoch-отмена устаревшего ответа при свежем входящем

Статус: **на согласование Даниила, кода нет.**
Ветка реализации: `fix/drill1-findings`.

## Факт проблемы (по коду, не по памяти)

- `ChatDebouncer._run` (telethon_run.py:480): флаш батча → `_on_ready` →
  `process_batch` в worker-потоке → доставка бабблов с паузами хуманайзера
  (десятки секунд, до ~90с).
- Входящие ВО ВРЕМЯ доставки: `add()` копит их в `self._buffer` (таск не done
  → новый не заводится), после доставки та же итерация `while True` сливает
  буфер следующим батчем. Слив есть — **отмены нет**: остаток бабблов
  устаревшего ответа уходит ПОСЛЕ новой реплики лида.
- Единственная mid-reply отмена сегодня — `_muted_now` перед каждым `Say`
  (run.py:536): ловит человеческий перехват, НЕ новую реплику.
- Форензика дрила 1 (18:22–18:34): реального пересечения не случилось (лид
  отвечал через 0.11–0.17с ПОСЛЕ последнего баббла), повтор вопроса про
  «окремий знак чи текстовий» — не Б4 (контекст был полный). Но сценарий
  «лід передумав, а вона досилає три бабли з розрахунком» остаётся MAJOR
  (P4): для продукта «неотличима от человека» это самый видимый провал.

## Решение: epoch-check на дебаунсере

### 1. Счётчик поколений — внутри `ChatDebouncer`

- `self._arrived: int = 0`; инкремент в `add()` (loop-поток).
- При флаше батча (`batch, self._buffer = ...`) — снапшот `epoch0 = self._arrived`.
- `fresh_incoming = lambda: self._arrived > epoch0` — замыкание уходит в
  `_on_ready` → `process_batch`.

Почему НЕ таблица `messages` как источник правды: входящее попадает в store
только в `process_batch` СЛЕДУЮЩЕГО батча (run.py:467) — пока новое сообщение
сидит в буфере дебаунсера, БД его не видит. Почему не dict на раннере: у
дебаунсера уже есть per-chat идентичность и точка `add()` — состояние локально,
кросс-модульного стейта не нужно. Threading: int инкремент (loop) / чтение
(worker) атомарны под GIL, локов не надо.

### 2. Прокидка в pipeline

`process_batch(contact_id, batch, transport, deps, *, missed_age_seconds=None,
fresh_incoming: Callable[[], bool] | None = None)`.

`Deps` не трогаем (транспорт-агностика сохранена). `None` (консольный ран,
существующие тесты, catch-up) = поведение прежнее, чек всегда False.

### 3. Точки проверки — рядом с `_muted_now`, перед КАЖДЫМ `Say`

```
elif isinstance(action, H.Say):
    if _muted_now(...): return                      # как сейчас
    if fresh_incoming and fresh_incoming():         # НОВОЕ
        transport.send_typing(False)                # не висеть «печатає»
        deps.store.add_event("stale_reply_cancelled",
                             contact_id=contact_id,
                             detail=f"не відправлено {N} з {M} бабблів")
        return
    transport.send(...); store.add_message(...)     # как сейчас
```

- Свежий входящий пришёл ДО первого `Say` (пока LLM генерил) → выбрасывается
  ВЕСЬ ответ. Стоимость LLM-вызова уже потрачена — принимаем осознанно.
- Свежий входящий между бабблами → отправленная часть остаётся в истории
  (persist на send, run.py:544 — уже так), остаток не уходит.
- Регенерацию НЕ кодим: буфер не пуст → та же итерация `_run` дебаунсера
  запускает новый `process_batch`, история = отправленная часть + новая
  реплика. Модель сама решает, что из недосказанного повторить. Это
  существующий механизм слива — мы только убираем устаревший хвост.

### 4. Что осознанно НЕ делаем

- НЕ прерываем сон внутри `Pause` — чек только на границе перед `Say`.
  Худшее ожидание отмены = одна пауза хуманайзера. Interruptible sleep — вне
  скоупа (усложнение без наблюдаемой пользы).
- НЕ откатываем классификатор/профиль/эскалацию устаревшего хода — факты и
  карточка корректны независимо от того, ушли ли бабблы.
- НЕ отменяем `suppressed_fallback`/safe-ответы — они тоже `Say`, чек общий:
  безопасный ответ лид получит от СЛЕДУЮЩЕЙ генерации, которая видит и его
  вопрос, и новую реплику.
- Catch-up path (`_process_missed`, telethon_run.py:1366) — `fresh_incoming`
  НЕ пробрасываем в первой версии. Там есть отдельная гонка (входящее во время
  catch-up заводит дебаунсер параллельно) — она пре-существующая, не Б4;
  фиксируем в AUDIT как отдельный долг, здесь скоуп не раздуваем.

### 5. Наблюдаемость (DEV-18 + урок «0 targets»)

- `control_events` kind=`stale_reply_cancelled` с contact_id и «N из M» —
  дрил Д-7 проверяется фактом из БД, не глазами.
- log.info в том же месте.

### 6. Тесты (TDD, RED до кода)

unit `process_batch` (run.py, фейк-транспорт):
1. fresh→True между Say-1 и Say-2: Say-2 не отправлен, Say-1 в истории,
   typing снят, событие `stale_reply_cancelled` записано.
2. fresh→True до первого Say: ноль отправок, событие записано.
3. `fresh_incoming=None`: все бабблы уходят (регресс-защита консоли/тестов).
4. Отменённый остаток НЕ попадает в `store.history` (контракт для
   регенерации: модель не думает, что уже сказала невысказанное).

unit `ChatDebouncer`:
5. `add()` во время `on_ready` → `fresh_incoming()` внутри этого `on_ready`
   становится True; после завершения — следующая итерация процессит слитый
   буфер (существующее поведение слива не сломано).
6. Эпоха снапшотится на флаше: сообщения самого батча НЕ считаются «свежими».

интеграция (существующий стиль test_humanizer_debounce):
7. Сквозной: реплика мид-доставки → остаток отменён → следующий ответ
   сгенерирован с историей «отправленная часть + новая реплика».

## Риски

- Лид шлёт стрим коротких сообщений → Ольга «замолкает» на полуслове и потом
  отвечает разом. Это ЖЕЛАЕМОЕ человеческое поведение (живой человек перестаёт
  печатать, когда собеседник пишет).
- Дребезг: entrance в `add()` на ЛЮБОЕ сообщение — включая то, что дебаунсер
  сольёт в тот же будущий батч. Отмена срабатывает только против УЖЕ идущей
  доставки — дребезга нет.
- Потеря контента невозможна: неотправленное отсутствует в истории, значит
  регенерация вправе сказать его заново.

## Дрил-критерий приёмки (Д-7 из TEST_MATRIX)

Живьём: написать реплику, пока Ольга «печатает» многобаббловый ответ →
остаток не приходит, в `control_events` есть `stale_reply_cancelled`,
следующий ответ учитывает новую реплику. Без открытия гейта — под флагом
semidemo, как дрилы 1–7.
