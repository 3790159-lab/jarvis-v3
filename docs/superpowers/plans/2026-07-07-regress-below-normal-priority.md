# План: безопасный полный регресс на 8-ГБ машине (не душить живого бота)

**2026-07-07.** Дважды за сессию полный `pytest tests/` (≈3500 тестов) задушил
живого бота: один pytest-процесс держит **~5.5 ГБ RSS**, на 8-ГБ машине с живым
ботом+backend+гардианом это уводит свободную RAM до ~150–240 МБ → своп-трэшинг →
heartbeat бота протухает (>90 с), гардиан сам голодает и не может респавнить.
Бот отвисает сам, как только pytest убит и RAM освобождается.

## Правило
НЕ гонять полный `tests/` одним процессом на живой prod-машине без throttling.

## Фикс (обе меры вместе — по отдельности мало)
1. **BELOW_NORMAL приоритет** (как `/regress` в пульте) — снимает CPU-конкуренцию,
   даёт heartbeat-потоку бота такты. Запуск:
   `cmd /c start "" /belownormal /b <venv>\python.exe -m pytest tests/ ...`
   или после старта: `(Get-Process -Id <pid>).PriorityClass = 'BelowNormal'`.
   ⚠️ Приоритет НЕ уменьшает RAM — только планирование CPU.
2. **Батчинг (главное против RAM-потолка)** — дробить прогон на группы тест-файлов
   (например по 3–4 батча), запускать по одному foreground с таймаутом (≤10 мин),
   объединять результаты. Пик RSS одного батча << 5.5 ГБ, между батчами бот дышит
   и heartbeat восстанавливается. Осиротеть не может (foreground, kill по таймауту).
3. **Мониторинг-предохранитель**: перед/во время прогона следить `FreePhysicalMemory`;
   при падении < ~600 МБ — прервать батч (не ждать заморозки).

## Где применить
- `/regress` в пульте (`_regress_run`) — убедиться, что уже BELOW_NORMAL; добавить
  батчинг+RAM-guard, если запускается на этой машине.
- Любой авто-регресс в devtask/merge-гейте на этой машине.
- Baseline: `state/regress_baseline.json` хранит только COUNTS (129 failed), не имена —
  для честного «diff имён» держать и список имён падений (снимок в state/).

## Аварийное восстановление (если снова задушило)
`Stop-Process` по `Name='python.exe' & CommandLine LIKE '*pytest*'` (бот НЕ трогать) →
RAM освобождается → бот отвисает сам за секунды. (Проверено 2× 2026-07-07.)
