# СПЕКА: панель Джарвиса — фаза 0, read-only

**Дата:** 2026-07-29 · **Статус:** черновик на чтение Даниила, кода нет ·
**Область:** внутренняя панель для владельца системы (не для клиентов TAMAPI).

Клиентский дашборд (`docs/dashboard/`) отвечает на вопрос «как идут продажи у
клиента». Эта панель отвечает на другой: **«что сейчас происходит в моей машине и
где она сломана»**. Разные зрители, разные данные, разный риск — поэтому отдельная
поверхность, а не вкладка в клиентском кабинете.

---

## 0. Предусловие, которое сильнее самой панели

> ⚠️ **Сторожевой ярус обязан жить ВНЕ этой машины. Это предусловие фазы 0, а не её
> часть, и оно НЕ закрывается кодом панели.**

Сегодня всё наблюдение — на том же железе, за которым наблюдает:
`JarvisOpsWatchdog` крутится на этом же PC, гардианы тоже, панель будет там же.
Отсюда прямое следствие: **смерть машины, потеря сети или засыпание = панель зелёная
ровно до момента, когда её перестаёт быть видно, и никто не узнает.** Тот же класс
уже кусался: раннер chatter был мёртв 12 часов (21.07 14:02 → 22.07), и это заметил
человек, а не система.

Второго канала фактически нет: Tailscale в состоянии `Logged out` (DEV-23), то есть
запасной путь до машины не поднят.

Что должно существовать снаружи, до того как панели можно верить:

| Уровень | Что делает | Где живёт |
|---|---|---|
| Внешний пинг | дергает публичный health раз в минуту, алертит в TG при 2 промахах | любой внешний uptime-сервис / VPS |
| Внешний дедлайн-монитор | «heartbeat не обновлялся N минут» — push-модель, машина сама шлёт наружу | внешний сервис (dead-man switch) |
| Второй канал связи | доступ к машине, когда основной путь лёг | Tailscale (сейчас разлогинен) |

**Панель фазы 0 обязана явно говорить, что она сама — не сторож.** На экране «Ферма»
— строка вида «Зовнішній сторож: НЕ налаштований», красная, пока внешний монитор не
подключён. Панель, которая молчит о собственной слепоте, опаснее отсутствия панели:
она создаёт ощущение контроля.

## 1. Принципы фазы 0

1. **Read-only. Ни одной мутирующей кнопки.** Ни рестарта, ни kill, ни ротации
   ключей, ни правки конфигов. Причина не в лени: каждая мутация из веба — это новый
   путь к проду в обход существующих предохранителей (скоупленный kill по точному
   PID, гардиан-дебаунс, ACL на `.secrets`). Пока путь не спроектирован — кнопки нет.
2. **Показывать источник и возраст каждого факта.** Не «раннер жив», а «heartbeat
   02:50:12, 8 с назад». Панель без возраста данных врёт при первом же зависании
   сборщика.
3. **Не выдумывать агрегатов.** Если данных нет — «немає даних», а не 0 и не прочерк,
   который читается как ноль.
4. **Секреты не покидают машину даже в панели.** Значение ключа не показывается
   никогда и ни в каком виде — только имя, назначение, срок, здоровье (§5).
5. **Панель не поднимает то, что осознанно отставлено.** Отставленное показывается
   как «відставлено навмисно», а не как авария (§6, снайпер).

## 2. Экран «Ферма»

Что крутится, живо ли, откуда мы это знаем.

```
┌──────────────────────────────────────────────────────────────┐
│  ФЕРМА                            зібрано 02:50:31 (щойно)   │
│  Зовнішній сторож: ⚠️ НЕ налаштований                        │
├──────────────────────────────────────────────────────────────┤
│  ● backend        :8010   PID 1600/12364   з 29.07 01:54     │
│  ● головний бот           PID 8988/11756   з 28.07 14:13     │
│  ● chatter раннер         PID 12540/4592   з 29.07 02:35     │
│  ○ снайпер                відставлено навмисно               │
├──────────────────────────────────────────────────────────────┤
│  ГАРДІАНИ                                                    │
│  ● backend_guardian       PID 5944   heartbeat 8 с тому      │
│  ● bot_guardian           PID 5936   heartbeat 8 с тому      │
│  ● chatter_guardian       PID 5964   heartbeat 8 с тому      │
│  ● ops_watchdog           PID 5908   heartbeat 8 с тому      │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 Источники статуса (проверено фактом 29.07)

| Сущность | Как определяем живость |
|---|---|
| Процессы | `Win32_Process` по `CommandLine`; для раннера — **обязательно** `Name='python.exe'` (см. грабля ниже) |
| Гардианы | heartbeat-файлы `state/*_heartbeat.txt` (`bot_`, `chatter_`, `chatter_guardian_`, `guardian_`, `ops_watchdog_`) |
| Таски | `Get-ScheduledTask` → поле `State` |
| Раннер chatter | heartbeat + факт, что процесс — потомок своего гардиана |

⚠️ **Грабля, стоившая ложного «поднялся» 29.07.** Проверка вида
`CommandLine -match 'chatter.telethon_run'` **матчит сам процесс проверки**: строка
попадает в командную строку PowerShell/bash, и счётчик показывает живого раннера,
которого нет. Сборщик обязан либо фильтровать по `Name -eq 'python.exe'`, либо
исключать собственный PID и его родителя, либо читать лог гардиана. Тест-сторож:
запустить сборщик при заведомо мёртвом раннере — он обязан сказать «мёртв».

⚠️ **`LastTaskResult` у Running-таска не значит ничего.** У всех живых гардианов он
`2147946720`, и это не ошибка — авторитетное поле для крутящегося таска — `State`.
Красить строку по `LastTaskResult` = четыре ложные аварии на пустом месте.

⚠️ **Размер файла на NTFS врёт про живой лог.** `dir`/`Get-ChildItem` показывают 0
байт у файла с открытым write-хэндлом. Возраст лога брать `Get-Content`/`os.stat`,
а не размером. Уже вводило в заблуждение (мираж «лог пустой»).

### 2.2 Правило цвета

🟢 heartbeat свежий И процесс есть · 🟡 процесс есть, heartbeat протух (или наоборот)
· 🔴 нет ни того ни другого · ⚪ отставлено намеренно.

Жёлтый — не косметика: расхождение «процесс жив, heartbeat мёртв» — это ровно тот
случай, когда сторож и гардиан считали DOWN по-разному (арка CHATTER-2), и его надо
видеть отдельно от красного.

### 2.3 Логи

Ссылка на хвост лога у каждой строки. ⚠️ Логи лежат в **двух** папках (`logs/` и
вторая, см. `docs/postmortems/2026-07-28-farm-and-legacy-anchor.md`) — сборщик обязан
знать обе, иначе панель покажет протухший хвост и это будет выглядеть как тишина.

## 7. Фазы 2–3 — зафиксированы, НЕ реализуются

Здесь они записаны, чтобы фаза 0 не проектировалась так, что их потом некуда
вставить. **В фазе 0 не делается ничего из перечисленного.**

### Фаза 2 — «Джарвіс пропонує»

Панель переходит от «показать» к «предложить»: карточки вида «ветка `X` без движения
14 дней и уже смержена — снять worktree?», «ключ FAL истекает через 12 дней»,
«classifier_error 3 дня подряд — чинить корень, а не поднимать порог».

Условия, без которых фазу 2 нельзя начинать:
1. Фаза 0 отработала достаточно, чтобы предложения строились на измеренном, а не на
   догадках.
2. Каждое предложение — **с явной причиной и ссылкой на факт**, иначе это гадание.
3. Предложение ≠ действие: подтверждение остаётся у человека, и первое время
   исполнение — вручную по инструкции из карточки.
4. Порог шума: предложение, которое отклонили дважды, замолкает.

### Фаза 3 — голос

Голосовой доступ к панели («что с фермой?», «сколько потратили вчера»). Требует
решённой фазы 2 и отдельного разбора приватности: голосовой канал — это ещё одна
поверхность аутентификации, и она не должна оказаться слабее веб-входа.

## 8. Архитектура фазы 0

- **Поверх существующего FastAPI**, за `auth_guard_middleware` (ENFORCE). Новых
  портов не открываем.
- **Auth — owner-only**, отдельно от клиентского дашборда: у панели другой класс
  данных (PID, ключи, ветки), и общий вход с клиентским кабинетом недопустим.
- **Сборщик — отдельный процесс/таск**, пишет снапшот в файл/таблицу; панель читает
  снапшот. Причина: панель не должна дёргать `Win32_Process` и `git` на каждый
  запрос — это и медленно, и делает веб-запрос способом нагрузить прод.
- **Возраст снапшота — на экране**, крупно. Мёртвый сборщик обязан быть виден
  (иначе панель показывает вчерашнюю зелень).
- **Ноль записи.** Ни в chatter-БД, ни в конфиги, ни в `state/`. Единственная
  запись — собственный снапшот панели, в собственное место.
