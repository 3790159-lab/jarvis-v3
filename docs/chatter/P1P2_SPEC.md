# P1P2_SPEC: шифрование секретов at rest (минимальный вариант)

**Дата:** 2026-07-22 · **Спринт 0, пункт 1** · **Статус:** **ОК Даниила получен** (дизайн + O1–O3, см. §9-Р). Cutover живых секретов — отдельный повторный ОК. Код — ветка `sprint0/secrets-p1p2`.

**Критерий готовности (Даниил):** *компрометация диска не даёт takeover аккаунта клиента.* ACL защитой **не считается** — критерий «украли диск/бэкап → нет takeover».

## 1. Модель угроз — что закрываем, что нет (минимальный вариант)

| Угроза | Закрываем? |
|---|---|
| Кража/копия диска, бэкапа, `.secrets/`-каталога (offline) | ✅ ДА — зашифрованные блобы бесполезны на другой машине/под другим пользователем |
| Утечка файла в git/логах/шаринге | ✅ ДА — на диске только шифртекст |
| Код, выполняющийся **под тем же Windows-пользователем на той же машине** | ❌ НЕТ — он расшифрует так же, как раннер. Это граница «минимального варианта», не полного vault (полный vault — при 3+ клиентах, §11 A9) |

Критерий Даниила = **offline-компрометация диска** (кража ноута/диска/бэкапа). Именно её закрываем. Явно фиксируем границу: same-user code execution остаётся вне охвата до полного vault.

## 2. Дизайн

### 2.1 Мастер-ключ — DPAPI (user scope)
Windows DPAPI (`CryptProtectData`, scope=CurrentUser) шифрует данные ключом, производным от учётки пользователя. Блоб расшифровывается **только** тем же пользователем на той же машине → копия диска на другой машине/под другим пользователем бесполезна. Интерактивный ввод пароля не нужен (раннер под гардианом стартует без консоли) — DPAPI не требует passphrase.

- Раннер и гардиан **обязаны бежать под тем же Windows-пользователем**, что шифровал (проверить: сейчас S4U-таски). Если пользователь разный — расшифровка упадёт. Это первый пункт проверки cutover.
- Питон: `pywin32` (`win32crypt.CryptProtectData/CryptUnprotectData`) либо `ctypes` к `crypt32.dll`. Выбор — S, обосную в реализации (склоняюсь к `ctypes`, без нового пакета).

### 2.2 Session — через StringSession, БЕЗ plaintext-файла на диске
Ключевое решение: **не** держать расшифрованный `.session` файл на диске даже временно. Вместо файловой сессии:
1. Экспортировать текущую сессию в **StringSession** (Telethon умеет: `StringSession.save(client.session)`).
2. Зашифровать строку DPAPI → хранить `.secrets/<slug>.session.enc` (шифртекст).
3. Раннер на старте: читает `.enc` → DPAPI-decrypt в память → `TelegramClient(StringSession(s), api_id, api_hash)`. **Plaintext-сессии на диске нет никогда.**

Это чище файлового варианта (где decrypt-в-temp оставляет окно plaintext). Точка правки — `derive_session_path`/создание клиента в `telethon_run.py` + `telethon_login.py` (при логине сразу сохранять `.enc`, не `.session`).

### 2.3 `.env` — decrypt-в-память при загрузке + ACL
- Хранить `.env.enc` (DPAPI-шифртекст всего файла). Маленький загрузчик: читает `.enc` → decrypt в память → парсит в `os.environ` (замена `dotenv.load_dotenv`). Plaintext `.env` на диске не лежит.
- ⚠️ `.env` читают **многие** процессы Jarvis, не только chatter. Поэтому: либо (а) все консьюмеры переходят на общий decrypt-загрузчик, либо (б) на этапе минимального варианта — **ACL** (только сервисный пользователь читает `.env`) + шифрование только для chatter-критичных секретов. **Открытый вопрос O1 ниже** — согласовать объём с Даниилом (весь `.env` через загрузчик = трогаем весь Jarvis; только chatter — меньше радиус).
- ACL (icacls): снять чтение у всех, кроме сервисного пользователя и админа — независимо от шифрования, как defense-in-depth.

### 2.4 БД (переписка лидов, P8/S5)
В минимальный вариант шифрование БД **не** входит (Даниил: «шифрование session+`.env`»). Но БД содержит ПДн лидов plaintext. Предлагаю ACL на `.secrets/*.db` заодно (S, дёшево) и пометить полное шифрование БД как хвост к полному vault. **Открытый вопрос O2.**

## 4. TDD-план (пишется ПЕРВЫМ, на фикстурах, без живых секретов)

1. `crypto.py`: round-trip (encrypt→decrypt = исходник); decrypt чужого блоба падает явно (не тихо); tamper (битый байт) → ошибка, не мусор.
2. `secret_loader.py`: `.env.enc` → корректный `os.environ`; отсутствие файла → понятная ошибка; StringSession round-trip (сохранить→зашифровать→загрузить→та же строка).
3. Раннер-загрузка: подменный `.enc` с фейковой StringSession → клиент конструируется из строки, не из файла (мокнутый TelegramClient).
4. Негатив: нет `.enc` и нет legacy `.session` → явная ошибка старта, не тихий фейл.
5. Совместимость: legacy plaintext `.session` есть, `.enc` нет → одноразовая миграция (зашифровать, оставить бэкап) — тест миграции.

Всё это тестируется фикстурами (фейковые строки, tmp-пути); DPAPI-часть — за тонкой обёрткой, в тестах мокается или гоняется на временных данных, НЕ на живом demo.session.

## 6. Cutover — безопасный перевод живых секретов (после ОК Даниила)

Порядок, каждый шаг обратим:
1. **Проверка пользователя.** Убедиться, что гардиан/раннер-таски бегут под тем же Windows-пользователем, которым будем шифровать (иначе DPAPI не расшифрует). Если нет — сначала это.
2. **Бэкап.** Скопировать `demo.session` + `.env` в защищённое место (вне репо, tighter ACL) — страховка отката.
3. **Мердж кода** Спринта 0 в phase-4.0, но раннер пока на старом (не деплоить).
4. **Миграция сессии:** оффлайн-скрипт читает `demo.session` → StringSession → DPAPI → `demo.session.enc`. Проверить, что `.enc` расшифровывается обратно в ту же строку.
5. **Миграция `.env`:** `.env` → `.env.enc` (+ решить объём по O1).
6. **Maintenance-окно:** остановить гардиан (`-Revert`/disable), деплой нового кода (checkout), старт. Раннер поднимается из `.enc`.
7. **Верификация:** heartbeat идёт; бот отвечает на тестовую реплику (allowlist, гейт закрыт); лог без ошибок расшифровки.
8. **Шред plaintext:** только после успешной верификации — удалить/зашифровать plaintext `demo.session` и `.env` (бэкап из п.2 держать до полной уверенности, потом тоже убрать).
9. **ACL** на `.secrets/` и `.env.enc`.

**Гейт при cutover не трогаем** — тестовая реплика идёт с allowlist-id при закрытом гейте.

## 7. Откат

- Любой шаг до п.8 — вернуть бэкап-файлы (п.2), `-Revert` гардиана на старый код (phase-4.0 без шифрования). Раннер поднимется на plaintext как сейчас.
- После п.8 (plaintext удалён) — восстановить из бэкапа п.2. Поэтому бэкап держим до финальной уверенности.
- Риск №1: раннер под другим пользователем → DPAPI-decrypt падает → бот не логинится. Ловится на п.1 и п.7; откат — бэкап.

## 8. Проверка критерия готовности

«Компрометация диска не даёт takeover»:
- Взять `demo.session.enc` + `.env.enc`, скопировать на **другую машину / под другим пользователем**, попытаться расшифровать → DPAPI отказывает → StringSession недоступна → аккаунт не угнать. **Это приёмочный тест cutover** (гоняем на копии, не на живом).
- Плюс: на диске не остаётся plaintext-сессии ни в покое, ни во время работы (StringSession в памяти).

### 9.1 Эксперимент S4U × user-scope DPAPI (2026-07-22) — ✅ РАБОТАЕТ

Опасение: при LogonType=S4U пароль не передаётся → user-scope DPAPI мог не расшифровать мастер-ключ из задачи планировщика. Проверено фактом:
- Тестовая строка зашифрована user-scope из интерактивной сессии.
- Расшифрована из процесса, запущенного **временной задачей с LogonType=S4U** (тот же принципал, что у гардианов): `whoami=pc-loe\admin`, session 0, non-interactive → **DECRYPT_OK**. Machine-scope тоже OK.
- Вывод: **регистрацию задач гардианов менять не нужно**, дизайн §2.1 подтверждён.
- ⚠️ Остаточные оговорки: (а) сценарий «свежий ребут, AtStartup-задача стартует ДО первого интерактивного логона» не проверен — проверить при ближайшем естественном ребуте, до финального шреда plaintext (п.8 cutover); (б) смена пароля учётки в обход штатного механизма (`net user`, reset админом) ломает user-scope мастер-ключи DPAPI — пароль менять только штатно (Ctrl+Alt+Del) и с валидным бэкапом секретов (§12).

## 12. Процедура восстановления — 🔴 БЛОКЕР ПРИЁМКИ P1/P2

DPAPI привязывает секреты к учётке+машине → смерть диска/профиля без процедуры восстановления = потеря всех сессий. **Без этого P1/P2 не закрыт:**

1. **Экспорт:** зашифрованный бэкап секретов (StringSession'ы + `.env`-значения plaintext-вида) в один контейнер под **паролем владельца**. ✅ Реализовано (`chatter/security/recovery.py`, 10 тестов): **НЕ DPAPI** (циркулярность — бэкап обязан открываться на чужой машине), пароль → **scrypt** (N=2¹⁵, соль 16Б) → **AES-256-GCM**, формат версионирован (`JRVBAK\0` + version + salt + nonce + ct, заголовок в AAD). Неверный пароль/tamper/чужая версия → явная ошибка.
2. **Хранение вне машины** (телефон/облако владельца — на его усмотрение). **Экспорт обязателен после подключения КАЖДОГО нового клиента** (закреплено в ONBOARDING_MANUAL §1 + чеклист).
3. **Тест восстановления:** «восстановили на чистом профиле → раннер поднялся» — прогоняется до закрытия P1/P2 (на тестовом профиле/машине, не трогая прод). ⏳ PENDING.

## 13. Ребут-тест DPAPI — 🔴 БЛОКЕР CUTOVER (решение Даниила 2026-07-22)

Оговорка (а) из §9.1 повышена до намеренного блокера: гардиан стартует AtStartup **ДО первого интерактивного логона** — доступен ли user-scope DPAPI в этом окне, S4U-экспериментом из живой сессии не доказано.

- **Проба готова:** задача `DpapiBootProbe_TEMP` (AtStartup, S4U, тот же принципал) расшифровывает user-scope и machine-scope тест-блобы, пишет факт в `C:\Users\Admin\.dpapi_boot_probe\boot_probe_log.txt` (timestamp, whoami, session, explorer_procs как признак «до логона»). Смоук из живой сессии пройден.
- **Порядок:** согласовать время ребута с Даниилом → ребут → **НЕ логиниться ~2 минуты** (иначе окно «до логона» не воспроизведётся) → факт из лога.
- **Пока не проверено: plaintext не шредим, cutover не делаем.**
- Если user-scope в окне недоступен — варианты (НЕ внедрять без ОК): (а) machine-scope DPAPI + ACL + entropy для стартовых секретов; (б) отложенный старт раннера до логона.
