# Дрил Д-7: отмена устаревшего ответа (Б4)

Что проверяем: лид пишет ВО ВРЕМЯ того, как Ольга «печатает» многобаббловый
ответ → остаток не приходит, факт есть в БД, следующий ответ учитывает новую
реплику. Гейт НЕ открываем — дрил идёт под флагом semidemo, как дрилы 1–7.

## 0. Перед стартом (30 секунд)

```powershell
# один поллер, а не два
Get-CimInstance Win32_Process -Filter "Name like '%python%'" |
  Where-Object { $_.CommandLine -match 'telethon_run' } |

# счётчик событий ДО дрила (потом сравним)
python -c "import sqlite3;c=sqlite3.connect(r'C:\jarvis\.secrets\demo.db');print(c.execute(\"SELECT COUNT(*) FROM control_events WHERE kind='stale_reply_cancelled'\").fetchone()[0])"
```

## 1. Как вызвать многобаббловый ответ

Отмена срабатывает только против УЖЕ идущей доставки, поэтому ответ должен
быть длинным: хуманайзер режет по `split_max_len: 160`, и между бабблами
стоят паузы печати (`cps 4–7` симв/сек + jitter). То есть ответ на 400+
символов даёт 3 баббла и **30–60 секунд** на перебивание — времени с запасом.

Пиши вопрос, который заведомо тянет развёрнутый ответ:

> **Розкажіть, будь ласка, детально що входить у повну айдентику і як
> виглядає процес роботи?**

## 2. Момент перебивания

Ждёшь **первый баббл**. Как только он пришёл — сразу, не дожидаясь второго,
пишешь:

> **ой, стоп, поки не треба**

Ключевое: писать надо в окно между бабблами, пока стоит плашка «печатає».
Если написать ПОСЛЕ последнего баббла — это обычный следующий ход, отмены не
будет (и это правильно).

## 3. Что должно произойти

| Признак | Ожидание |
|---|---|
| Бабблы | 2-й и 3-й **не приходят** |
| Плашка «печатає» | снимается сразу, не висит |
| Следующий ответ | реагирует на «поки не треба», а не договаривает про айдентику |
| Повтор недосказанного | допустим: неотправленного нет в истории, модель вправе сказать это заново |

Если карточка керівниці ушла на этом же ходу — в пульт придёт **отдельное**
предупреждение «лид дописал сразу после карточки — она могла устареть».
На этом сценарии карточки быть не должно (вопрос про процесс — не тригер).

## 4. Проверка фактом (главное — не глазами)

```powershell
python -c "import sqlite3,datetime; c=sqlite3.connect(r'C:\jarvis\.secrets\demo.db'); c.row_factory=sqlite3.Row; [print(datetime.datetime.fromtimestamp(r['ts']).strftime('%H:%M:%S'), r['contact_id'], r['detail']) for r in c.execute(\"SELECT * FROM control_events WHERE kind='stale_reply_cancelled' ORDER BY ts DESC LIMIT 5\")]"
```

Ожидаемая строка:

```
18:42:07  237616472:volska  не відправлено 2 з 3 бабблів
```

- `contact_id` — твой id, не NULL;
- `detail` — «N з M бабблів», где N ≥ 1 и M > N. Если N == M — перебил ДО
  первого баббла (тоже валидный кейс, весь ответ выброшен);
- события НЕТ вообще → отмена не сработала: смотри, точно ли ты успел в окно
  между бабблами, и есть ли в логе `stale reply cancelled`.

История диалога — проверка, что отменённый хвост туда не попал:

```powershell
python -c "import sqlite3; c=sqlite3.connect(r'C:\jarvis\.secrets\demo.db'); c.row_factory=sqlite3.Row; [print(r['role'],'|',r['text'][:90]) for r in c.execute(\"SELECT role,text FROM messages ORDER BY id DESC LIMIT 6\")]"
```

В `assistant`-строках должна быть **только отправленная часть**. Если там есть
текст, который до тебя не дошёл, — сломан контракт регенерации (модель будет
думать, что уже это сказала).

## 5. Негативная проверка (чтобы не было ложного зелёного)

Сразу после — обычный ход **без** перебивания: задаёшь тот же длинный вопрос
и молчишь до конца. Все бабблы должны прийти, новых `stale_reply_cancelled`
появиться не должно. Без этой проверки «отмена» неотличима от «бот сломался
и перестал досылать».

## 6. Известная цена (не баг, зафиксировано в спеке §8)

- Отмена срабатывает на границе перед бабблом, а не мгновенно: если ты
  написал в момент паузы печати, остаток отменится после её окончания —
  худшее ожидание равно одной паузе хуманайзера.
- Карточка эскалации при отмене НЕ откатывается, воронка остаётся
  `escalated` — приходит только предупреждение.
