## Порядок работ

### 1. Секреты P1/P2 — минимальный вариант
**Что.** Шифрование `.secrets/` (session + per-account БД) и `.env` at rest; раздельные ACL, чтобы chatter-раннер видел только свои 4 ключа из 188. Полный vault — отложен до 3+ клиентов (§11 A9).
**Объём.** M (DPAPI-обёртка над session/db + правка путей загрузки; ACL на `.env`).
**Зависимость.** Нет. Первым.
**Блокер запуска.** 🔴 **ДА — блокер перед первым платящим клиентом.** Подключение чужих аккаунтов (любым путём) включается только после этого (§11 A8).
**Что ломается, если пропустить.** Session-файл plaintext = угон аккаунта клиента; `.env` = слив 188 ключей всей экосистемы при компрометации машины. Для «пульта чужих бизнесов» — недопустимо. Дашборд это обостряет (централизует доступ к N аккаунтам).

### 2. Prompt-caching
**Что.** `cache_control` на системный промпт (стабилен весь диалог) + окно истории (последние N сообщений/токенов вместо всей — закрывает и P3-стоимость, и рост ПДн P8). Плюс usage-логгер (§4 ниже врезается сюда же — `cache_read` появляется в usage).
**Объём.** S (окно) + M (кэш с корректной инвалидацией). Правка `core/llm.py` + `brain.py`, аддитивная, конвейер не меняем.
**Зависимость.** Нет (но usage-логгер MVP v1 логичнее делать одновременно — общая точка `AnthropicLLM.complete`).
**Блокер запуска.** 🟡 **Можно после первого клиента, но ДО второго** (§11 A10) — следующая по деньгам работа после секретов.
**Что ломается, если пропустить.** −70% расходов не получаем (см. §эконом.). Первый клиент выживет, но экономика при масштабе рушится: 1000 диалогов/мес = $350 токенов/клиент вместо $110 — съедает тариф.

### 3. P4 (Б4-хвост) + P5 (funnel-edge)
**Что.** P4 — epoch-счётчик на дебаунсере, инвалидация устаревшего ответа перед каждой отправкой. P5 — при исходящем к незнакомцу создавать контакт с флагом «инициировано нами», пускать ответы через admission.
**Объём.** M + M.
**Зависимость.** Нет. Проверяются живыми дрилами Д-7, Д-8 (TEST_MATRIX §4).
**Блокер запуска.** 🟡 **Можно после** запуска, но до заметного объёма — это то, что видит живой клиент как «глючит».
**Что ломается, если пропустить.** P4: персона договаривает поверх новой реплики лида → выглядит как глухой бот (главный провал для продукта «неотличимость от человека»). P5: диалог, начатый владельцем вручную, обрывается на первом ответе лида → потерянные лиды у риелтора/фрилансера.

### 4. MVP дашборда v1 — «вести подключённый аккаунт без yaml и SSH»
**Что.** Auth (пароль+2FA владельца, роли/скоуп в схеме, редактирует только владелец) + аудит-лог · М1 клиенты/аккаунты (`client → N accounts`, статус, start/stop/revert) · **М7 Агент** (персона + красные линии переключателями + превью промпта + откат) · М3 редактор конфига (Знання+Playbook, валидация, `.versions/`-откат, reload) · **М8 Приклади** (few-shot `examples.yaml`: ручной ввод/правка, статический отбор с бюджетом токенов, поддержка в `brain.py`) · М4 тумблеры (honesty c consent/funnel_gate/pause/allowlist) · М5 лента (эскалации + ответ владельца + кнопки, SSE) · М6 аналитика + usage-логгер ($ по прайсу-конфигу, тариф↔расход) · событийная шина (webhook + Sheets). Экран аккаунта — вкладки: Агент·Знання·Приклади·Playbook·Тумблери·Канали·Інтеграції·Аналітика.
**Объём.** L (2–3 недели). Control-plane над раннерами (обобщение semidemo-флага в реестр аккаунтов) — самый рискованный кусок. М7 — фасад над готовым (persona/settings уже есть). **М8 требует правки ядра** (аддитивно): `examples.yaml` в `CONFIG_FILES` (версионирование) + новая секция в `build_system_prompt` (`brain.py`) + отбор с бюджетом токенов — заложить ~M внутри общего L.
**Зависимость.** P1/P2 (для подключения чужих аккаунтов; на своих/демо катать параллельно). Usage-логгер и М8 стыкуются с **prompt-caching (п.2)** — примеры увеличивают статичную часть промпта, кэш даёт по ним ещё больший выигрыш (см. §эконом.). Логично: М8 после/вместе с caching.
**Блокер запуска.** 🟡 **Это и есть продукт** — подключение реальных клиентов гейтится P1/P2.
**Что ломается, если пропустить.** Ведение остаётся ручным (yaml+SSH). Без М8 клиент вынужден писать промпт руками — теряем ключевое преимущество онбординга «покажи диалоги вместо промпта».

### 4.5. Импорт истории Telegram для М8 (v1.5)
**Что.** Экспорт Telegram (JSON) → авто-нарезка на пары «клиент→ассистент» → **анонимизация** (имена/телефоны/@-хендлы/ссылки → плейсхолдеры) → экран «оставить/выкинуть» (тег+приоритет) → `examples.yaml`.
**Объём.** M (парсер JSON + нарезка + анонимайзер + экран курирования). Самостоятельный кусок поверх готового М8.
**Зависимость.** М8 (п.4) + **P1/P2** (импорт пишет ПДн третьих лиц в конфиг — анонимизация обязательна, файл незашифрован до P1/P2).
**Блокер запуска.** 🟢 **После v1.** Ускоряет онбординг, но не блокирует первого клиента (в v1 примеры вводятся вручную).
**Что ломается, если пропустить.** Онбординг медленнее (клиент/оператор набивают примеры руками вместо загрузки реальной переписки) — рост, не выживание. Без анонимизации импорт делать НЕЛЬЗЯ (утечка чужих ПДн).

### 5. v2 — онбординг с нуля + клиентские роли + подключение по ключу
**Что.** М2 визард целиком (QR/код → авто-провизия раннера) · клиентские роли (client-кабинет: своя лента+тумблеры, без миграции схемы) · **подключение по ключу (session string / api_id+api_hash) + bulk** · адаптеры amoCRM/Kommo+CSV · RAG-синк знаний · редактор персоны с few-shot.
**Объём.** L+ (несколько итераций).
**Зависимость.** MVP v1 + **подключение по ключу зависит от P1/P2** (ключ шифруется at rest — §11 B-доп).
**Блокер запуска.** 🟢 **После** — расширение, не блокер первого клиента.
**Что ломается, если пропустить.** Онбординг остаётся полу-ручным (аккаунт логинит владелец); клиент не может сам зайти в свой кабинет; нет bulk для клиентов с N аккаунтами. Всё это — рост, не выживание.

## Юнит-экономика подписки

**Источник цифр:** замеры фазы 1 через `count_tokens` (AUDIT §3), не оценка на глаз. Модель — **sonnet-5**, цена по стикеру **$3 / $15** за 1M вход/выход (интро $2/$10 действует до 2026-08-31 — привожу ниже, но планировать стоит по стикеру, интро истечёт).

**Замеры на диалог** (средний = 10 обменов):
- Системный промпт brain: **5 168 ток** + классификатор: **3 458 ток** — оба на **каждый** ответ.
- Итого на диалог: **~99k input + ~3.6k output** → **$0.35 (стикер)** / $0.23 (интро).
- После prompt-caching: системный промпт (87% входа, стабилен) уходит в cache-read ×0.1 → **~$0.11 (стикер)** / ~$0.07 (интро). Экономия **−70%**.

### Расход $/клиент/мес (по стикеру $3/$15)

| Диалогов/мес | До caching | После caching | Экономия |
|---|---|---|---|
| 100 | **$35** | **$11** | −$24 |
| 300 | **$105** | **$33** | −$72 |
| 1000 | **$350** | **$110** | −$240 |

*(Интро-цены до 31.08, для справки: 100 → $23/$7 · 300 → $70/$22 · 1000 → $233/$73.)*

### Влияние few-shot примеров (М8) на стоимость

Статический блок примеров ~**1500 токенов** добавляется к системному промпту **brain** (в классификатор не идёт), на каждый из ~10 ответов диалога. Стоимость ответа (на диалог, стикер $3/$15):

| Конфигурация | $/диалог (10 обменов) | Δ |
|---|---|---|
| Без примеров, без кэша | **$0.35** | база |
| **С примерами, без кэша** | **$0.40** | +$0.045 (примеры ×10 ответов) |
| **С примерами + кэш** | **~$0.115** | +$0.005 к «после кэша» |

**Ключевой вывод:** примеры без кэша заметно дороже (+13% к диалогу), а **с кэшем — почти бесплатны** (+$0.005), потому что статичны и кэшируются целиком. То есть М8 **усиливает довод за prompt-caching** (п.2): чем больше статичных примеров, тем больше выигрыш кэша. Порядок «caching → М8» (или вместе) — не случайный: включать много примеров ДО кэша = раздувать счёт; после кэша — можно щедро, почти без цены.

Per-client/мес с примерами (стикер): 100 диал — без кэша $40 / с кэшем $11.5; 300 — $120 / $34.5; 1000 — $400 / $115. С кэшем примеры практически не сдвигают экономику; без кэша — добавляют ~15% к и без того высокому счёту.

### Что это значит для тарифа

- Ориентир подписки из проекта — **$500–1000/мес с клиента**.
- При **300 диалогов** после caching токены = **$33/мес** → валовая маржа по токенам ~93–97%. Здорово.
- При **1000 диалогов БЕЗ caching** = **$350/мес** → съедает больше половины тарифа $500. **Именно caching делает высокообъёмных клиентов рентабельными** — отсюда приоритет п.2 (до второго клиента).
- **Осторожно с длинными диалогами:** без окна истории 30-обменный диалог ~$1 (стикер) из-за квадратичного роста истории. Окно истории (входит в п.2) это ограничивает — иначе болтливый клиент/лид раздувает счёт непредсказуемо. Это ещё один довод сделать п.2 рано.

**Вывод для Даниила:** тариф $500+ безопасен при любом реалистичном объёме **после** внедрения caching+окна (п.2). До caching — рентабельны только низко-/среднеобъёмные клиенты; высокообъёмные съедают маржу. Тарифную сетку задавать конфигом (§11 A2), пороги диалогов/мес — из этой таблицы.

**Оговорки.** Цифры — для volska-конфига (uk, sonnet-5); другой клиент с более коротким knowledge/playbook даст меньший системный промпт → дешевле. Точный per-client факт даст usage-логгер (п.4) после запуска.
