# ARCHITECTURE: дашборд chatter — спека (без кода)

**Дата:** 2026-07-22 · **Ветка:** `arc/dashboard-spec` · **Опора:** AUDIT.md (фаза 1) + COMPETITORS.md (фаза 4) + PROBLEMS.md (фаза 3) · **Статус:** черновик спеки для решения Даниила. Кода нет.

**Решения Даниила зафиксированы в §11** (бизнес + инженерные дефолты). Ключевое для этой спеки:
- Сегмент: **предприниматели в целом** — универсальный визард, playbook-шаблоны по вертикалям.
- Монетизация: **подписка за подключённый аккаунт**; дашборд ведёт учёт `клиент → тариф → расход $` для юнит-экономики (тарифная сетка — конфигом).
- Дисклоуз: **honest by default + рубильник клиента** (существующий `/honesty free` с consent); активных инструкций сокрытия не добавляем — поведение как есть.
- Инженерные дефолты помечены **«default, changeable»** — приняты, но не забетонированы.

---

## 1. Цель и принципы

**Цель.** Онбординг и ведение клиента **без ручной правки yaml и без SSH**. Мультиклиентность с первого дня. Дашборд — это **пульт чужих бизнесов**, поэтому auth и изоляция секретов — не фича, а условие существования (PROBLEMS P1/P2).

**Принципы:**
1. **Тонкий слой, не переписывание.** Дашборд управляет тем, что уже есть в chatter: 4 файла конфига на клиента, `.versions/`, `control_events`, heartbeat, гардиан, `/reload`, `yaml_edit`. Ядро (`run.py`, `telethon_run.py`, `core/*`) **не рефакторим** — дашборд читает его состояние и пишет его конфиги, а не лезет внутрь конвейера.
2. **Файлы конфига остаются источником правды.** Дашборд-редактор пишет ровно те же `persona.md/knowledge.md/playbook.md/settings.yaml`, что раннер уже умеет читать и hot-reload'ить. Каждая правка → снапшот в `.versions/` (уже есть) → откат из UI бесплатно.
3. **Control-plane / data-plane split.** Дашборд (control+view) отдельно от раннеров (data). Падение дашборда не роняет живые диалоги; падение раннера видно в дашборде через heartbeat.
4. **Безопасность с первого дня.** Session-файлы и `.env` дашборд **не отдаёт наружу никогда** (PROBLEMS P1). Auth обязателен до первого клиента.

## 2. Что переиспользуем vs что строим

| Уже есть в chatter (переиспользуем) | Строим в дашборде |
|---|---|
| 4 файла конфига на клиента + строгая валидация (`config/loader.py`) | Веб-редактор этих файлов с валидацией в браузере; **+5-й файл `examples.yaml`** (М8, few-shot) |
| `yaml_edit.py` (точечная правка funnel_gate/honesty с сохранением комментариев) | HTTP-ручки поверх него для тумблеров |
| `.versions/` (снапшоты, `/rollback`) | Кнопка «откатить» в UI |
| `control_events` (журнал эскалаций/тапов/`bot_question`) | Аналитика читает эту таблицу |
| heartbeat + гардиан + semidemo-флаги | Control-plane, обобщающий semidemo-флаг в реестр клиентов |
| `create_client.py` (скаффолд 4 файлов из шаблона) | Онбординг-визард вызывает его логику |
| `telethon_login.py` (интерактивный логин → `.session`) | Визард подключения аккаунта (QR/код) поверх него |
| control-bot (эскалации, тапы, команды) | Лента/inbox дублирует карточки в вебе + ответ владельца |
| notifications (Telegram-алерты) | Событийная шина расширяет это до вебхуков/Sheets |

**Вывод:** ~70% механики уже написано. Дашборд — это HTTP-фасад + фронт + control-plane над раннерами + событийная шина.

## 3. Стек (с обоснованием)

| Слой | Выбор | Почему |
|---|---|---|
| Backend | **FastAPI** | Уже основание Jarvis (`app/` на FastAPI), общий стиль, async, автогенерация OpenAPI = наш API-контракт бесплатно. |
| Хранилище (control-plane) | **SQLite** (реестр клиентов, users дашборда, аудит) отдельно от per-client chatter-БД | Не смешивать пульт и переписку лидов; chatter-БД остаётся per-client как сейчас. |
| Фронт | **FastAPI + Jinja + HTMX/Alpine, серверный рендер, без SPA** (default, changeable) | Форма-центричный CRUD + лента + графики. SSR проще, быстрее к MVP, ложится на FastAPI без отдельного билда. |
| Auth | **Пароль + 2FA владельца, argon2, session-cookie; роли owner/client, скоупинг по клиенту с первого дня** (default, changeable) | Пульт чужих бизнесов → auth с первого дня (PROBLEMS P1). Публичных ручек нет. OAuth/SSO — v2. |
| Real-time | **SSE** (Server-Sent Events) для ленты/статуса | Односторонний поток событий, проще WebSocket, ложится на FastAPI. |
| Деплой | **Текущая инфра** — backend-гардиан-таск рядом с `:8010`, за тем же ENFORCE-middleware | Не плодить инфру; auth-middleware уже боевой (память: security-audit). |

## 4. Как дашборд управляет раннерами (ключевой технический вопрос)

Сегодня: раннер — **один процесс на Telegram-аккаунт**, поднимается гардианом, состав персон — из `active.yaml`, semidemo-флаг пинит окружение под volska.

**Модель `client → N accounts` с самого начала** (решение Даниила, §11 B-доп). Разделяем две сущности:
- **client** — платёжно-владельческая сущность (предприниматель/бизнес): имя, тариф, кабинет. Один клиент может подключить **несколько аккаунтов**, у каждого своя персона/конфиг.
- **account** — то, что 1:1 ложится на сегодняшний раннер: один Telegram-аккаунт = свой `.session` (зашифрован), своя БД, свой каталог конфига, свой процесс раннера под гардианом. Персона задаётся на уровне аккаунта.

> Схему закладываем `client → N accounts` сразу, а не `client → 1`, чтобы не переделывать при bulk-подключении. «Один аккаунт, несколько персон» (как demo+demo2 в `active.yaml`) остаётся частным случаем внутри одного account.

**Архитектура control-plane:**
- **Реестр** (SQLite дашборда, см. §8): `client{...}` + `account{ id, client_id, slug, tg_ref, session_ref(зашифр.), db_path, config_dir, enabled, runner_state }`.
- **Обобщённый гардиан-механизм.** Semidemo-флаг (`state\chatter_semidemo_volska.flag`) — прото-реестр на один аккаунт. Обобщаем: гардиан читает реестр **аккаунтов**, для каждого `enabled` держит живой раннер с его пинами окружения (`CHATTER_PERSONAS`, `TELETHON_SESSION`, `CHATTER_DB`).
- **start/stop/revert** из дашборда = запись в реестр (`enabled`/`runner_state`) + сигнал гардиану; гардиан приводит реальность к желаемому (поднять/убить процесс). Дашборд **не запускает процессы напрямую** — только декларирует желаемое состояние, гардиан исполняет (как сейчас с флаг-файлом). Безопасно: тот же паттерн.
- **Живой статус** — heartbeat каждого аккаунта + PID-состояние от гардиана → зелёный/жёлтый/красный.
- **reload без рестарта** — дашборд записал конфиг → `/reload` этого аккаунта либо `auto_reload` по mtime. Рестарт нужен только при смене сессии.

> ⚠️ **Catch-up-риск (AUDIT §1.7) в UI.** При включении аккаунта / открытии funnel_gate дашборд ОБЯЗАН показывать предупреждение: «на старте бот ответит на непрочитанное за 24ч через текущее состояние гейта». Гейт-тумблер — с подтверждением (как `/funnel_gate on confirm`).

**MVP-упрощение:** в v1 control-plane управляет аккаунтами, которые **уже подключены** (залогинены владельцем). Полная авто-провизия процесса из визарда (подключил в браузере → гардиан сам поднял раннер) — стык визарда и гардиана, довести в v1 если успеваем, иначе v2 (§10).

## 5. Модули

### М1. Клиенты (список + управление)
- Карточки клиентов: имя, персона, аккаунт, **живой статус** (раннер/гардиан/heartbeat — зелёный/жёлтый/красный), последняя активность.
- Действия: **start / stop / revert** (через control-plane §4), открыть конфиг (М3), открыть ленту (М5), открыть аналитику (М6).
- Revert = откат конфига на предыдущий снимок `.versions/` (существующий `/rollback`).

### М2. Онбординг-визард
Универсальный визард (сегмент — предприниматели в целом), по модели Kommo «4 блока» (COMPETITORS §2), ложится на 4 файла конфига. Один клиент может пройти визард несколько раз → **N аккаунтов** (§4). Playbook-шаблоны — **по вертикалям**: услуги, продажи, недвижимость, агентства, ивенты.

1. **Подключение Telegram-аккаунта — три пути** (поверх `telethon_login.py`):
   - **QR (default)** — скан, как BotHelp.
   - **Код на номер (fallback)** — телефон → код → 2FA, если QR не подошёл.
   - **По ключу (v2, после P1/P2)** — вставка `session string` и/или `api_id+api_hash` в поле, плюс **bulk-режим** (клиент с несколькими аккаунтами загружает пачкой, каждый со своей персоной/конфигом).
   ⚠️ Общие требования всех путей: `.session`/ключ **шифруются at rest** (зависимость P1/P2), в UI **всегда маскированы, повторно не показываются**; **пароль/2FA клиента НЕ храним** (вводится разово при логине); при вводе — **проба коннекта с понятной ошибкой** вместо тихого фейла; каждое подключение/отключение аккаунта — в **аудит-лог** (кто, когда, какой аккаунт). Путь «по ключу» идёт строго ПОСЛЕ закрытия P1/P2 (ROADMAP).
2. **Анкета персоны** → `persona.md` (первая строка — проза для честного раскрытия, требование `create_client.py`).
3. **Загрузка знаний** — файлы/текст/URL → `knowledge.md`. RAG-синк без переобучения (Respond.io) — v2; v1 = собрать в один markdown.
4. **Выбор playbook-шаблона по вертикали** → `playbook.md` (воронка, keyword-эскалации, цели). Плюс `settings.yaml` из шаблона `create_client.py`.
5. **Приклади діалогів (М8)** → `examples.yaml`. В v1 — ручной ввод пар; в **v1.5** — импорт экспорта Telegram (JSON) с авто-нарезкой и экраном «оставить/выкинуть» + анонимизация (ключевая фича онбординга: клиент показывает реальные диалоги, а не пишет промпт).
- В конце — снапшот в `.versions/` + регистрация аккаунта в реестре (disabled, пока владелец не нажал start).

### М3. Редактор конфига
- persona / knowledge / playbook / settings в браузере, с **валидацией** (переиспользуем `loader.py` серверно: сохранение прогоняется через тот же парсер, опечатка в поле → та же ошибка, что ловит раннер).
- Улучшения из конкурентов: **few-shot примеры ответов** (Chatfuel) в persona-редакторе; **структурированные правила** вместо сырого промпта (Kommo, лимит N правил) — маппинг на `_STYLE_*`/playbook. Связано с PROBLEMS P12 (вынести хардкод-тексты в конфиг — предпосылка для полноценного редактора).
- Сохранение → снапшот `.versions/` → `/reload` без рестарта. Кнопка «откатить» (список версий).

### М4. Тумблеры
Поверх существующих `yaml_edit.py` + команд:
- **honesty** (honest / free_owner_liability) — с consent-флоу и именем клиента (как `/honesty ... confirm`; дефолт honest).
- **funnel_gate** (on/off) — с подтверждением + предупреждением о catch-up (§4).
- **pause / resume** — глобально и per-контакт (kill_switch + mute).
- **allowlist / denylist** — редактор списков.
Каждый тумблер — HTTP-ручка, пишет в тот же yaml + reload; поведение 1:1 с командами пульта (уже под тестами, фаза 2 §3).

### М5. Лента / inbox
- Карточки эскалаций (дубль того, что уходит в control-bot), takeover-события, деградации, `bot_question`-всплески — потоком через SSE.
- **Ответ владельца из дашборда** → отправляется тем же раннером в диалог лида (для лида = «сообщение персоны»), эквивалент ручного ответа с телефона. Ставит takeover-паузу (существующий механизм).
- **Кнопки как в карточке**: ▶️ вернуть · ⏸ ещё 1ч · 🔴 стоп · ✅ оставить боту — те же callbacks, что в control-bot.
- Handoff-нарратив (Respond.io §2): «AI глохнет мгновенно при перехвате» — у нас уже есть (re-check mute перед каждой отправкой), подать явно в UI.

### М7. Агент (редактор персоны/системного промпта)
Отдельная вкладка (не «сырой промпт»), редактирует то, из чего `brain.py` собирает системный промпт:
- **Тон / роль / персона** → `persona.md` (первая строка — проза для честного раскрытия, требование `create_client.py`). Плюс структурированные правила стиля (Kommo-подход, лимит N правил) вместо простыни — маппинг на `_STYLE_*`. Связано с PROBLEMS P12 (вынести хардкод-стиль в конфиг — предпосылка полноценного редактора).
- **Красные линии — переключателями, НЕ свободным текстом** (чтобы клиент не снёс случайно): `strict_knowledge` (не выдумывать цифры), `safe_payment` (безопасные каналы оплаты), guard дедлайнов (не обещать срок вне knowledge). Первые два — уже поля `settings.yaml` (`strict_knowledge`, `safe_payment_reply`, `forbidden_terms`); guard дедлайнов — небольшое добавление (флаг + пост-фильтр по образцу `unbacked_claim`). Тумблеры пишут `settings.yaml`, не трогая прозу персоны.
- **Требования модуля:** валидация перед сохранением (через `loader.py`), **превью итогового промпта** (что реально уйдёт в модель — сборка `build_system_prompt` серверно, read-only), версии через существующий `.versions/` с **откатом в один клик**, **reload без рестарта**.

### М8. Приклади діалогів (few-shot)
Новый файл конфига **`clients/<slug>/examples.yaml`** (обоснование формата — см. врезку ниже). Ключевая фича онбординга: клиент **не пишет промпт, а показывает свои реальные диалоги**.

**Структура примера** (`examples.yaml`):
```
examples:
  - id: ex1
    tag: price            # ціна | заперечення | дожим | дедлайн | скарга | знайомство
    priority: 10          # для отбора при лимите
    enabled: true
    turns:                # пара или цепочка
      - {role: client, text: "а скільки коштує?"}
      - {role: assistant, text: "залежить від... орієнтовно X, підкажу точніше якщо..."}
```

**Отбор в промпт (стратегия + лимит).** Ключевое ограничение — **prompt-caching**: примеры уходят в системный промпт (кэшируемый префикс). Если отбирать **динамически per-сообщение** по тегу — блок примеров меняется на каждый ответ → **кэш ломается**. Поэтому:
- **v1 — статический курируемый набор (рекомендую).** Отбор считается **один раз на версию конфига**, не per-сообщение: берём `enabled` примеры, покрываем все теги (по одному-двум на сценарий), сортируем по `priority`, режем по **бюджету ~1200–1500 токенов** (примерно 8–12 коротких пар). Блок стабилен весь диалог → **полностью кэшируется**. «Отбор по тегу/релевантности» превращается в **помощник курирования** в редакторе (баланс по сценариям), а не рантайм-выбор.
- **Альтернатива (v2, опционально) — динамический per-тег отбор.** Больше релевантности, но каждый ответ — свой блок примеров → кэш системного промпта не работает на части с примерами. Приемлемо только если релевантность важнее экономии; по умолчанию НЕ берём.

**Влияние на стоимость** (замеры-логика, см. ROADMAP §эконом.): статический блок ~1500 токенов добавляется к системному промпту brain (в классификатор примеры НЕ идут). Без кэша: +~$0.045/диалог (10 ответов × 1500 × $3/1M). С кэшем: +~$0.005/диалог. **Примеры увеличивают статичную часть промпта → делают кэш ЕЩЁ выгоднее** — прямая связь с P3.

**Импорт истории Telegram (v1.5).** Загрузка экспорта переписки (JSON) → **авто-нарезка на пары** «клиент→ассистент» → экран **«оставить/выкинуть»** (оператор курирует, отмечает тег/приоритет) → в `examples.yaml`.
- ⚠️ **Приватность (связь с PROBLEMS P8).** Экспорт содержит ПДн третьих лиц. При импорте — **анонимизация имён/контактов** (заменять на плейсхолдеры `[клієнт]`, вырезать телефоны/@-хендлы/ссылки) ДО показа и ДО записи в конфиг. Примеры хранятся в незашифрованном конфиге (как и остальные файлы) → анонимизация обязательна, и это ещё один довод к P1/P2 (шифрование). Импорт — только по явному действию, с аудит-логом.

**Поддержка в `brain.py`.** При сборке промпта — новая секция `=== ПРИКЛАДИ ДІАЛОГІВ ===` из отобранного блока (аддитивно, конвейер не меняем). `examples.yaml` добавляется в `CONFIG_FILES` (`config_versions.py`) → версионируется и откатывается вместе с остальными 4 файлами (5-й файл конфига).

> **Врезка — почему `examples.yaml`, а не `examples.md`:** persona/knowledge/playbook идут в модель дословно как проза → markdown. У примера же есть **поля** (tag/priority/enabled/turns) и нужен **программный отбор** по тегу и бюджету токенов + надёжный round-trip из редактора/импорта. Это структурированные данные → YAML со строгой валидацией (стиль `loader.py`). В промпт из YAML собирается текстовый блок диалогов — модель видит естественную переписку, хранение остаётся структурным.

### Экран аккаунта — вкладки
Конфиг привязан к **аккаунту** (не к клиенту — модель `client → N accounts`, §4/§8). Вкладки:
**Агент** (М7) · **Знання** (knowledge, М3) · **Приклади** (М8) · **Playbook** (М3) · **Тумблери** (М4) · **Канали** (подключение/статус аккаунта, М1/М2) · **Інтеграції** (шина, §6) · **Аналітика** (М6).

### М6. Аналитика + учёт расхода (юнит-экономика)
Читает `control_events` + chatter-БД (только агрегаты, не сырую переписку без нужды — P8) + таблицу usage:
- Диалоги, лиды, эскалации, время ответа, воронка (стадии `contacts.state`).
- **Счётчик «ты бот?»** (`bot_question`, реализован в фазе 2) — пилотный сигнал доверия/подозрения.
- **Учёт расхода (решение §11 A2/A7).** На **каждый** вызов LLM пишем в БД `usage{ account_id, contact_ref, input_tokens, output_tokens, cache_read_tokens, ts }` — берём прямо из `response.usage` (см. §8). $ считаем по **прайсу из конфига** (не хардкод), агрегируем `клиент → тариф → расход $/мес` для юнит-экономики. До prompt-caching — `cache_read=0`; после (P3) — видно экономию по факту.
- **Тариф на клиента** — поле в реестре (`client.tariff`), тарифная сетка — **конфигом**, дашборд её не выдумывает; сопоставление тариф↔расход для маржи.
- Операционные метрики уровня Wati/Umnico (§2): время ответа, активность по аккаунтам.

> Точка врезки usage-логгера — `AnthropicLLM.complete` (`core/llm.py`): один вызов = одна строка usage. Это единственная правка ядра, и она аддитивная (не меняет конвейер). Согласовать с P3 (кэш меняет форму usage — cache_read появляется там же).

## 6. Событийная шина + адаптеры (интеграционный зазор)

**Контракт событий** (единый для всех адаптеров), см. `API_CONTRACT.md`:
- `lead.created` · `lead.qualified` · `lead.escalated` · `lead.status_changed` · `dialog.taken_over` · `dialog.resumed` · `bot_question.asked`.
- Каждое событие: `{ event, client_id, contact_ref, ts, payload }`. Источник — тот же слой, что пишет `control_events` (расширяем эмиттер, не трогая конвейер).

**Адаптеры как плагины** (интерфейс `emit(event) -> None`):
- **MVP:** generic **webhook** (POST на URL клиента, HMAC-подпись — уже есть паттерн `N8N_JARVIS_WEBHOOK_SECRET`) + **Google Sheets** (append строки; креды через `GOOGLE_SERVICE_ACCOUNT_JSON`, уже в `.env`).
- **Интерфейсом (v2):** amoCRM/Kommo, CSV-экспорт. В спеке — контракт и интерфейс адаптера; реализация двух в MVP, остальные — заглушки под тем же интерфейсом.

> Это закрывает разрыв с CRM, не встраивая CRM внутрь: chatter остаётся «AI-продавец от первого лица», а сделки/воронка живут в CRM клиента через шину (в отличие от Kommo, где CRM встроена — наш выбор осознанный, COMPETITORS §3).

## 7. Auth и безопасность (условие, не фича)

- **Auth с первого дня** (решение §11 A6): пароль + **2FA владельца**, argon2, session-cookie, за тем же ENFORCE-middleware, что `:8010` (память: security-audit-highs). **Публичных ручек нет.**
- **Роли `owner` / `client` и скоупинг по клиенту — с первого дня** в схеме и в проверках доступа (каждая ручка проверяет, что ресурс принадлежит клиенту вызывающего). Но в MVP **редактирует только владелец** (§11 A11) — клиентские роли (лента + тумблеры в своём кабинете) включаются в v2 без миграции схемы, т.к. скоуп заложен сразу.
- **Session-файлы/ключи/`.env` наружу не отдаются никогда** — ни через API, ни в логах, ни в ленте (P1/P2). Дашборд оперирует ссылками (`session_ref`), не содержимым; ключи в UI маскированы и повторно не показываются; **пароль/2FA клиента не храним**.
- **ПДн лидов** (P8): аналитика по умолчанию — агрегаты; полная переписка — только по явному действию, с аудит-логом доступа.
- **Аудит действий дашборда** — отдельная таблица (кто/что/когда переключил, **какой аккаунт подключил/отключил**): критично для пульта чужих бизнесов и для фичи «подключение по ключу».
- **Порядок (решение §11 A8):** P1/P2 (шифрование секретов at rest) — **блокер перед первым платящим**; дашборд разрабатывается **параллельно**; **подключение чужих аккаунтов включается только после закрытия P1/P2**. Дашборд P1/P2 **обостряет** (централизует доступ к N чужим аккаунтам). Секреты сейчас — **минимальный вариант** (шифрование session+`.env`, ACL); полный vault — **при 3+ клиентах** (§11 A9).

## 8. Модель данных (control-plane, отдельная БД)

Схема заложена `client → N accounts` с самого начала (§4, §11 B-доп):

- `client{ id, display_name, tariff, created_at }` — платёжно-владельческая сущность.
- `account{ id, client_id→client, slug, tg_ref, session_ref(зашифр., маскир.), db_path, config_dir, enabled, runner_state, connected_via(qr|code|key), created_at }` — 1:1 с раннером; `session_ref` шифруется at rest (P1/P2), наружу не отдаётся.
- `dashboard_user{ id, login, argon2_hash, totp_secret, role(owner|client), client_id?(для роли client), created_at }`
- `usage{ id, account_id→account, contact_ref, input_tokens, output_tokens, cache_read_tokens, ts }` — строка на каждый LLM-вызов, из `response.usage`; источник юнит-экономики (§6).
- `audit_log{ id, user_id, action, target, detail, ts }` — включая connect/disconnect аккаунта.
- `integration{ id, account_id→account, type(webhook|sheets|...), config_json, enabled }`
- Аналитика и лента **не дублируют** переписку — читают per-account chatter-БД (`control_events`, `contacts`, `messages`-агрегаты) по `db_path` из реестра. `usage` — единственная новая «горячая» таблица дашборда.

> **Операционные ресурсы (конфиг, тумблеры, лента, статус) — на уровне account.** Биллинг и юнит-экономика — роллап на уровень client. Тарифная сетка — конфигом, не в схеме.

**Файлы конфига на аккаунт (в `config_dir`):** `persona.md` · `knowledge.md` · `playbook.md` · `settings.yaml` · **`examples.yaml`** (М8, новый). Все пять версионируются через `.versions/` (добавить `examples.yaml` в `CONFIG_FILES`, `config_versions.py`) — единственная правка ядра для М8, аддитивная.

## 9. Деплой

- FastAPI-приложение рядом с текущим backend, свой guardian-таск (S4U/Highest, как `JarvisBackendGuardian`), за ENFORCE-middleware.
- Control-plane и раннеры — разные процессы; гардиан(ы) раннеров расширяются на реестр клиентов (§4).
- Откат дашборда не влияет на живые диалоги (раннеры автономны).

## 10. MVP-срез

**v1 (2–3 недели) — «вести уже подключённый аккаунт без yaml и SSH»:**
- Auth (§7): пароль + 2FA владельца, роли/скоуп в схеме, **редактирует только владелец** (§11 A11) + аудит-лог.
- М1 Клиенты/аккаунты: список `client → N accounts`, живой статус, start/stop/revert над аккаунтами.
- **М7 Агент**: редактор персоны + красные линии переключателями + превью промпта + `.versions/`-откат.
- М3 Редактор конфига (Знання + Playbook, валидация, `.versions/`-откат, reload).
- **М8 Приклади** (few-shot): `examples.yaml` — ручной ввод/редактирование пар, статический отбор в промпт с бюджетом токенов, поддержка в `brain.py`. **Импорт истории Telegram — v1.5.**
- М4 Тумблеры (honesty c consent+именем клиента / funnel_gate / pause / allowlist) — поверх `yaml_edit`.
- М5 Лента: карточки эскалаций + ответ владельца + кнопки (SSE).
- М6 Аналитика + **usage-логгер** (строка на вызов, $ по прайсу-конфигу, тариф↔расход).
- Событийная шина: контракт + **webhook + Sheets** адаптеры.

**v1.5 (врезка) — импорт истории для М8:** экспорт Telegram (JSON) → авто-нарезка на пары → экран «оставить/выкинуть» + анонимизация ПДн (P8). Небольшой самостоятельный кусок поверх готового М8; вынесен из v1, чтобы не раздувать первые 2–3 недели.

**v2 — «онбординг с нуля в браузере + клиентские роли + подключение по ключу»:**
- М2 Онбординг-визард целиком (QR/код → авто-провизия раннера гардианом); **третий путь — по ключу (session string / api_id+api_hash) + bulk**, строго после P1/P2.
- **Клиентские роли** (owner уже в MVP; client-кабинет: своя лента + тумблеры) — без миграции схемы (скоуп заложен).
- Адаптеры amoCRM/Kommo + CSV; RAG-синк знаний без переобучения.
- Редактор персоны с few-shot примерами; полный vault секретов (при 3+ клиентах, §11 A9).

**Зависимость-блокер:** P1/P2 (шифрование секретов) — **до первого платящего**; дашборд параллельно; **подключение чужих аккаунтов (любым путём) — только после P1/P2**.

**B-дополнение (2026-07-22, backlog/v2): подключение по ключу + bulk.**
Третий путь подключения — **session string и/или api_id+api_hash** вставкой в поле, плюс **bulk-режим** (один клиент → N аккаунтов, каждый со своей персоной/конфигом).
